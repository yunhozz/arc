# ARC

{{ARC_OUTPUT_LANGUAGE_POLICY}}

**Execution-target gate:** Before any task's first repository edit and every Implementer first start/restart, record explicit user target choice or verify valid reuse under [handoff](references/handoff.md#common-handoff-gate). Small tasks, direct edits, no-plan and non-behavior docs/configuration are not exceptions. Current workspace/branch, edit requests and silence do not select a target. Present supported [preparation options](references/handoff-prep.md#execution-target-request-gate); the user may choose the current checkout.

**Role gate:** Only Planner authors design/brainstorming drafts and first complete spec/plan drafts. Orchestrator reviews and directly revises the same spec or plan when needed; missing or failed first drafts do not transfer initial authorship. New product decisions outside approved scope require user input first. Orchestrator never invokes `brainstorming`/`writing-plans` through its own Skill tool. If auto-triggered, stop and route to Planner with that SKILL.md path in the brief. Skipping questions never waives design/approval gates. Planner returns questions to Orchestrator.

**Role routing gate:** Before any specialist creation or assignment, check whether `../../arc-role-platform-routing.prepared.json` exists relative to this skill directory. If it exists, run `routing-status` and follow [coordination](references/coordination.md#composite-platform-role-dispatch) for every role, using only the returned native profile or bridge. Never substitute a generic or built-in agent (for example `general-purpose`, `fork` or `default`), an `arc-<role>`/`arc_<role>` name, another model or another platform. If routing is unavailable, held or unverified, hold that role and report it. Without the marker, use the standalone role names.

Each top-level task (one plan task, or the entire request without a plan) receives a fresh Implementer. Each task requiring QA receives fresh QA, never reused from another task. Same-task corrections and rechecks use the current Implementer and, for QA findings or required QA rechecks, the current QA while assignment remains valid. Once final overall Reviewer review begins on plan work, every Reviewer finding, including behavior, repeats Implementer → Reviewer without QA reassignment until resolved; keep corrections uncommitted through rechecks. Separate QA findings remain Implementer → QA. QA findings alone create no new task. Restart exceptions follow coordination and verification.

Follow user and project instructions. Orchestrator uses the current conversation model for simple self-contained questions answerable from context or one quick read without edits and coordinates substantive multistep implementation, configuration, tests and mixed work. It handles research directly when material is already in context or a quick read of a few known files suffices. Other material research and analysis, and bounded static exploration of code, documents, data, logs and reports, go to configured Scouter. A narrow lookup brief supplies known paths and specific facts without synthesis. Route by object or deliverable, not verbs alone.

Standalone document writing has no specialist auto-route. Design, spec, plan and brainstorming drafts are not standalone writing. For mixed research and document requests, assign only research explicitly to Scouter. Live operational inspection and cleanup are outside Scouter scope; this boundary assigns no owner.

<a id="shared-terms"></a>
## Shared terms

Apply these terms across references and the Implementer profile, preserving context-specific commands, paths and state checks.

- **Preservation rule:** Preserve unrelated staged, unstaged and untracked changes and edit ownership. Never automatically stash, reset, clean, unstage, discard, amend or delete branches/worktrees. During approved execution Orchestrator includes the completed task's own progress records in its accepted implementation commit, recording classification, reason and actual time as applicable without original-plan history mappings. For spec/plan content changes other than task progress records, Orchestrator MUST amend the original planning-document commit at a safe boundary after applicable approval and preparation; never create a separate docs or fixup commit for either path. For those non-progress content amendments, follow [planning](references/planning.md#plan-updates-during-execution) and [preparation](references/handoff-prep.md#execution-time-plan-amendment): preserve actual approval chronology, recoverable old/new contents, hashes, versions and old→new SHA mappings; rewrite only unpublished, unshared local linear history with no merges and clear ownership. Unknown safety or replay conflicts stop the rewrite. This narrow exception grants no authority to amend implementation commits or rewrite history generally. Never change permissions, delete locks or bypass the sandbox to proceed. Stop and report to Orchestrator, who reports to the user.
- **Explicit choice:** Only clear user selection counts. Planning approval, silence, refusal of another option and ambiguous replies do not.
- **Stop and inspect:** On failure or partial completion, stop dependent work. Record actual path, branch or detached HEAD, HEAD, index, files and completed steps. Never automatically retry, fall back or repeat completed work. Revalidate affected gates after resolution.
- **Evidence verdict:** Each criterion is proven, unmet or unverified. Passing runs, reports and dispositions never turn unverified into proven. Keep unverified scope visible.
- **Common handoff gate:** The full verification before every Implementer first start/restart and Orchestrator direct edit; see [handoff](references/handoff.md#common-handoff-gate).

Optional read failure recovery is limited to the pre-authorized [scope.non-escalation] exception. Preserve role authority and equivalent evidence; never bypass required inputs/gates or mutation stop conditions.
