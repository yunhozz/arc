# Planning and approval

CEO classifies scope before implementation. A simple, narrow, understood, readily reversible change with no dependent stages or cross-component shared state, lifecycle, or integration-order concerns may use the CEO direct path only after a short design receives explicit user approval before the first edit. The short design must state scope and files, why every eligibility criterion holds, acceptance criteria, and focused verification. Before editing, verify the Coder first-start handoff gate, including explicit execution target choice or valid reuse, intended workspace/repository, Git state (branch or detached HEAD, HEAD, staged/unstaged/untracked changes), ownership/preservation, and no unresolved failure or partial completion. Edit only approved files and run focused checks afterward, connecting acceptance criteria to evidence. Silence, ambiguous replies, and approval of other work are insufficient. Follow the full CEO direct-path contract in the adjacent SKILL.md; stop and reclassify if scope or risk changes. Significant work needs a design/specification and implementation plan at a depth matching its risks. Load brainstorming and writing-plans as applicable. Planner reads evidence and returns drafts; CEO saves them and obtains explicit user approval. Planner's read-only tools do not authorize saving files or executing commands.

Significant risk includes shared role/behavior contracts, shared state, lifecycle/integration order, security/permissions, data loss/migration, public interfaces, or costly installation/deployment/rollback, and excludes work from the CEO direct path. Substantial behavior or contract changes are significant regardless of file count. Unclear risk requires investigation or the higher flow; do not infer eligibility from a small file count.

Record the complete applicable document set with absolute paths, purpose and coverage, approved versions, approval evidence, dependencies/order, and excluded documents with rationale. Resolve scope ambiguities and required unfinished documents before implementation. Preserve prior approved decisions; substantive changes require renewed approval. Administrative status updates must accurately describe actual progress.

After approval: explicit execution-target choice, planning-document batch commit, final Git state verification, canonical handoff, then Coder. A spec or plan approval is not an execution-target choice. Never retroactively claim a missed gate passed. Return scope changes and unresolved decisions to the user through CEO. Define verifiable acceptance criteria, meaningful failure-first tests, scoped ownership, and QA/Reviewer follow-up before code work.
