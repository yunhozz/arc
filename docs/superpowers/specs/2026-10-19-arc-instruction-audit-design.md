## 1. 목적과 현재 상태

ARC가 소유하는 Codex·Claude 지침 문서를 전수 조사하여 모순, 불필요한 중복, 플랫폼 간 의미 편차, 오래된 규칙, 검증 공백을 식별하고 승인된 범위에서 개선한다.

문서 수나 지침 길이를 줄이는 것 자체를 목표로 삼지 않는다. 역할별로 필요한 안전장치와 플랫폼별 적용법을 보존하면서, 같은 상황에서 일관된 행동을 요구하고 그 의미를 확인할 수 있게 만드는 것이 목적이다.

완료 시 다음을 설명할 수 있어야 한다.

1. 조사 대상 파일과 생성 지침을 빠짐없이 확인했는가.
2. 각 지침의 의무·금지·예외·중단 조건을 검토했는가.
3. 발견한 문제마다 유지·수정·삭제·보류의 근거가 있는가.
4. 승인된 수정이 실제 배포·생성 지침에 반영되는가.
5. 검증이 확인하는 범위와 확인하지 못한 범위는 무엇인가.

S0에서 Scouter가 **29개 지침 문서 전체와 G01 생성 지침 텍스트의 의미 검토를 완료**했다. 여덟 일반 reference 쌍과 역할별 반복 지침도 비교했다. 제거 가능한 문서나 역할별 안전장치는 입증되지 않았다.

이는 지침 수정, 검사 실행, 실제 설치 동작 또는 agent의 런타임 준수 검증 완료를 뜻하지 않는다.

F01·F02는 기존 승인된 개선 방향을 유지한다. 사용자는 F08에 대해 **“Orchestrator 전용으로 정합화 (추천)”**를 선택했다. 따라서 두 런타임에서 수락 후 집중 커밋의 소유·실행 권한을 Orchestrator에만 둔다. 이 정책 결정은 반영하되, 수정 명세와 개정 계획의 승인은 별도로 필요하다.

## 2. 승인된 범위

### 2.1 조사 대상

조사 대상은 **29개 지침 문서와 생성 전역 지침 원본 한 곳**이다.

- Codex: 핵심 `SKILL.md`, 역할 프로필 5개, 일반 references 8개, Codex 전용 `handoff-worktree.md` — 15개.
- Claude: 핵심 `SKILL.md`, 역할 프로필 5개, 일반 references 8개 — 14개.
- 생성 전역 지침: `lib/installer/global-config.mjs`에서 ARC 관리 블록으로 생성하는 지침 텍스트.

TOML 역할 프로필은 agent에게 전달되는 지침과 그 적용 문맥을 검토한다. 모델 선택이나 런타임 구성의 일반 최적화로 범위를 확대하지 않는다.

### 2.2 보조 근거

다음은 조사 대상 지침의 배포·생성 경로 확인 또는 승인된 변경 검증에 필요한 부분만 참조할 수 있다.

- `package.json`
- installer 및 manifest 관련 코드
- 관련 계약·정책·payload 테스트
- 무결성과 설치 검증에 필요한 기존 자산·스크립트

보조 코드와 자산의 일반적인 구조 개선, 중복 제거, 성능 최적화, 이관 기록 정리는 이번 범위에 포함하지 않는다. 지침 변경을 전달하거나 검증하기 위한 최소한의 수정만 허용하며, 별개의 문제를 발견하면 범위 밖 발견으로 전달한다.

S0에서는 package·manifest를 전달 경로 확인에만 사용했다. 테스트 내용은 조사하지 않았고 검사를 실행하지 않았다.

### 2.3 제외 대상

- 작업 시작 전에 존재하던 모든 `docs/**` 내용
- `codex/skill/references/superpowers/**`
- `claude/skill/references/superpowers/**`
- `models.toml`, 모델 helper 코드, `codex/tools/codex_token_usage.py` 등 지침 문서가 아닌 자산의 일반 감사
- 저장소 밖 설치본이나 upstream의 수정
- 실제 agent 실행을 통한 광범위한 런타임 준수 평가
- 공통 원본 생성기 도입과 배포 구조 재설계

제외된 문서의 내용은 읽거나 평가하지 않는다. 범위 내 문서가 제외된 경로를 참조한다는 사실은 기록할 수 있지만, 그 사실을 참조 대상 내용의 적정성 판단으로 확장하지 않는다.

새 명세와 계획은 이번 작업의 산출물이다. 기존 `docs/**`를 조사 입력으로 사용하는 것과 구분한다.

## 3. 확정된 설계 결정

### D1. Planner 작성 책임 유지

현재 `AGENTS.md`에 따라 설계·명세·계획 초안은 Planner가 작성한다. Orchestrator는 통합·저장·검토·승인 요청과 구현 수락을 담당한다.

일반 planning reference에 있는 사용자 지정 작성 책임 예외가 이 역할 계약과 충돌하지 않도록 정리한다. 이번 변경으로 Planner 전담의 새로운 예외나 다른 역할의 작성 권한을 도입하지 않는다.

### D2. 현재 플랫폼 파일 구조 유지

Codex·Claude의 기존 파일 구조를 유지한다. 두 플랫폼의 지침을 하나의 원본에서 생성하는 체계는 도입하지 않는다.

공통 정책의 의미를 맞추고, 필요한 플랫폼 차이는 이유를 기록하여 보존한다. 바이트 단위 동일성을 수락 기준으로 사용하지 않는다.

### D3. 반복 지침의 문맥 검토

역할 프로필·핵심 지침·일반 reference·생성 전역 지침에서 같은 내용이 반복되더라도 자동 삭제하지 않는다.

어떤 역할이 해당 지침만 읽는 상황에서도 필요한 보호를 받는지 확인한다. 삭제 또는 링크 대체는 규칙의 도달 가능성과 의미 보존을 설명할 수 있을 때만 수행한다.

S0에서는 제거할 수 있는 역할별 안전장치를 입증하지 못했다. 역할이 핵심·reference 전체를 다시 읽지 않는 실행 문맥을 고려하여 직접 보호 지침을 유지한다.

### D4. 조사표는 명세 부록에 유지

별도 audit report나 matrix 파일을 만들지 않는다. 파일별 조사표와 발견별 결정표를 이 명세 부록에 유지하고, 구현·검증 증거는 승인된 계획의 작업 기록과 연결한다.

조사표는 감사 증거이며 새로운 런타임 규범 원본이 아니다.

### D5. 새 정책 결정의 승인 경계

전수 조사에서 발견되는 모든 문제의 해결책이 미리 승인된 것으로 취급되지는 않는다.

이미 확정된 정책의 표현 정합화와 의미를 보존하는 정리는 진행할 수 있다. 역할 권한, 승인 순서, 중단 조건, 작업 수락 기준 등 새로운 행동을 결정해야 하는 발견은 해당 항목을 보류하고 Orchestrator가 결정을 확보한다. 승인된 설계의 의미가 달라지면 명세를 갱신하고 필요한 승인을 다시 받는다.

F08은 사용자 선택으로 해결 방향이 확정되었다. 두 런타임에서 Orchestrator만 수락 후 집중 커밋을 소유·실행하며, Claude Coder는 명시적 위임을 받아도 커밋하지 않는다. 이 결정의 구현은 수정 명세와 개정 계획 승인 후 진행한다.

### 4.2 분류

| 분류 | 의미 |
|---|---|
| 공통 기준 규칙 | 양 플랫폼에서 같은 의미를 요구해야 하는 정책 |
| 의도된 플랫폼 어댑터 | 실제 도구·환경·지원 기능 차이에 필요한 변형 |
| 역할별 안전장치 | 해당 역할의 독립적인 실행 문맥에서 직접 필요한 지침 |
| 중복·의미 편차 | 반복되거나 표현 차이로 요구 강도가 달라지는 규칙 |
| 모순 | 같은 조건에서 동시에 준수할 수 없는 요구 |
| 오래됨·제거 가능 | 현재 적용 경로와 유지 목적이 없다는 근거가 있는 항목 |
| 미확인 | 판단 근거가 부족하거나 승인된 조사 경계로 확인할 수 없는 항목 |

여러 분류가 동시에 적용될 수 있다. 예를 들어 반복된 보존 규칙은 중복이면서 필요한 역할별 안전장치일 수 있다.

### 4.3 권위와 원본 관계

규칙마다 공통 정책을 설명하는 위치, 절차를 구체화하는 위치, 역할별로 직접 전달하는 위치를 식별한다. 핵심 `SKILL.md`, 일반 references, 역할 프로필, 생성 전역 지침의 관련 위치를 부록에 연결한다.

이는 파일 간 새로운 우선순위를 암묵적으로 도입하는 작업이 아니다. 실제 요구가 충돌하면 어느 문서가 더 길거나 먼저 등장하는지를 근거로 해결하지 않는다. 승인된 정책 결정에 따라 관련 위치를 함께 정리한다.

### 4.4 제거 기준

삭제·축약·링크 대체에는 다음 근거가 필요하다.

- 삭제 대상의 요구와 예외를 식별했다.
- 필요한 정책이 남아 있는 위치를 지정했다.
- 해당 역할이 필요한 시점에 그 정책을 읽는 경로를 설명할 수 있다.
- 플랫폼별 기능 차이나 실패 대응이 사라지지 않는다.
- 관련 계약과 전달 경로를 확인할 수 있다.

근거가 부족하면 유지하거나 명시적으로 보류한다. 반복량만을 근거로 제거하지 않는다. S0 결과에 따라 이번 수정 초안에서 새로 승인 대상으로 제안하는 문서·역할별 보호 지침 삭제는 없다.

F08의 위임 예외 제거는 단순 중복 삭제가 아니라 사용자가 선택한 권한 정책의 정합화로 구분한다.

## 5. 발견과 처리 상태

### F01. 작성 책임 예외 충돌

두 플랫폼의 핵심 `SKILL.md`는 Planner 전담을 요구하지만 일반 `planning.md`는 사용자가 작성 책임을 변경할 수 있다고 표현한다.

- 근거:
  - `codex/skill/SKILL.md:10-13`
  - `claude/skill/SKILL.md:10-13`
  - `codex/skill/references/planning.md:72-76`
  - `claude/skill/references/planning.md:58-60`
- 결정: 기존 승인대로 D1을 유지하고 충돌하는 예외를 제거하거나 범위를 명확히 한다.
- 수락: 범위 내 지침에서 Orchestrator나 다른 역할이 Planner 전담을 우회해 초안을 작성하도록 허용하는 요구가 남지 않는다.
- 보호: 언어·경로·작업 범위 등의 사용자 선호와 작성 역할 변경을 혼동하지 않는다.
- 상태: 의미 확인 완료, 승인된 구현·검증 대기.

### F02. 커밋 시점의 의미 편차

Codex는 수락 후 다음 행동으로 커밋 준비·커밋을 요구하고 Claude는 “promptly”로 표현한다.

- 근거:
  - `codex/skill/references/commit.md:8-17`
  - `claude/skill/references/commit.md:3-9`
- 결정: 기존 승인대로 양 플랫폼에서 Orchestrator의 작업 수락 뒤 다음 행동이 필요한 커밋 준비·커밋이 되도록 정합화한다.
- 수락: 수락 전 커밋이나 수락 후 무관한 후속 작업을 먼저 요구하지 않는다.
- 보호: 필요한 Git 확인·실패 대응·중단 조건을 유지한다.
- 상태: 의미 확인 완료, 구현·검증 대기.

### F04. 반복된 역할별 보호 지침

반복 계열 전체를 검토했으며 제거 가능한 문서나 역할별 안전장치는 입증되지 않았다.

| 반복 계열 | 유지 근거 |
|---|---|
| 역할·권한·위임 | 각 역할이 직접 읽는 프로필에서 담당 범위와 금지 행동을 알아야 함. F08에 해당하는 권한 문구는 사용자 결정에 따라 정합화 |
| 보존·중단·보고 | 핵심 문서를 다시 읽지 않는 역할도 무관한 변경과 실패 상태를 보호해야 함 |
| 인계·승인 | trusted handoff와 실제 충돌 보고를 역할 문맥에서 직접 확인해야 함 |
| TDD | 범위 내 ARC 지침의 역할별 요구를 유지. 제외된 superpowers 내용과의 비교는 수행하지 않음 |
| QA·Reviewer 독립성 | 검사·검토·편집·수락의 경계를 각 역할에 직접 전달해야 함 |
| 증거·수락 | 완료 보고·검사 통과·Orchestrator 수락을 혼동하지 않도록 직접 지침 필요 |
| limits | 역할과 native 실행 환경의 한도·예약 경계를 유지해야 함 |

삭제·링크 대체에 필요한 도달 가능성과 대체 증거가 없으므로 유지한다.

상태는 **중복 검토 완료·보호 지침 유지**이다. 향후 삭제 제안이 생기면 D3과 4.4의 근거를 다시 제시해야 한다.

### F05. 관련 계약 검증의 확인 필요

S0는 테스트 내용을 읽거나 검사를 실행하지 않았다. 따라서 현재 테스트가 F01·F02의 상충 요구를 검출하는지, 의도된 플랫폼 차이를 보존하는지에 대한 coverage는 미검증이다.

- 결정: 승인된 계획과 필요한 개정에 따라 관련 정책의 적용 조건·상충 조합을 집중 검증한다.
- 수락: F01·F02의 재발과 F08의 위임 예외 재도입을 검출하는 검사 및 관련 회귀 증거가 있다.
- 한계: 검사 인터페이스나 경로의 존재 확인은 실제 coverage·통과의 증거가 아니다.
- 상태: 지원 검사에 의한 검증 대기. 테스트 전체 감사는 수행하지 않는다.

### F06. 생성 전역 지침 정합성

`lib/installer/global-config.mjs:41-42`의 생성 지침 텍스트와 조건을 검토했다.

- Orchestrator direct-path 요약

현재 근거로 생성 지침 텍스트 변경을 요구하지 않는다. 실제 `languagePolicy()` 번역 출력은 조사 범위 밖으로 미검증이다.

상태는 **범위 내 텍스트·조건 검토 완료·유지**, 실제 번역·설치·런타임 동작은 미검증이다.

## 6. 구현 경계와 호환성

지침의 경로·역할 식별자·지원 플랫폼 구조를 유지한다. 플랫폼별 도구 사용법과 지원하지 않는 기능을 동일하게 만들지 않는다.

생성 전역 지침을 변경해야 한다면 `lib/installer/global-config.mjs`의 관련 지침 텍스트와 이를 전달·검증하는 최소 범위만 변경한다. 일반적인 installer 리팩터링은 수행하지 않는다. S0 결과만으로는 G01 변경이 요구되지 않는다.

배포 지침 변경에 필요한 manifest 갱신은 허용한다. manifest 보호 기능이나 기존 이관 기록은 제거하지 않는다.

새 공통 생성기, 별도 런타임 규칙 엔진, 새 감사 도구 도입은 기본안에 포함하지 않는다. 필요성이 생기면 비용·범위·호환성 영향을 Orchestrator에 전달한다.

F07·F10은 현행 어댑터·보호를 유지하고 추가 변경을 보류한다. F09·F11은 사용자 조사 범위의 한계에 따라 미검증·보류한다. F08은 사용자 결정에 따라 수정하되, 관련 문서 승인과 구현 검증을 생략하지 않는다.

## 8. 검증 요구

승인된 계획과 필요한 개정의 검사 명령·기대 결과를 따른다. 이 수정 명세는 새로운 테스트 실행 결과를 주장하지 않는다.

- 변경 전 관련 검사의 baseline을 확보한다.
- F01에는 전담 규칙과 상충 예외의 조합을 확인하는 검증을 둔다.
- F02에는 수락과 커밋의 순서를 확인하는 검증을 둔다.
- F08에는 양 플랫폼의 Orchestrator 전담과 Claude Coder 위임 예외 제거를 확인하는 검증을 둔다.
- F02·F08의 올바른 요구와 상충하는 위임 문구가 공존하는 경우도 검출한다.
- 수정한 역할별 보호 지침과 플랫폼 차이에 필요한 집중 검사를 수행한다.
- 변경한 payload·생성 지침의 전달과 무결성을 확인한다.
- 기존 실패가 있으면 baseline과 새 실패를 분리하여 보고한다. 실패한 검사를 통과로 표현하지 않는다.
- 각 최상위 작업은 필수 검사와 발견사항을 Orchestrator가 확인하여 수락한다.
- 모든 작업 수락 후 최종 전체 변경에 대한 독립 Reviewer 검토를 한 번 수행한다.

Reviewer를 각 작업의 필수 검사로 반복 지정하지 않는다. 최종 전체 검증과 개별 작업 수락 요건은 계획에서 범위·시점을 구분한다.

기존 Claude BL1·BL2의 baseline disposition 등 이미 승인된 검사 조건은 계획 개정에서도 유지한다. F08을 이유로 관련 없는 테스트나 프로필 요구를 수정하지 않는다.

## 9. 보류 및 변경 조건

다음 상황에서는 관련 변경을 보류하고 Orchestrator에 전달한다.

- 선택된 경로·branch·기준 상태가 인계 기록과 맞지 않는다.
- 필요한 경로가 누락되거나 읽을 수 없다.
- 판단에 제외된 문서의 내용 검토가 필요하다.
- 새 역할 권한, 승인 절차, 중단 조건 등 미승인 정책 결정이 필요하다.
- 반복 삭제가 역할별 보호를 유지하는지 설명할 수 없다.
- 실제 플랫폼 제약과 공통 정책 편차를 구분할 수 없다.
- 필요한 변경이 supporting code의 일반 재설계로 확대된다.
- 관련 필수 검사가 실패하거나 필수 증거를 확보할 수 없다.
- 수정 명세 또는 F08을 반영한 개정 계획의 승인이 없다.

서로 독립적으로 진행 가능한 승인된 항목은 계속할 수 있다. 보류된 항목을 누락하거나 암묵적으로 완료 처리하지 않는다. 현재 단계에서는 수정 명세와 개정 계획 승인 전 Coder를 시작하지 않는다.
