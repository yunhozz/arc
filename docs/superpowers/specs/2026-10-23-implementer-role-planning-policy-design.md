# Implementer 역할 전환 및 계획 운영 정책 보완 설계

문서 상태: written spec 초안. 초기 설계 방향은 승인되었으며, 이 문서의 개별 승인 후 구현 plan을 작성한다.

## 1. 목적과 대상

ARC의 다음 네 항목을 개선한다.

1. plan 실행 중 문서가 변경되면 안전 조건 아래 최초 계획 문서 커밋에 반영한다.
2. Orchestrator가 Planner에게 필요한 근거를 처음부터 전달하고 보완 요청을 통합한다.
3. Coder의 정식 이름을 Implementer로 바꾸면서 기존 설정과 설치 데이터를 호환한다.
4. `lib/installer/plan.mjs`의 내부 책임을 분리하고 관찰 가능한 동작을 보존한다.

준비된 실행 대상은 다음과 같다. 상태는 Orchestrator가 제공한 준비·검증 근거를 사용한다.

| 항목 | 대상 |
|---|---|
| workspace | `/Users/ma-24-007/Desktop/workspace/arc` |
| branch | `chore/implementer-planning-policy` |
| HEAD | `d9044d52a9de2925c932c6ab6dc1e2de47e02ac4` |
| 변경 상태 | branch 생성 후 tracked/untracked clean 확인, 구현 변경 없음 |
| handoff 기록 | `/Users/ma-24-007/Desktop/workspace/arc/.git/arc/handoff/2026-10-23-implementer-role-planning-policy.md` |
| spec 저장 경로 | `/Users/ma-24-007/Desktop/workspace/arc/docs/superpowers/specs/2026-10-23-implementer-role-planning-policy-design.md` |
| 후속 plan 경로 | `/Users/ma-24-007/Desktop/workspace/arc/docs/superpowers/plans/2026-10-23-implementer-role-planning-policy.md` |

전체 변경은 역할 식별자·설정·runtime·설치 계약에 걸치므로 architectural 경로를 사용한다. installer 리팩토링 자체의 범위는 bounded로 제한한다.

## 2. 범위와 유지할 경계

정책 원본, 현재 운영 지침, 역할 프로필, 모델 설정 처리, runtime 역할 판단, 설치·upgrade, 생성물과 관련 검증을 변경한다.

다음은 범위에서 제외한다.

- 역할 권한 확대와 승인·QA·Reviewer 관문 축소.
- 게시·공유 이력의 자동 재작성과 강제 push.
- plan 문서 amend 예외를 구현 파일 수정에 적용하는 것.
- 외부 플랫폼이 정의하는 역할·API 이름 변경.
- 과거 실행 기록·승인 증거·역사적 spec/plan의 일괄 이름 치환.
- runtime 버전·정책 해시가 다른 기존 workflow의 무조건 재개와 포괄적 상태 migration.
- installer의 공개 API·출력·실패 의미 변경.

문서 정책 변경을 검증하기 위한 새로운 실행 강제 인프라는 추가하지 않는다. 구조 검증과 실제 에이전트 실행 준수 증거를 구분한다.

## 3. 실행 중 plan 문서 갱신과 최초 커밋 수정

### 3.1 적용 원칙

승인된 plan의 task 실행 중 해당 plan 문서를 갱신하면, 안전 조건을 만족하는 시점에 **최초 계획 문서 커밋을 수정한다. 별도의 계획 문서 커밋이나 fixup 커밋은 만들지 않는다.**

이 원칙은 다음 두 경우에 모두 적용한다.

1. 승인 내용의 의미를 바꾸지 않는 기계적 실행 기록.
2. 범위·방법·위험 등이 변경되어 수정된 plan 버전을 승인받은 경우.

문서의 승인과 Git 이력 반영은 별개의 절차다. 최초 커밋을 수정하더라도 실제 승인 시점은 달라지지 않는다. 수정된 plan은 승인 시점 이후의 작업에만 적용되며, 이전에 착수한 작업을 소급 승인하지 않는다.

구현 task는 기존 focused commit 규칙을 유지한다.

### 3.2 승인 여부에 따른 두 처리 경로

**기계적 실행 기록은 새 사용자 승인 없이 반영한다.**

체크박스 완료, task 완료 상태, 실제 결과, 이미 수행한 검증의 결과·증거 링크처럼 승인된 목표·요구·실행 계약을 바꾸지 않는 표기가 이에 해당한다. Orchestrator는 변경 내용과 시점을 handoff 기록에 남기고 안전한 시점에 최초 문서 커밋에 반영한다.

다음은 기계적 기록으로 취급하지 않는다.

- 검증을 수행하지 않고 완료로 표시하는 것.
- 실패를 성공으로 바꾸거나 근거 없이 인수를 기록하는 것.
- task 완료 표시와 함께 범위·기준·의존성을 변경하는 것.
- 요구된 검증이나 QA·Reviewer 관문을 제거하는 것.

**목표·task 범위 또는 경계·인수 기준·방법·위험·의존성·필수 검증이 달라지면 수정된 plan 버전을 승인받는다.**

영향받는 작업을 보류하고 필요한 설계·spec·plan의 변경과 승인을 순서대로 완료한다. 새 범위에 필요한 대상·소유권·검증·handoff 준비를 마친 뒤 해당 버전에 의존하는 작업을 진행한다.

이 경우에도 plan 문서 변경은 최초 문서 커밋에 반영한다. 새 범위라는 이유로 두 번째 계획 문서 커밋을 만들지 않는다.

오탈자·경로·명령·설명 정정은 의미상 영향을 판정한다. 기계적 실행 기록 외 승인된 문서 본문을 바꾸는 수정은 기존 문서 버전 승인 규칙을 적용하며, 위 계약 항목에 영향을 주면 반드시 수정된 plan 버전 승인과 관련 준비를 완료한다.

### 3.3 실제 승인 연혁 보존

최초 커밋의 내용만으로 승인 순서를 판단하지 않는다. canonical handoff 기록에 다음을 보존한다.

- plan의 절대 경로와 Git 경로.
- 각 변경 전후 문서의 content hash와 버전 식별자.
- 이전 승인 버전과 수정 버전의 관계.
- 수정 이유와 기계적 실행 기록 또는 승인 필요 변경의 분류.
- 수정 버전의 승인 참조와 실제 승인 시점.
- 기계적 기록이면 신규 승인이 불필요한 이유와 기록 시점.
- 영향받는 task, 보류·준비·재개 시점과 관련 근거.
- 최초 문서 커밋, 현재 대체 커밋, 각 재작성의 이전→이후 SHA 대응.
- 후속 구현 커밋의 SHA 대응과 재검증 결과.

수정 전후 버전은 hash만 남기는 데 그치지 않고 필요 시 내용을 확인할 수 있는 근거를 함께 보존한다. 과거 승인 참조나 승인 당시 내용을 최신 버전으로 덮어쓰지 않는다.

문서 이력이 다시 쓰였어도 특정 작업 당시 어느 버전이 승인되어 있었는지 확인할 수 있어야 한다. 재작성된 최초 커밋이 최신 plan을 포함한다는 사실은 그 내용이 최초부터 승인되어 있었다는 증거가 아니다.

### 3.4 독립 문서 커밋 없는 반영

Orchestrator는 필요한 승인·준비와 기록을 완료한 뒤 안전한 Git 변경 경계에서 처리한다.

- 최초 문서 커밋이 HEAD이면 해당 plan 내용만 amend한다.
- 뒤에 task 커밋이 있으면 허용된 로컬 선형 구간에서 최초 문서 커밋을 수정하고 후속 커밋을 원래 순서와 task 경계를 유지하여 재적용한다.
- 재작성 전 HEAD와 원래 커밋들을 복구할 수 있는 로컬 근거를 확보한다.
- 문서 수정용 독립 커밋이나 중간 fixup 커밋을 만들지 않는다.
- 구현 task를 합치거나 구현 변경을 문서 커밋에 편입하지 않는다.

최초 커밋이 여러 문서를 포함해도 이번 변경 대상은 갱신 대상으로 확인한 plan 경로로 제한한다. spec 등 다른 문서 수정에는 해당 문서의 별도 승인·반영 규칙을 적용한다.

재작성은 Git 객체와 SHA를 바꿀 수 있다. “독립 문서 커밋 없음”은 “SHA 불변”을 의미하지 않는다. Git 변경은 Orchestrator만 수행한다.

### 3.5 안전 조건과 중단

다음 조건을 모두 확인한다.

- 최초 문서 커밋이 현재 HEAD의 조상이다.
- 재작성 구간이 미게시·미공유 로컬 선형 이력이다.
- 구간에 merge commit이 없다.
- 관련 변경의 소유권과 포함 범위가 명확하다.
- 다른 역할의 쓰기가 중지되고 미완료 변경이 안전하게 정리된 경계다.
- 문서의 승인·분류·연혁 기록이 완전하다.
- 후속 커밋을 충돌 없이 재적용할 수 있다.

이력이 게시·공유되었거나 그 여부가 불명확한 경우, merge 이력, 관련 없는 변경의 불명확한 소유권, 예상하지 않은 HEAD·dirty 상태, 재적용 충돌이 있으면 재작성과 관련 의존 작업을 중단한다.

충돌을 자동 해결하거나 강제 push하지 않는다. 별도 계획 문서 커밋으로 자동 대체하지 않는다. Orchestrator가 관찰 상태와 필요한 해결을 기록하고 해결한 뒤 관련 gate를 갱신한다.

안전 조건을 만족하지 못하면 “새 커밋을 만들지 않는다”는 요구를 우회하여 완료한 것으로 보고하지 않는다.

### 3.6 반영 후 검증과 정책 정합성

새 HEAD, plan 내용·승인 버전, SHA 대응, 후속 구현 내용·task 경계 보존, 남은 변경 상태를 확인한다.

SHA 변경만으로 기존 인수 결과를 무조건 폐기하지 않는다. 증거가 특정 HEAD·문서·정책 내용에 묶여 있으면 새 상태에 연결 가능한지 확인한다. 연결할 수 없거나 의미상 영향을 받은 검증은 다시 수행한다. 기존 runtime 증거 무효화 규칙은 유지한다.

`planning`, `handoff-prep`, `commit`, `verification` 지침과 정책 생성 표면을 일치시킨다. 기존의 “새 범위를 과거 커밋에 소급 편입하지 않는다”는 문구는 다음 두 원칙을 함께 표현하도록 보완한다.

- 수정된 plan의 내용은 필요한 승인 후 최초 문서 커밋에 반영한다.
- 실제 승인 시점 이전의 작업을 정당화하거나 승인 연혁을 변경하지 않는다.

구현 수정의 focused commit, 역할 권한, QA·Reviewer와 테스트 실행 규칙에는 예외를 추가하지 않는다.

## 4. Planner 입력과 보완 계약

### 4.1 최초 전달 전 준비

Orchestrator는 formal drafting 전에 다음 정보를 완성한다.

- 사용자 요구의 원문·기준 ID, 목표·제외 범위, 승인된 결정과 미결정.
- 실제 workspace·branch/HEAD·변경·소유권, 실행 대상 선택과 준비 근거.
- 이번 단계 문서의 절대 경로, 선행 승인 문서의 버전·경로.
- 현재 동작과 정책·source·generated·runtime·installer·문서의 연결 관계.
- 충돌하는 규칙과 해결 방향, 공유 계약·의존성.
- 설계 깊이와 plan 깊이 판단, 검증 위험과 필요한 증거.
- 인수 기준, 보류 조건, 이번 호출의 정확한 산출물.

공유 brief의 기존 고정 필드 순서를 유지한다. 전체 대화·원시 로그 대신 접근 가능한 경로와 필요한 범위를 제공한다.

대상 준비나 필수 결정이 빠졌다면 formal drafting 전에 해결하거나 해당 단계를 보류한다. 초기 설계 제안은 기존 규칙대로 대상 선택 전에 가능하다.

### 4.2 단계별 산출물과 통합 보완

Planner는 현재 단계의 완전한 비례적 초안과 자가 검토를 반환한다. Orchestrator는 다음을 함께 확인한다.

- 범위·근거와 경로·소유권.
- 정책 충돌과 공유 계약.
- 의존성·인수 기준·검증·보류 조건.
- 역할·승인·커밋 경계.
- 초안의 완결성.

누락과 보완 사항은 하나의 통합 요청으로 전달한다. 이미 전달한 brief를 기준으로 변경 필드만 보내고 나머지는 `unchanged`로 표시한다. 해결된 질문을 위해 추가 호출하지 않는다.

고정 호출 상한을 두거나 미완성 문서를 수용하지 않는다. 실질적 누락·사용자 수정·새 증거는 추가 호출 사유다.

순서는 다음과 같이 유지한다.

**초기 설계 승인 → spec 작성·저장·검토·개별 승인 → plan 작성·저장·검토·개별 승인**

spec 승인 전에 종속 plan을 작성하지 않는다. 문서 저장은 승인이나 커밋이 아니다. 최초 계획 문서 커밋은 필요한 문서 세트의 승인 완료 후 기존 절차로 만든다. 실행 중 plan 갱신에는 제3절을 적용한다.

## 5. Implementer 정식 명칭과 호환

### 5.1 정식 이름

| 사용처 | 정식 표현 |
|---|---|
| 역할명 | `Implementer` |
| runtime 의미 역할 | `implementer` |
| 모델·플랫폼 역할 키 | `arc_implementer` |
| Codex 프로필 | `arc-implementer.toml` |
| Claude 프로필 | `arc-implementer.md` |
| 역할 기반 task 이름 예시 | `implementer_<short_task>` |

권한은 기존 Coder와 같다. 이름 변경으로 Git·외부 작업·승인 권한을 얻지 않는다.

새 모델 역할 목록과 출력은 정식 키를 사용한다. legacy 이름은 호환 입력·migration 처리·호환 테스트·역사 기록에 남을 수 있다.

### 5.2 기존 모델 설정

`lib/models/config.mjs`의 strict 검증 전에 legacy 키 `arc_coder`를 `arc_implementer`로 정규화한다. 파일 입력과 직접 전달되는 설정 객체, preset 해석·검증·직렬화에 같은 계약을 적용한다.

- legacy 키만 있으면 모든 preset의 model·effort 값을 보존한다.
- 새 키만 있으면 그대로 사용한다.
- 두 키가 있고 검증된 의미 값이 같으면 정식 키 하나로 합친다.
- 값이 다르면 쓰기 전에 충돌을 보고한다. 임의 우선순위를 적용하지 않는다.
- 다른 알 수 없는 키와 잘못된 구조·값·platform·version은 계속 거부한다.
- 읽기·preview가 원본 설정 파일을 자동 수정하지 않는다.
- 승인된 설정 저장·설치·upgrade는 `arc_implementer`만 직렬화한다.

다른 역할 설정, 선택한 preset, 언어·limits 설정을 보존한다.

### 5.3 기존 설치와 upgrade

새 이름만 찾으면 기존 설치를 불완전 설치로 오판할 수 있으므로, 기존 `arc-coder.*`를 정상 upgrade 입력으로 인식한다.

old/new 프로필의 존재 상태를 snapshot과 변경 감지에 포함한다. 기존 설정을 정규화하여 새 프로필을 생성하고, 성공한 upgrade 결과에서 동일 역할이 두 이름으로 남지 않도록 한다.

사용자 변경을 조용히 삭제하거나 덮어쓰지 않는다. 기존 지원 범위에서 해석 가능한 model 설정은 보존한다. 그 밖의 변경에는 기존 installer의 보존·복구 계약을 적용하며, 안전한 이전을 입증할 수 없으면 쓰기 전에 중단한다. old/new 프로필이 함께 있고 의도가 불명확하면 자동 선택하지 않는다.

프로필 생성, legacy 프로필 정리, 설정·manifest 반영은 기존 transaction의 원자성·snapshot·복구 보장을 유지한다. 실패 시 이전 데이터가 보존되어야 한다.

새 설치와 정상 upgrade의 활성 프로필 목록은 정식 이름만 제공한다.

### 5.4 runtime 입력과 저장 상태

기존 actor·identity·assignment·cooperative 입력의 `coder`를 `implementer`와 동일한 역할 의미로 해석한다.

- 역할 비교·assignment·검증·정책 평가에 같은 정규화 규칙을 사용한다.
- 신규 identity·assignment 등 새 역할 값은 `implementer`로 생성한다.
- legacy 허용을 다른 알 수 없는 역할의 허용으로 확장하지 않는다.
- 중복·모호한 identity와 assignment 제약은 유지한다.

기존 승인·audit·request·해시 근거는 이름 치환으로 수정하지 않는다. 저장된 역사적 원문을 보존하면서 역할 의미를 해석한다. 원본 검증과 의미 정규화의 순서를 명확히 하여 fingerprint·replay·provenance 검증을 보존한다.

이 호환은 진행 중 workflow의 무조건 재개를 보장하지 않는다. 정책·runtime 버전 또는 hash가 맞지 않으면 기존 reconciliation·증거 갱신·보류 규칙을 적용한다. 이름 호환을 이유로 해당 검증을 끄거나 과거 승인·인수를 자동 승계하지 않는다.

기존 workflow 전체의 자동 변환·재개는 범위 밖이다.

### 5.5 반영 표면

정책 원본은 `lib/policy/role-policy.json`이다. `lib/policy/render.mjs`와 `scripts/update-role-policy.mjs`의 생성 대상·출력을 새 이름과 맞춘다.

다음을 포함한다.

- `codex/agents/`, `claude/agents/`의 프로필 파일명·내용·참조.
- 현재 운영 skill·reference의 역할 설명·routing·handoff 예시.
- `lib/models/config.mjs`, `lib/models/profiles.mjs`와 모델 입력·출력.
- `lib/runtime/operations.mjs`, `schema.mjs`, `cooperative-schema.mjs`, `assignment.mjs`, `evaluate.mjs`, `verification.mjs`와 관련 역할 소비 코드.
- `lib/installer/targets.mjs`, `upgrade-state.mjs`, 설치 계획·manifest·payload 처리.
- `scripts/update-runtime-assets.mjs`의 runtime 복제본.
- fixture·테스트·parity·manifest 기대값.

generator가 관리하지 않는 파일명·일반 문구도 확인한다. 역사 문서는 현재 운영 입력 계약으로 사용되는 경우에만 별도 판단하며 기본적으로 수정하지 않는다.

## 6. `lib/installer/plan.mjs` 리팩토링 계약

`buildInstallPlan`, `previewLimits`, `previewLanguage`, `validatePlanSet`의 공개 계약을 유지한다. 새로운 공개 API나 외부 의존성을 추가하지 않는다.

`buildInstallPlan`의 다음 책임을 이름 있는 내부 단위로 분리할 수 있다.

- 모델·프로필 생성과 언어·Claude hook 반영.
- skill payload와 설정 구성.
- 대상·프로필 경로 관찰과 snapshot 구성.
- native 설정 병합과 요약 생성.
- 최종 plan 조립과 검증.

구체적 함수·파일 분할은 구현 plan에서 정한다. 필요 이상의 모듈화나 installer 전체 재설계는 하지 않는다.

다음 불변 조건을 보존한다.

- 함수 인수·반환 구조·기본값·선택지.
- `Buffer` 내용, 생성 파일 내용, Map 순서.
- snapshot 키·메타데이터와 변경 감지 시점.
- native merge 결과와 summary 내용·순서.
- 경로 충돌·symlink·descriptor 기반 안전 검사.
- 오류 종류·메시지·발생 순서와 쓰기 전 실패 의미.
- `skipGlobal`, preview 재사용, concurrency drift, 모델·언어·limits 검증.
- preview에서 설치 대상에 쓰지 않는 동작.

역할명 변경에 필요한 출력 차이는 역할 전환의 승인된 변경으로 검증한다. 리팩토링은 그 결과를 기준으로 추가 차이를 만들지 않는다.

## 7. 의존성과 적용 순서의 제약

다음은 후속 plan이 지켜야 할 관계이며 구현 task 분할은 아니다.

- written-spec 승인이 종속 plan 작성보다 먼저다.
- 정식 역할명과 legacy 정규화 계약이 프로필·runtime·설치의 공통 기준이다.
- 기존 설치 인식이 legacy 프로필 정리보다 먼저 성립해야 한다.
- 정책·runtime 생성물은 source와 일치해야 한다.
- 역할 변경으로 승인된 installer 결과를 기준으로 리팩토링의 동작 보존을 확인한다.
- 실행 중 plan 갱신은 승인 분류·실제 연혁·이력 안전 조건을 함께 충족해야 한다.

후속 plan은 독립 검증할 수 없는 변경을 같은 task에 배치하고, task마다 범위·대상 파일·의존성·인수 기준·필수 검증·보류 조건을 명시한다.

## 8. 인수 기준과 필요한 증거

| ID | 인수 기준 | 필요한 증거 |
|---|---|---|
| AC-01 | 기계적 실행 기록은 신규 사용자 승인 없이 기록·amend하며 승인 내용 변경과 구분한다 | 운영 지침·정책의 교차 검토와 해당 사례 검증 |
| AC-02 | 목표·task 범위·경계·기준·방법·위험·의존성·검증 변경은 수정 버전 승인 후 영향 작업을 진행한다 | 변경 분류·승인·준비·재개 순서의 규칙 검증 |
| AC-03 | 두 경우 모두 안전 조건 아래 최초 문서 커밋을 수정하고 별도 문서 커밋을 만들지 않는다 | HEAD·후속 task 존재 사례와 보류 사례 검증 |
| AC-04 | 이력 재작성 후에도 이전·이후 내용 hash, 버전, 승인 참조·시점, SHA 대응으로 실제 연혁을 확인할 수 있다 | handoff 기록 계약과 관련 증거 확인 |
| AC-05 | 공유·불명 이력, merge, 불명 소유권, 충돌에서 중단하며 승인 소급·강제 push·자동 대체 커밋을 허용하지 않는다 | 정상·거부 경로 검증 |
| AC-06 | Planner 최초 brief와 통합 보완을 강화하고 단계별 승인·추가 보완 가능성을 유지한다 | profile·planning·coordination 간 일치 |
| AC-07 | 새 정식 역할·프로필·설정·runtime 출력이 Implementer로 일치한다 | role-policy·profile·model·runtime·설치 검증 |
| AC-08 | 기존 모델 값 보존과 이중 키 충돌 거부가 두 플랫폼에서 일관된다 | legacy/new/동일 이중 키/충돌 입력 검증 |
| AC-09 | 기존 설치를 인식하고 사용자 데이터를 보존하며 정식 프로필로 전환한다 | legacy 설치·upgrade·충돌·실패·복구 검증 |
| AC-10 | legacy runtime 역할의 의미를 호환하고 승인·해시·replay·권한 제약을 보존한다 | provider/cooperative 입력·상태·거부 사례 |
| AC-11 | 리팩토링이 승인된 역할 변경 외 동작 차이를 만들지 않는다 | installer 성공·실패·preview·native merge·snapshot 회귀 결과 |
| AC-12 | 생성물·복제본·manifest·parity가 일치하고 역사 기록을 불필요하게 수정하지 않는다 | 생성 결과 차이와 관련 검증 |

기존 검증 표면은 `tests/node/role-policy.test.mjs`, `profile-render.test.mjs`, `models.test.mjs`, `plan.test.mjs`, `legacy-parity.test.mjs`, `manifest.test.mjs`를 포함한다. 정확한 runtime·upgrade 검증 범위는 후속 plan에서 기존 구조에 맞춰 정한다.

각 task는 위험에 비례한 필수 확인과 필요한 fresh QA를 통과하고 Orchestrator 인수 후 focused commit으로 남긴다. 전체 task 인수와 필수 QA 완료 후 독립 Reviewer가 최종 전체 변경을 한 번 검토한다. 최종 finding은 Implementer → Reviewer 재확인으로 해결하며, 이 최종 단계에 QA를 다시 배정하지 않는다. 최초 최종 검토 전 필요한 QA와 실패 재검증은 유지한다.

문서·구조 검증은 정책의 명시 내용을 입증한다. 실제 승인 순서·amend·에이전트 호출 준수는 대응하는 실행 기록이 있을 때만 입증된 것으로 보고한다. 이번 문서 이력 예외는 테스트·QA·Reviewer 면제를 추가하지 않는다.

## 9. 공통 보류 조건

대상·HEAD·소유권 불일치, 누락된 승인, 예상하지 않은 변경, 설정·프로필 충돌, 사용자 데이터 보존 불가, 생성물 불일치, 검증 실패, 해시·승인 증거를 우회해야 하는 호환 구현이 발견되면 영향 작업을 보류한다.

Orchestrator가 관찰 상태·완료 부분·필요한 해결을 기록한다. 해결 후 관련 증거와 gate를 갱신한다.

실행 중 plan 갱신의 이력 안전 조건이 성립하지 않으면 독립 문서 커밋으로 우회하지 않는다. runtime 자동 migration과 공유 이력 재작성은 별도 범위 결정 없이 진행하지 않는다.

---

자가 검토 결과:

- **승인 불필요:** 체크박스·실제 결과·증거 링크·완료 상태 같은 기계적 실행 기록은 기록 후 안전한 시점에 amend한다.
- **수정 버전 승인 필요:** 목표·범위·task 경계·기준·방법·위험·의존성·필수 검증 변경은 승인·준비 완료 후 이후 작업에 적용한다.
- 두 경우 모두 최초 plan 문서 커밋을 수정하며, 별도 문서 커밋·fixup 커밋을 만들지 않는다.
- 새 plan 내용의 이력 반영과 승인 소급을 구분했다. handoff 기록으로 실제 내용·승인·작업·커밋 대응 연혁을 보존한다.
- 기존 “새 범위의 과거 커밋 편입 금지” 문구는 이번 요구와 충돌하므로 변경 대상으로 명시했다. 승인 소급 금지는 유지하면서, 승인된 수정 plan의 최초 커밋 반영을 허용하도록 보완한다.
- 나머지 역할 권한·focused 구현 커밋·QA·Reviewer·검증 규칙은 유지한다.
- 추가 사용자 결정이 필요한 미해결 충돌은 없다. 파일 저장·plan 작성·검증·Git 변경은 수행하지 않았다.
