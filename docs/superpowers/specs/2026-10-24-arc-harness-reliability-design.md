## 1. 목표와 문제

ARC 공통 하네스가 다음 세 가지 실패를 줄이도록 역할 계약과 인계·검증 요구사항을 보완한다.

1. 선택적인 읽기 방법의 실패를 필수 입력·권한·상태 실패와 동일하게 취급하여 작업 전체가 불필요하게 멈추는 문제.
2. 사용자 제공 지침과 저장소 지침 파일을 구분하지 못하여 적용 지침이 이미 있는데도 중단하는 문제.
3. 승인 시각자료가 구현·QA의 구체적인 비교 기준과 증거로 이어지지 않아 불일치를 놓치는 문제.

기존의 역할 권한, 승인 단계, Git 상태 보존, 실패·부분 완료 처리, QA와 Reviewer 의무, Orchestrator의 수용 책임은 유지한다. 복구는 승인 범위 안에서 이미 확인된 동일 자료를 읽는 방법에만 제한한다.

## 2. 관측 근거와 한계

조사 대상은 `local` host의 “설치 메뉴 UI/UX 개선” 대화와 그 하위 역할 대화다. 아래 내용은 Orchestrator가 대화별로 확인하여 제공한 증거이며, 이번 명세 작성에서 대화를 다시 조회하거나 재현하지 않았다.

| 관측 | 설계에 반영할 요구 |
|---|---|
| Planner가 이미지 처리 중 `ModuleNotFoundError: PIL`을 만난 뒤 중단 | 선택적 읽기 방법 실패와 필수 시각 입력의 부재를 구분하고, 권한 내에서 사전 허용된 동일 자료 읽기 대안을 명시 |
| 이미 읽은 `scripts/update-manifest.mjs`가 있는데 `scripts/lib/manifest.mjs`를 추정해 읽다가 실패한 뒤 문서 작성 중단 | 확인된 경로를 인계하고, 추측 경로를 복구 수단으로 사용하지 않으며, 해당 자료의 필요성을 구분 |
| Implementer/Coder가 저장소 루트의 `AGENTS.md` 부재로 중단 | 사용자 제공 적용 지침과 실제 파일 존재를 별도 사실로 전달 |
| 승인 mockup의 압축된 이중 윤곽형 ARC mark와 구현의 ASCII 대각선 형태가 달랐음 | 승인 원본에서 핵심 기준을 도출하고 실제 구현 산출물과 비교 |
| 구현 보고와 QA가 원본 대비 시각 일치를 충분한 비교 증거 없이 주장 | 항목별 `pass`·`mismatch`·`unverified`와 비교 근거를 의무화 |
| 실패 해소 후 재진입에서 완료 작업·승인·참조 맥락의 연속성이 필요 | canonical record와 재개 brief에 완료·미완료·무효화된 증거를 구분하여 전달 |

`PIL` 실패가 있었다는 사실만으로 해당 이미지 처리 작업 전체가 Planner에게 허용된 읽기 작업이었다고 판단하지 않는다. crop 등 파일을 만드는 작업은 Planner의 읽기 전용 권한을 넘는다. 도구 사용 가능성과 역할 권한은 별도로 판단해야 한다.

과거 UI 구현의 적합성을 다시 판정하거나 수정하는 것은 본 명세의 범위가 아니다. 해당 사례는 공통 하네스의 계약을 설계하는 근거다.

## 3. 범위와 승인된 결정

### 3.1 포함 범위

- 공통 실패 처리와 역할별 중단 문구의 제한적 읽기 복구 조건.
- 역할 brief의 적용 지침 출처와 필수 입력 상태.
- 승인 시각자료의 식별·접근·기준·구현 산출물·QA 비교 증거 연결.
- 실패 해소와 역할 재진입 시 기존 승인·완료 작업·유효 증거의 전달.
- Canonical policy, Codex·Claude 프로필과 reference, 생성물, 운영 문서, 검증·배포 표면 사이의 의미 일관성.
- 정적 검사와 실제 역할 실행·시각 비교 증거의 구분.

### 3.2 제외 범위

- 새 역할, 새 실행 환경, 범용 자동 복구 시스템 도입.
- 임의 경로 탐색, 환경·권한 변경, 의존성 설치를 통한 fallback.
- mutation 재시도나 부분 완료 상태의 자동 해소.
- 기존 승인·실행 대상 준비·Git·보존·수용·commit 흐름의 완화.
- 일반적인 visual skill 재설계 또는 Planner 사용 경험 전반의 개편.
- 과거 instruction audit 및 final review finding loop의 범위 재작성.
- 과거 UI의 mark 또는 메뉴 구현 수정.

### 3.3 선택한 접근

승인된 B안은 다음을 결합한다.

- 실패한 단계와 영향을 받는 의존 작업을 보류한다.
- brief에 사전 허용된 경우에만 동일하게 확인된 자료·승인 버전·목적을 유지하는 동등한 읽기 전용 방법을 사용한다. 다른 접근 locator가 필요하면 brief에 정확히 지정되어야 한다.
- 적용 지침의 출처를 명시한다.
- 승인 시각자료를 검증 가능한 기준과 실제 산출물 비교로 연결한다.

인계만 보강하는 접근은 선택적 방법 실패의 반복 중단을 충분히 줄이지 못한다. 별도 실행 검증기를 도입하는 접근은 상태·기록 수명과 배포 범위를 확대한다. 본 변경은 기존 계약과 표면을 보완하는 수준으로 제한한다.

## 4. 용어와 실패 분류

| 용어 | 의미 |
|---|---|
| 필수 입력 | 현재 승인 단계나 수용 기준을 충족하는 데 반드시 필요한 자료·지침·증거 |
| 선택적 읽기 방법 | 동일 입력을 관측하는 수단 중 하나로, 그 방법 자체는 필수 결과가 아닌 경우 |
| 확인된 동일 자료 | 출처와 정확한 경로가 brief에서 식별되고 현재 단계에 적용되는 자료 |
| 허용된 읽기 대안 | brief가 대상 자료·목적·방법·전제조건을 명시하여 사전 허용한 대안 |
| 의존 작업 | 실패한 입력·상태·결과의 유효성을 전제로 하는 후속 작업 |
| 시각 기준 | 승인 시각자료에서 도출하여 실제 산출물과 대조할 수 있는 개별 요구 |
| `pass` | 요구한 관측을 수행했고 해당 기준이 충족됨을 뒷받침하는 증거가 있음 |
| `mismatch` | 관측 결과 기준과 다른 점이 확인됨 |
| `unverified` | 필요한 관측이나 증거가 부족하여 충족 여부를 판단할 수 없음 |

실패는 다음과 같이 처리한다.

| 분류 | 예 | 처리 |
|---|---|---|
| 선택적·부작용 없는 읽기 방법 실패 | 동일 이미지의 허용된 열람 방법 하나가 사용 불가 | 제5절 조건을 모두 충족할 때만 사전 허용 대안 사용 |
| 필수 입력 누락·접근 불가 | 필수 승인 원본, 필요한 작업 파일, 필수 reference 부재 | 영향을 받는 작업 보류 후 Orchestrator 반환 |
| 대상·권한·소유권 문제 | 예상 밖 branch·HEAD, 권한 거부, 소유권 불명 | 현행 중단·보존 규칙 적용 |
| mutation 실패·부분 완료·상태 불확실 | 쓰기나 Git 작업의 완료 여부 불명 | 자동 재시도·fallback 금지, 실제 관측과 미확인 사항 반환 |
| 지침 출처의 혼동 | 사용자 지침은 전달됐으나 루트 `AGENTS.md` 없음 | 파일 부재와 적용 지침을 구분하여 판단 |
| 시각 비교 증거 부족 | 원본 또는 실제 출력 미관측 | 해당 기준 `unverified`, 시각 일치 주장 금지 |

오류 코드나 예외 이름 하나만으로 복구 가능 여부를 정하지 않는다. 선택적 읽기 실패와 다른 문제가 함께 있으면 더 제한적인 조건을 적용한다.

## 5. H1 — 제한된 읽기 복구 계약

### 5.1 복구 전제

역할은 다음 조건을 모두 확인할 수 있을 때만 허용된 읽기 대안을 사용할 수 있다.

1. 실패한 작업이 선택적인 읽기 방법이다.
2. 실패가 mutation이나 부분 완료를 포함하지 않고, 부작용 없는 읽기였다는 근거가 있다.
3. 입력 자료의 source·정확한 경로·목적이 이미 확인되어 있다.
4. 대안이 brief에 명시되어 있고 역할 권한과 승인 범위 안에 있다.
5. 대안이 같은 확인 자료·승인 버전·목적을 유지하며 필요한 관측을 동등하게 충족한다. 다른 접근 locator가 필요하면 brief가 정확히 지정한다.
6. 입력·권한·대상·소유권·현재 상태에 미해결 불확실성이 없다.

대안의 동등성은 같은 종류의 출력이 나온다는 이유만으로 성립하지 않는다. 예를 들어 이미지의 존재 확인은 시각적 내용 열람을 대신하지 못하고, 파일 일부 읽기는 필요한 전체 범위를 확인했다는 증거가 되지 않는다.

### 5.2 brief의 복구 정보

허용하려는 경우 brief에 다음을 명시한다.

- 입력 식별자와 정확한 source·경로.
- 읽기 목적과 필요한 관측 범위.
- 기본 방법과 허용 대안.
- 대안이 다른 접근 locator를 사용한다면 그 정확한 경로와 동일 자료·승인 버전을 확인하는 근거.
- 대안의 전제조건과 적용 가능한 실패 유형.
- 대안 사용 후 필요한 증거.
- 즉시 반환할 조건.

허용 대안이 없거나 명시가 모호하면 역할은 스스로 대안을 추가하지 않는다. 새 대안의 준비·배정은 Orchestrator가 기존 승인 범위와 역할 권한을 검토하여 처리한다.

### 5.3 실행·보고

실패한 단계를 보류한 후 허용 대안을 사용한다. 대안이 실패하면 다른 방법을 연쇄 탐색하거나 재시도하지 않고 Orchestrator에게 반환한다.

대안이 성공하면 실패 원인, 사용 방법, 동일 자료임을 확인한 근거, 확보한 관측, 남은 제한을 보고한다. 그 증거가 충족하는 의존 작업만 재개한다.

독립 작업은 실패한 입력·상태에 의존하지 않는다는 근거가 있을 때 계속할 수 있다. 안전한 분리가 불명확하면 보류한다.

### 5.4 금지 사항

복구 예외는 다음을 허용하지 않는다.

- 추측 경로, 유사 파일, 과거 버전 또는 전역 경로로 대체.
- 새 의존성 설치, 환경 설정 변경, 권한 확대, sandbox 우회.
- 파일 생성·변경·삭제 또는 Git 상태 변경.
- mutation 재시도, 불명확한 결과를 성공으로 추정.
- 역할 변경·재시작·다른 도구를 통한 권한 우회.
- 필수 입력의 부재를 선택적 방법 실패로 재분류.

동일 자료를 다른 위치에 준비해야 한다면 역할의 fallback으로 처리하지 않는다. Orchestrator가 별도 준비의 권한·경로·출처 연결을 확인하여 새 인계 사실로 제공해야 한다.

## 6. H2 — 적용 지침의 출처와 입력 상태

역할 brief는 필요한 지침을 자체 완결된 형태로 전달하면서 다음 출처를 구분한다.

| 출처 | 전달할 내용 |
|---|---|
| 사용자 제공 지침 | 메시지·대화 식별 근거, 필요한 원문 또는 정확한 발췌, 적용 범위 |
| 현재 작업공간의 지침 파일 | 실제 발견한 절대 경로, 읽은 범위, 적용 범위와 확인 상태 |
| 설치된 역할·skill·reference | 정확한 경로·section, 현재 단계의 필수 여부와 접근 상태 |
| 작업 입력 | 승인 문서·시각자료·소스 등 필요한 파일의 정확한 경로와 필수 여부 |

출처 기록은 지침의 우선순위를 새로 정의하지 않는다. 충돌은 기존 권한·지침 체계에 따라 Orchestrator에게 반환한다. 역할은 충돌하는 지침을 임의 병합하거나 편의상 선택하지 않는다.

현재 사례에서는 다음 사실을 함께 전달해야 한다.

- 사용자가 제공한 AGENTS coordination 지침이 적용된다.
- 저장소 루트에 `AGENTS.md` 파일은 없다.
- 두 사실은 양립하며, 해당 파일 부재만으로 “적용 지침 없음”이나 blocker로 판단하지 않는다.
- 실제 필수 작업 입력이나 필수 reference의 누락은 별도로 보류한다.

전체 부모 대화의 자동 상속을 전제로 하지 않는다. fresh 역할에는 필요한 출처·발췌·결정·접근 경로를 다시 전달한다. 존재 여부를 확인하지 않은 파일을 발견한 파일로 기록하지 않는다.

## 7. H3 — 승인 시각자료의 연속성과 비교 증거

### 7.1 시각자료 식별

승인 시각자료가 있는 작업의 brief·spec·plan은 필요한 범위에서 다음 정보를 유지한다.

- 자료 식별자, 정확한 접근 경로와 버전.
- 사용자 승인 근거와 승인 범위.
- 해당 단계와 역할에서의 접근 가능 여부.
- 자료에서 도출한 시각 기준 ID.
- 기준별 적용 대상과 비교 방법.
- 실제 산출물의 경로 또는 재현 가능한 관측 위치.
- 미결정 해석·제약·허용된 차이.

파일 이름이나 “mockup 반영”이라는 표현만으로 자료를 식별하지 않는다. 승인되지 않은 다른 버전으로 조용히 대체하지 않는다.

현재 회고의 승인 원본은 다음이다.

`/Users/yunho/.codex/visualizations/2026/10/23/01a1699c-8c88-76c2-8855-c86c4c89a914/arc-tui-ux-mockup-v3.png`

비교 첨부는 다음과 같다.

- `/var/folders/2x/zy_vqh9s35qczpl53nxq1sx40000gn/T/codex-clipboard-5b3759b5-3bf3-443a-80aa-5143bc4f4710.png`
- `/var/folders/2x/zy_vqh9s35qczpl53nxq1sx40000gn/T/codex-clipboard-cbb0d90d-2e5e-424a-b814-8b3b663ae06c.png`

임시 경로의 지속 접근 가능성은 향후 사용 단계에서 다시 확인해야 한다. 본 문서에 경로를 기재했다는 사실은 현재 역할의 열람 증거가 아니다.

### 7.2 시각 기준

기준은 원본의 핵심 형상·배치·위계·간격·색상 등 실제 승인 내용에서 도출한다. 정량 근거가 없는 수치나 허용 오차를 발명하지 않는다.

기준마다 다음을 기록한다.

- 고유 ID와 원본의 해당 영역.
- 관측할 속성.
- 충족 판단 방법과 필요한 환경 조건.
- 승인된 차이 또는 아직 해결되지 않은 해석.
- 구현·QA 증거.

과거 사례의 “압축된 이중 윤곽형 ARC mark”는 핵심 기준의 예다. 실제 윤곽·비례를 보지 않고 임의의 ASCII 형상을 동등하다고 정하지 않는다. 터미널 표현 제약으로 핵심 형상을 변경해야 한다면 승인 범위의 변경 여부를 Orchestrator에게 반환한다.

### 7.3 구현과 QA

Implementer는 기준별로 실제 산출물의 `pass`·`mismatch`·`unverified`와 근거를 보고한다. 이는 자체 구현 보고이며 인수 결정이 아니다.

Fresh QA는 승인 원본과 실제 구현 산출물을 직접 대조한다. Implementer의 보고나 소스 존재만으로 시각 기준을 통과시키지 않는다. QA 증거에는 다음이 필요하다.

- 원본과 실제 산출물의 식별·관측 위치.
- 실행 revision과 변경 상태에 대한 Orchestrator 제공 연결 근거.
- 터미널 크기·렌더링 환경 등 비교에 영향을 주는 조건.
- 기준별 결과와 차이 또는 판단 불가 이유.
- 캡처·관측 등 비교를 뒷받침하는 증거.

원본 또는 실제 산출물을 보지 못했다면 해당 기준은 `unverified`다. 필수 기준의 `mismatch`·`unverified`는 시각 적합성 인수 근거가 될 수 없다.

`visual-companion.md`의 설계 대화 운영과 구현 QA는 구분한다. 시각 동반 도구 사용이나 화면 승인 이력만으로 실제 구현 비교를 완료했다고 간주하지 않는다.

## 8. H4 — 역할·승인·보존과 재개 불변조건

- Planner는 설계·spec·plan 초안을 반환하며 파일 저장·구현·검증·승인 요청·수용을 수행하지 않는다.
- Implementer는 승인된 소유 범위의 구현·설정·테스트와 배정된 문서를 수정한다.
- QA는 승인된 검증을 수행하고 증거·제한을 보고한다.
- Reviewer의 독립성과 최종 전체 변경 검토 및 필요한 finding 재확인은 현행 계약을 따른다.
- Orchestrator는 통합·저장·승인 요청·배정·수용·완료를 소유한다. 기존 direct path 외의 구현 파일 편집 권한을 확대하지 않는다.
- Git 변경, 승인 재사용, 실행 대상 준비, 보존, task 인수와 focused commit의 기존 조건을 유지한다.
- 복구 성공이나 검사 통과는 Orchestrator 수용을 대신하지 않는다.

실패 후 재개 brief에는 원래 승인 범위, 완료 작업, 실패 지점, 실제 관측 상태, 미해결 사항, 해소 근거, 유효·무효화된 증거, 정확한 다음 목표를 포함한다. 완료한 작업을 이유 없이 반복하지 않는다.

같은 범위의 일반적인 해소·재검증에 중복 사용자 승인을 요구하지 않는다. 범위·방법·위험·대상·필수 기준이 실질적으로 바뀌면 기존 승인 변경 절차를 적용한다.

기존 역할 재사용·fresh 역할 조건을 유지한다. 재시작은 승인·지침·출처·증거를 초기화하거나 미해결 상태를 없애는 수단이 아니다. 영향을 받은 gate는 해소 후 다시 확인한다.

## 11. 검증 접근과 증거 한계

후속 검증은 다음 증거를 구분한다. 본 단계에서는 실행하지 않았다.

### 11.1 정책·구조 검사

기존 정책·parity 검사와 필요한 focused check로 원본·렌더링·프로필·reference·배포 연결의 일관성을 확인한다. 관련 기존 표면은 다음과 같다.

- `tests/node/role-policy.test.mjs`
- `tests/test_arc_policy.py`
- `tests/node/parity-check.test.mjs`
- `scripts/check-installer-parity.mjs`

문구 존재 검사만으로 충분하다고 보지 않는다. 허용 조건과 금지 조건, 이전의 포괄적 no-fallback 문구와의 충돌도 확인해야 한다.

### 11.2 행동 사례

승인된 검증 범위에서 최소한 다음 양·음성 사례를 관측한다.

- 허용된 동일 자료 읽기 대안의 성공.
- 대안 미허용·대안 실패·추측 경로.
- 필수 입력 부재·권한 거부·상태 불확실성의 보류.
- 사용자 제공 지침이 있고 루트 `AGENTS.md`가 없는 경우.
- 원본·산출물 비교가 가능한 경우와 불가능한 경우.
- 실제 시각 불일치를 `mismatch`로 보고하는 경우.
- 실패 해소 후 승인·완료 작업·유효 증거가 유지되는 재개.

라이브 역할 실행을 사용하는 경우 그 방법·격리·임시 자료·정리 소유권은 후속 계획과 검증 brief에 명시한다. 실제 Git 손상이나 권한 우회를 유발하여 금지 조건을 시험하지 않는다.

### 11.3 주장 가능한 범위

- 정적 통과: 계약과 생성·구조의 일관성 증거.
- 관측한 역할 실행 통과: 해당 플랫폼·버전·brief·사례에서의 행동 증거.
- 시각 비교 통과: 관측한 원본·산출물·환경·기준의 적합성 증거.

어느 결과도 모든 향후 실행의 준수를 보장하지 않는다. 실행 불가·누락·환경 제한은 실패나 통과로 꾸미지 않고 증거 공백으로 보고한다.

significant/high-risk 작업의 검증과 최종 전체 변경의 독립 Reviewer 검토는 현행 흐름을 따른다. Reviewer를 task별 필수 검사로 추가하지 않는다.

## 12. 호환성·위험·보류 조건

기존 brief에 허용 대안 정보가 없으면 자동 fallback 권한은 생기지 않는다. 기존 보호 동작을 유지한다. 시각자료가 적용되지 않는 작업에는 근거 있는 비해당 기록을 사용하며 불필요한 시각 검증을 추가하지 않는다.

주요 위험은 다음과 같다.

- 선택적 방법이라는 이름으로 필수 입력 부재를 숨길 위험: 입력과 방법을 별도로 분류한다.
- 복구가 역할 권한 확장으로 해석될 위험: 모든 전제조건과 금지 사항을 함께 주입한다.
- 출처 요약이 원문 의미를 바꿀 위험: 필요한 원문·발췌와 locator를 유지한다.
- 정적 검사 통과가 행동 증명으로 과장될 위험: 결과 유형과 한계를 분리한다.
- 이미지·임시 경로의 소실과 터미널 렌더링 차이: 사용 단계의 접근 확인과 환경 증거를 요구한다.
- 플랫폼별 프로필·설치본의 갱신 시차: 선택한 변경·배포 범위와 미갱신 표면을 명시한다.

다음 경우 영향을 받는 작업을 보류한다.

- 대상·소유권·준비 증거가 현재 인계 사실과 충돌한다.
- 필요한 지침·승인 원본·입력에 접근할 수 없고 허용된 해소 경로가 없다.
- 시각 기준에 승인 범위를 바꾸는 해석이나 표현 제약이 남는다.
- 생성 원본과 배포 대상의 대응 관계가 확인되지 않는다.
