## 1. 목적과 승인 범위

Codex와 Claude에서 ARC의 자동 활성화를 유지하면서, 전역 지침과 SKILL.md의 길이를 줄이고 상세 절차를 필요한 단계에서 읽도록 정리한다.

변경하는 것은 **지침의 배치와 읽는 시점**이다. 다음 의미와 동작은 보존한다.

- 기존 ARC 자동 활성화 조건과 후속 요청에서의 지속 적용.
- 역할 소유권과 권한 경계.
- 사용자 승인과 승인 재사용 조건.
- 설계·spec·plan의 순서와 승인 조건.
- TDD 및 기존 예외 조건.
- QA·Reviewer·Orchestrator 인수·커밋의 순서와 책임.
- CLI, 설치·갱신·제거 절차 및 runtime gate.
- 모델 설정, 도구 권한, Claude hook과 플랫폼별 제약.

규칙의 의미를 보존한다는 것은 각 규칙이 적용될 행동 전에 담당 역할에게 전달되도록 유지한다는 뜻이다. 매 요청의 시작부터 모든 규칙 전문을 context에 넣는 현재의 배치는 변경한다.

현재 정책 원문과 생성 흐름은 활용한다.

- 정책 원문: lib/policy/role-policy.json

## 4. 제안 구조

### 4.1 전역 bootstrap

대상은 기존 전역 파일의 ARC 관리 블록이다.

- Codex: ~/.codex/AGENTS.md
- Claude: ~/.claude/CLAUDE.md
- 사용자 지정 home에서는 현재 경로 해석 결과를 그대로 사용한다.

전역에는 다음을 유지한다.

1. 출력 언어 정책.
2. 기존 ARC 자동 활성화 조건.
3. 설치된 arc/SKILL.md를 읽고 따르라는 명시적 지시.
4. 같은 작업의 관련 후속 요청에서 계속 적용하는 규칙.
5. specialist는 profile과 brief를 따르며 Orchestrator용 skill을 다시 읽지 않는다는 지시.
6. skill을 읽기 전에 역할 경계를 넘지 않도록 하는 최소 배정 지시.

기존의 조사·분석·구현·설정·테스트·설계·spec·plan·brainstorming 적용 조건을 보존한다. 단순한 문구 정리 과정에서 적용 대상을 개발 변경 요청으로 한정하거나 새로운 예외를 만들지 않는다.

전역에 전체 역할 계약과 단계별 절차를 삽입하지 않는다. 경로를 기재하는 것만으로 파일이 자동 로딩됐다고 간주하지 않으며, 읽어야 한다는 지시를 명시한다.

### 4.2 짧은 플랫폼별 SKILL.md

대상:

- codex/skill/SKILL.md
- claude/skill/SKILL.md

두 파일은 다음을 가진 진입점과 색인이 된다.

- 현재 역할과 specialist 라우팅.
- 개발 작업의 소유권과 작은 작업 직접 처리 경로의 존재.
- 승인 범위 확대 금지, 기존 변경 보존, 외부 작업 승인 등 즉시 적용해야 하는 공통 경계.
- 기존 작은 작업·계획 생략·TDD 예외의 정확한 판단 근거를 읽을 위치.
- 행동별 필수 참조 문서와 읽는 시점.
- 필수 참조 누락·손상·충돌 시 기존 중단·보고 처리.
- 플랫폼별 실행 어댑터 차이.

예외의 이름만 보고 작은 작업으로 분류할 수 없도록 한다. 예외 적용 전에는 현재의 전체 요건을 읽어야 한다.

색인은 상세 절차의 복사본으로 커지지 않도록 구성한다. 반대로 모든 내용을 링크로만 바꾸어 첫 역할 배정이나 첫 도구 사용 전에 필요한 경계가 사라지지 않도록 한다.

### 4.3 조건부 상세 references

기존 참조 문서를 우선 활용한다.

| 단계 또는 행동 | 담당 참조 영역 | 필수 읽기 시점 |
|---|---|---|
| 설계·spec·plan 배정 | references/planning.md와 brief에 지정할 로컬 skill | 작성 역할 배정 및 해당 단계 진입 전 |
| 첫 specialist 생성 | references/limits.md, 설치된 limits.toml | 첫 생성 전 |
| 대상 준비 및 Coder handoff | references/handoff-prep.md, references/handoff.md 등 현재의 관련 참조 | 준비·배정·재시작 행동 전 |
| 의존성 및 병렬 배정 | 기존 planning·limits의 해당 영역 | 배정 순서와 동시 실행 결정 전 |
| QA 및 검증 증거 처리 | references/verification.md | 검증 배정과 관련 인수 판단 전 |
| Git 변경 | references/commit.md | 인수 및 해당 Git 변경 전 |
| 최종 전체 리뷰와 finding 처리 | 검증 참조의 해당 영역 | 최종 리뷰 배정과 후속 수정 배정 전 |

표는 문서 배치 방향을 정의한다. 구현 계획에서는 기존 참조의 관련 섹션을 확인한 뒤 정확한 링크와 이동 범위를 지정한다.

참조에는 다음을 함께 둔다.

- 언제 적용되는가.
- 누가 읽고 수행하는가.
- 필요한 선행 승인과 증거는 무엇인가.
- 무엇을 하기 전에 읽어야 하는가.
- 해당 참조를 사용할 수 없을 때 무엇을 중단하고 보고하는가.

다른 문서로 이동한 내용을 찾기 위해 이전 전체 문서를 다시 읽어야 하는 구조를 만들지 않는다. Specialist가 Orchestrator용 전체 절차를 읽어야 하는 경로도 추가하지 않는다.

### 4.4 역할별 profiles

대상:

- codex/agents/arc-*.toml
- claude/agents/arc-*.md

각 profile에는 해당 역할이 첫 행동부터 지켜야 할 완전한 계약을 유지한다.

- 역할의 허용 범위와 금지 행동.
- specialist의 Git 변경 금지.
- 승인 범위와 권한 확대 금지.
- Orchestrator에게 직접 보고하는 구조.
- 재위임 금지.
- 기존 변경 보존과 충돌 시 처리.
- 역할별 필수 입력, 산출물, 관련 참조 읽기 조건.

profile을 줄이기 위해 specialist가 전역 파일 또는 Orchestrator용 skill을 별도로 읽도록 변경하지 않는다.

모델·effort와 Codex TOML 구조, Claude frontmatter·tool allowlist·hook 연결은 유지한다. 플랫폼별 계약의 차이를 공통 문구로 덮어쓰지 않는다.

## 5. 정책 원문과 생성 구조

lib/policy/role-policy.json을 정책의 canonical source로 유지한다.

다음 내용은 변경하지 않는다.

- 규칙 ID와 역할 범위.
- effect·operations·evidence·authority.
- 정책 본문의 의미.
- 플랫폼별 controls와 notice의 의미.
- review routing.
- Git 정책과 runtime 정책.

지침 배치를 위한 출력 구분은 renderer 측에서 관리한다. 이를 위해 runtime 정책이나 gate schema를 변경하지 않는다.

renderer는 출력 위치별로 포함할 정책을 결정한다.

- 전역: bootstrap에 필요한 최소 출력.
- skill: 초기 라우팅과 즉시 적용할 공통 경계.
- references: 해당 단계의 정책과 상세 절차.
- profiles: 해당 역할의 계약.

정책 전문은 해당 출력 위치에서 canonical source로부터 생성한다. 짧은 안내문은 정책을 찾아 읽게 하는 역할을 하며 canonical 규칙 전문의 대체물이 되지 않는다.

POLICY_TARGETS와 갱신 흐름은 실제 배치를 반영한다. 모든 산출물을 동일한 방식으로 전체 계약으로 채우는 현재 동작은 지침 출력 범위에서 조정한다. Git 정책 JSON과 Claude hook 생성은 기존 결과를 유지한다.

생성은 결정적이고 반복 실행에 안정적이어야 한다. 관리 마커의 누락·중복·예상하지 않은 위치에 대한 기존 오류 검출을 약화하지 않는다.

## 6. 규칙 보존과 도달성

각 기존 규칙은 다음 관계를 가져야 한다.

canonical rule → 출력 위치 → 대상 역할 → 필수 읽기 조건 → 적용 행동

검사 가능한 배치표에는 최소한 다음을 포함한다.

- 규칙 ID.
- 의미를 보존한 전문의 출력 위치.
- 해당 규칙을 알아야 하는 역할.
- 그 역할이 읽을 경로.
- 읽기를 요구하는 행동 전 조건.
- 관련 생성 산출물.

역할별 profile에만 규칙을 두면 Orchestrator가 배정·인수에서 알아야 할 경계가 빠질 수 있다. 따라서 규칙의 실행 주체뿐 아니라 배정·승인·인수 책임자에게 필요한 경로도 확인한다.

상세 절차를 읽어야 할지 결정하는 규칙을 그 상세 절차 안에만 두지 않는다. 인수 전에 필요한 QA 조건이나 설계 전에 필요한 승인 조건이 해당 행동 이후에 읽히는 배치는 허용하지 않는다.

## 7. 배포 및 설치 산출물

지침의 원본, 정책 생성 결과, 설치 payload와 manifest를 함께 일치시킨다.

- 양 플랫폼의 skill·references·profiles가 패키지에 포함된다.
- 참조 링크는 설치된 경로에서도 해석된다.
- 사용자 지정 home과 공백을 포함한 경로 처리를 보존한다.
- 기존 전역 관리 블록 갱신과 사용자 작성 내용 보존을 유지한다.
- 재설치 시 오래된 관리 대상 파일 정리와 무관한 파일 보존을 유지한다.
- --skip-global, dry-run, check, uninstall 등 기존 동작을 유지한다.
- 기존 manifest 검증과 stale generated output 검출을 유지한다.

새 참조가 필요하면 기존 skill payload 구조 안에 둔다. 새 파일 때문에 기존 검증이 누락되는 경우 해당 산출물 검증 범위를 보완한다. 이를 이유로 설치나 runtime 동작을 재설계하지 않는다.

## 8. 수용 기준

1. 양 플랫폼 전역 블록과 SKILL.md가 기준 HEAD보다 짧아진다. 파일별 줄 수와 바이트 수의 전후 값을 기록한다.
2. 기존 자동 활성화 조건과 후속 적용 조건이 보존된다.
3. 모든 정책 규칙과 비생성 절차에 대해 대상 역할과 행동 전 읽기 경로가 존재한다.
4. 역할 소유권·승인·TDD 예외·검증·인수·Git 규칙의 의미가 보존된다.
5. profile의 모델·도구·hook 및 runtime 정책에 의도하지 않은 변화가 없다.
6. 양 플랫폼 설치 결과에서 모든 필수 참조와 생성 산출물이 존재하고 링크가 유효하다.
7. 정책 생성과 manifest가 일치하며 재생성 결과가 안정적이다.
8. 기존 CLI·설치·갱신·제거 의미와 사용자 내용 보존이 유지된다.
9. 상세 규칙 전문을 전역에서 제거한 사실을 규칙 삭제로 처리하지 않으며, 이동 후 도달성을 증거로 제시한다.
10. 실제 모델의 모든 행동이 동일하다고 단정하지 않는다. 확인한 구조적 보존과 실행 계약의 한계를 보고한다.

## 9. 필요한 focused checks와 증거

구현 계획은 다음을 영향 범위에 맞춰 구체화한다.

| 확인 영역 | 필요한 증거 |
|---|---|
| 전역 생성 | 두 플랫폼의 bootstrap 출력, 기존 trigger와 경로·언어·후속 적용 보존 |
| 정책 생성 | 규칙별 배치 누락 검출, 역할별 출력, 결정성·재생성 안정성, stale output 검출 |
| 참조 구조 | 설치 경로 기준 링크 유효성, 역할별 도달성, 행동 전 필수 읽기 조건 |
| 역할 계약 | 기존 권한·금지·승인·검증 의미 비교, 모델·도구·hook의 보존 |
| 설치 payload | 양 플랫폼과 사용자 지정 home의 필수 파일 포함, manifest 일치 |
| 설치 회귀 | 관리 블록 갱신·사용자 내용 보존·반복 설치 및 관련 기존 CLI 동작 |
| runtime 보존 | 관련 정책·설정·hook의 의미 있는 diff가 없다는 근거와 영향받는 기존 검사 |

주요 기존 검사 대상은 tests/node/global-config.test.mjs, tests/node/role-policy.test.mjs, 설치 plan·consumer·manifest 관련 검사 및 tests/test_arc_policy.py의 관련 정책 구조 검사다.

check:role-policy와 check:manifest를 적용한다. 기존의 “특정 문장이 전역에 존재한다”는 검사는 해당 의미의 배치와 도달성을 확인하는 검사로 대체한다. 단순히 기존 assertion을 삭제하여 통과시키지 않는다.

참조 로딩에 관한 구조 검사는 실제 에이전트가 매번 읽었다는 실행 증거와 구분한다. focused checks의 통과 범위와 한계를 최종 보고에 명시한다.

## 10. 중단 조건

다음이 발견되면 영향받는 후속 작업을 중단하고 Orchestrator에게 보고한다.

- 자동 활성화 범위를 보존하면서 필요한 배치를 표현할 수 없는 경우.
- 정책 의미를 바꾸거나 권한·승인·검증 단계를 줄여야 하는 경우.
- 필수 규칙이 누락되거나 담당 역할의 읽기 경로가 없는 경우.
- 필요한 판단 규칙이 조건부 참조 내부에만 있어 로딩 여부를 결정할 수 없는 경우.
- runtime gate, CLI, 설치 절차, 모델·도구·hook 변경이 필요해지는 경우.
- 필수 참조 또는 기존 정책 근거가 누락·손상·충돌한 경우.
- 승인된 target·HEAD·소유권과 다른 상태를 실제 작업 중 발견한 경우.
- 기존 검사를 대체할 동등한 보존 근거를 제시할 수 없는 경우.

정책 의미 변경이 필요하면 문서 재배치의 사소한 구현 선택으로 처리하지 않는다. 승인 범위 변경으로 Orchestrator에게 반환한다.

## 11. 한계와 후속 단계

이 설계는 항상 읽는 지침을 줄이면서 필요한 규칙을 해당 행동 전에 읽게 하는 계약을 유지한다. 정적 검사는 정책의 완전성, 배치, 링크, 생성 결과와 로딩 지시를 확인할 수 있다. 실제 플랫폼의 모델이 모든 요청에서 동일하게 참조를 읽고 동일한 결정을 내린다는 보장은 제공하지 않는다.

Orchestrator가 초안을 통합·저장하고 written-spec 승인을 받은 다음, Planner가 writing-plans 절차에 따라 작업 의존성·수용 기준·필수 검사·중단 조건을 포함한 구현 계획을 작성한다. 이 문서는 구현 순서나 커밋 단위의 계획을 대신하지 않는다.

---

자체 검토 결과:

- **범위 일치:** Codex와 Claude의 전역 자동 진입을 유지하며 기존 적용 조건을 축소하지 않았습니다.
- **정책 보존:** canonical source와 runtime 정책을 유지하고 출력 위치와 읽는 조건만 변경하도록 경계를 명시했습니다.
- **누락 위험:** 역할 실행자뿐 아니라 배정·인수 책임자의 규칙 도달성, 조건 판정의 순환 참조, 늦은 로딩을 검사 대상으로 포함했습니다.
- **설치 의미 구분:** 지침 payload의 변경과 설치 절차의 변경을 구분했습니다. generated output과 manifest 갱신은 범위에 포함됩니다.
- **플랫폼 차이 보존:** Codex profile과 Claude allowlist·hook의 차이를 유지했습니다.
- **확인 한계:** 구조 검사를 실제 모델 행동의 동일성 증명으로 제시하지 않았습니다.
- **남은 구현 계획 결정:** 기존 참조의 정확한 이동 섹션, renderer의 배치표 표현 방식, focused check 명령과 작업 분할은 written-spec 승인 후 계획에서 확정해야 합니다.
- **현재 수행 범위:** 초안 작성과 자체 검토만 수행했습니다. 파일 저장·수정·테스트·Git 변경·승인 요청은 하지 않았습니다.
