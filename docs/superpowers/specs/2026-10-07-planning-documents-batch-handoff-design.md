# 계획 문서 승인 완료 후 일괄 실행 준비 설계 명세

## 1. 목적

해당 작업에 필요한 모든 spec과 plan을 작성하고 각각 승인받은 뒤, 실행 체크아웃을 선택·필요한 브랜치 전환을 수행하고 미커밋 계획 문서를 한 번에 커밋한다.

spec 작성·승인과 plan 작성·승인 사이에 실행 체크아웃 선택·전환 또는 계획 문서 커밋을 끼워 넣지 않는다. 기존 written-spec 승인과 plan 승인 단계는 유지한다.

이 변경은 계획 산출물 작성과 Git 실행 준비의 순서를 바꾸는 Harness 정책 변경이다. 이 spec 승인 뒤 `writing-plans`에 따라 구현 계획을 작성하고 별도 승인을 받는다.

## 2. 문제와 근거

현재 [Harness 지침](../../../skill/SKILL.md)은 written-spec 승인 후 계획을 작성하고, 적용되는 계획 승인이 끝난 뒤 체크아웃을 선택하며, Coder 인계 전에 미커밋 승인 문서를 집중 커밋하도록 한다. 그러나 설치된 brainstorming 스킬은 written-spec 리뷰 전에 spec 커밋을 지시한다. Harness가 이 중간 커밋을 최종 계획 문서 일괄 준비 단계로 이연한다고 명시하지 않아, spec과 plan 사이에 브랜치 전환이나 커밋이 들어갈 여지가 있다. 여러 plan이 필요한 작업에서 적용 문서 집합이 언제 완결되는지도 분명하지 않다.

## 3. 핵심 용어와 범위

- **적용 문서 집합:** 현재 승인된 작업 범위에 필요한 모든 spec과 plan. 미래에 발생할 모든 프로젝트 문서를 뜻하지 않는다.
- **집합 완결:** 필요한 문서가 모두 작성되고 각각 승인됐으며, 미해결 범위·의존성 결정 때문에 추가 문서가 필요한 상태가 아닌 것.
- **일괄 준비:** 집합 완결 후 실행 대상을 선택하고, 필요한 경우 같은 체크아웃에서 승인된 브랜치로 전환한 뒤, 아직 커밋되지 않은 승인 문서를 한 번의 집중 docs 커밋으로 준비하는 것.

CEO는 shared brief에 현재 범위, 설계·계획 깊이 판단, 필요한 문서의 절대 경로와 범위, plan 간 의존성과 실행 순서, 승인 버전과 승인 상태, 생략되는 단계와 근거, 작성·승인이 남은 문서를 기록한다. 문서를 누락하거나 목록 밖으로 분류해 준비를 완료 처리하지 않는다.

## 4. 정상 순서

```text
설계 승인
→ 필요한 spec 작성·저장·자체 검토·승인
→ 필요한 plan 하나 이상 작성·저장·자체 검토·개별 승인
→ 적용 문서 집합과 승인 버전 완결 확인
→ 실행 체크아웃 선택 및 필요한 브랜치 전환
→ 기존 유효 커밋 검증 및 미커밋 승인 문서 일괄 커밋
→ 커밋·최종 Git 상태 검증
→ Coder 인계
```

각 승인 단계는 독립적으로 유지한다. written-spec이 필요한 경로에서는 spec 승인이 plan 작성보다 앞선다. spec 또는 plan이 기존 깊이 기준에 따라 불필요한 경로는 그 근거를 brief에 기록하고 해당 단계를 건너뛴다. 문서 작성·검토·승인 중에는 이 작업의 실행 준비를 위한 체크아웃 선택 요청, 브랜치 생성·전환, staging 또는 planning-document 커밋을 하지 않는다. 경로·저장소·Git 상태의 읽기 전용 확인은 허용한다.

문서 집합이 완결되지 않았거나 필요한 문서 승인이 하나라도 없으면 실행 준비와 Coder 인계를 보류한다. plan을 여러 개 작성하는 작업에서는 일부 plan 승인만으로 해당 부분의 Coder를 먼저 시작하지 않는다.

이 순서는 프로젝트 전체의 미래 문서가 아니라 **현재 승인된 실행 범위**의 적용 산출물에 매번 적용한다. 기존 깊이 판단에 따른 문서 생략은 문서 의무만 생략한다. 실행 대상을 명시적으로 선택하고 Git 상태·변경 소유권·최종 인계 증거를 확인하는 공통 게이트는 생략하지 않는다.

| 작업 경로 | 실행 전 필요한 승인·산출물 | 준비·인계 순서 |
|---|---|---|
| **Spike 탐색** | 탐색 질문, probe 방법·범위·수락 기준·제약 승인. 아직 모르는 구현을 위한 spec/plan은 강제하지 않음 | probe 승인 후, Coder가 실행하면 공통 게이트를 통과해 탐색 수행. CEO/Planner의 읽기 전용 조사라 Coder가 없으면 Coder 게이트는 발생하지 않음. 결과를 보고하고 구현 가능성을 재분류 |
| **Bounded, plan 생략** | 필요한 짧은 설계 승인과 기존 기준에 따른 계획 생략 근거 | 해당 승인·근거 완료 → 실행 대상 선택 → 실제 승인 문서가 있으면 일괄 커밋, 없으면 생략 사유 기록 → 공통 게이트 → Coder |
| **Bounded, plan 필요** | 짧은 설계 승인, 필요한 plan 작성·승인. written-spec은 기존 판단상 필요한 경우에만 작성 | 적용 산출물 전체 승인 → 한 번 실행 준비 → 공통 게이트 → Coder |
| **Architectural** | 설계 승인 → written-spec 작성·승인 → `writing-plans`로 필요한 plan 하나 이상 작성·개별 승인 | 적용 문서 집합 완결 → 체크아웃 선택·필요한 전환 → 미커밋 문서 일괄 커밋 → 최종 검증 → 공통 게이트 → Coder |
| **설계·계획이 적용되지 않는 비행동 문서/설정** | 범위·수락 기준과 해당 단계가 적용되지 않는 근거 | 근거 완료 → 실행 대상 선택과 Git 상태 확인 → 실제 승인 문서가 있으면 일괄 커밋, 없으면 생략 기록 → 공통 게이트 → Coder |

Spike와 후속 구현은 별개의 승인 범위다. Spike는 구현의 실현 가능성이나 불확실성을 확인하는 독립된 probe다. 결과가 구현 범위를 정하면 새로운 설계·계획 깊이 판단을 하고, 필요한 spec과 모든 plan을 작성·승인한 뒤 구현 준비 묶음을 진행한다. Spike 승인이나 탐색 코드는 후속 구현 승인으로 재사용하지 않는다. 각 범위 안에서는 그 범위의 필요한 산출물을 모두 준비한 뒤 실행 준비를 한다.

설계·계획 깊이와 검증 위험도는 독립적으로 판단한다. bounded 또는 문서 생략이 저위험을 뜻하지 않으며, architectural 작업이라는 이유만으로 매 단계에 QA·Reviewer를 추가하지 않는다. 실제 변경 위험과 기존 승인 의무에 맞춰 Harness의 위험별 QA·Reviewer 기준을 별도로 적용한다.

## 5. 외부 스킬 지시

Harness는 설치된 brainstorming 스킬의 spec 선행 커밋 지시를 이 작업 흐름에서 다음과 같이 대체한다.

- spec은 작성·저장·자체 검토 후 커밋 없이 written-spec 리뷰를 받는다.
- written-spec 승인이 있어야 계획 작성 단계로 진행한다.
- spec 커밋은 모든 적용 plan까지 작성·승인된 뒤의 일괄 준비 단계로 이연한다.
- 승인 요청에서 spec이 이미 커밋됐다고 잘못 설명하지 않는다.

외부 스킬 파일 자체는 수정하지 않는다. `writing-plans`의 구현 단계 커밋 지시는 계획 작성 중 문서 커밋이나 Coder 시작 승인으로 해석하지 않는다.

## 6. 실행 대상 선택과 모든 Coder 시작·재개의 공통 게이트

적용 문서 집합 완결 후 CEO는 절대 작업공간, 현재 브랜치 또는 detached HEAD, 기준 HEAD, 새 브랜치를 선택지로 제시할 때 검증한 후보를 알린다. 사용자는 현재 체크아웃 또는 같은 체크아웃 안의 새 task branch를 명시적으로 선택한다. 일반적인 spec·plan 승인, 무응답, 모호한 답변, 새 브랜치 거절만으로 현재 체크아웃 선택을 추정하지 않는다.

모든 최초 Coder 시작과 재개에 현재 Harness의 명시적 실행 대상 선택 및 상태 확인 규칙이 적용된다. Coder는 편집 전 brief와 실제 체크아웃을 독립적으로 확인하고, 증거 누락·상태 불일치·소유권 불명확 시 편집하지 않고 CEO에게 보고한다.

Coder를 최초 시작하거나 재개하기 전에 다음을 모두 충족한다.

1. 현재 승인 범위에 적용되는 설계, written-spec, 모든 plan의 승인과 경로가 기록됐거나 적법한 깊이 생략 근거가 있다. Coder가 Spike probe를 수행하면 승인된 탐색 질문·범위·방법·수락 기준·제약도 기록한다.
2. 현재 범위의 적용 문서 집합, 승인 버전, plan 의존성과 순서가 완결됐다. Spike probe에서는 후속 구현 산출물이 적용 문서 집합에 아직 포함되지 않으며, probe 승인으로 완료 처리하지 않는다.
3. 이번 인계의 명시적인 실행 대상 선택이 기록됐다.
4. 실제 저장소·절대 경로·브랜치·HEAD·변경 상태·소유권이 확인됐다.
5. 기존 문서 커밋과 일괄 준비 커밋이 검증됐거나, 유효한 문서 생략 근거가 있다.
6. 최종 Git 상태에 미해결 실패·부분 완료가 없다.
7. Coder brief에 승인 산출물과 준비 증거가 포함됐다.

## 7. 계획 문서 커밋

브랜치 경로에서는 성공한 전환, 실제 브랜치, 동일한 체크아웃 경로와 기존 변경 보존을 먼저 확인한다. 현재 체크아웃 경로에서는 명시적으로 선택된 브랜치 또는 detached HEAD, 경로와 기존 변경을 확인한다.

CEO는 승인된 각 문서가 이미 커밋된 경우 SHA, 실제 메시지, 포함 경로, 승인 내용과 선택된 체크아웃에서의 유효성을 확인해 재사용한다. 첫 커밋 전에 구체적인 한국어 Conventional Commit 메시지를 확정한다. 아직 커밋되지 않은 승인 문서는 대상 경로와 staged diff가 정확히 일치하는지 확인한 뒤 함께 하나의 focused docs 커밋으로 기록한다. 구현 파일과 무관한 문서는 포함하지 않는다.

- 전부 미커밋이면 적용 문서 전체를 하나의 커밋으로 준비한다.
- 일부만 미커밋이면 기존 커밋을 검증·재사용하고 나머지를 한 번에 커밋한다.
- 전부 유효하게 커밋됐으면 검증만 하고 중복·빈 커밋을 만들지 않는다.
- 과거 커밋을 단일 SHA로 억지로 합치기 위해 amend, reset, 재커밋하지 않는다.

성공 뒤 커밋 SHA, 실제 메시지, 포함 경로와 승인 내용의 일치, post-commit HEAD, 브랜치와 staged/unstaged/untracked 상태를 확인한다. 성공 종료 코드만으로 준비 완료를 선언하지 않는다. 기존 staged 파일이나 승인 범위 밖 변경은 보존하고, 준비를 중단한다. Git 쓰기 거부·브랜치 실패·부분 완료에는 기존의 안전한 진단과 차단 규칙을 적용한다.

## 8. 경계 사례

| 상황 | 처리 |
|---|---|
| plan 여러 개 | 모두 작성·개별 승인하고 의존 순서를 기록할 때까지 실행 준비를 보류한다. |
| bounded 작업에서 plan 생략 | 기존 생략 기준을 유지하고 사유를 기록한다. 실제 승인 문서가 있으면 준비하고, 문서가 하나도 없을 때만 문서 커밋을 생략한다. 불필요한 문서를 강제하지 않는다. |
| 이미 유효하게 커밋된 문서 | 내용을 검증해 재사용하고 역사 수정·재커밋을 하지 않는다. |
| 승인된 문서 수정 | 수정된 버전의 승인을 다시 받고, 이전 승인 버전으로 대체 완료 처리하지 않는다. |
| 계획 중 새 범위 발견 | 문서 목록·깊이·의존성을 재평가하고 필요한 문서를 추가 승인받는다. 집합이 완결될 때까지 준비하지 않는다. |
| 구현 중 새 범위 발견 | 영향받는 실행을 멈추고 새 범위의 승인 문서와 준비를 완료한 뒤 재개한다. 과거 커밋을 amend해 범위를 소급 포함하지 않는다. |
| 이미 실행 중인 Coder | 준비 완료로 소급 처리하지 않는다. 새 계획에 의존한 편집 전에 중단하고 현재 변경·Git 상태를 확인한다. |
| 문서 변경 없는 Coder 재개 | 기존 커밋을 검증해 재사용한다. 현재 규칙의 재개별 명시적 실행 대상 선택과 Git 상태 확인을 유지한다. |

정상 작업의 “한 번”은 문서별 준비 커밋을 없애는 의미다. 새로 승인된 범위 변경이나 안전한 실패 복구를 금지하지 않는다.

## 9. 변경 범위

- `skill/SKILL.md`: 계획 문서 작성·승인 완료 전 실행 준비 금지, 완결 기준, 외부 brainstorming 커밋 지시 이연, 일괄 문서 커밋과 예외를 명시한다.
- `README.md`: 모든 적용 문서 승인 후 체크아웃 선택과 문서 일괄 준비를 안내한다.
- `MANIFEST.sha256`: 관리 대상 변경 파일의 해시만 갱신한다.
- `agents/yunho-team-coder.toml`: 독립 사전 확인 계약은 유지한다. 필요한 문서 목록·승인 버전 확인이 부족하면 범위 변경을 보고한다.
- `tests/test_install.py`: 읽기 전용 근거로 검토한다. 이번 범위에서는 테스트를 추가·수정·실행하지 않는다.

외부 brainstorming·writing-plans 스킬, 설치기, 모델 설정, 다른 역할 프로필, 설치된 Harness 사본, 별도 프로젝트의 Git 권한은 변경하지 않는다. Push·merge·배포 권한도 확대하지 않는다.

## 10. 수락 기준

- **AC1:** 현재 승인 범위에 적용되는 모든 spec과 plan의 작성·개별 승인·목록 완결이 체크아웃 선택·전환·문서 커밋보다 먼저다.
- **AC2:** brainstorming의 spec 선행 커밋 지시는 명시적으로 이연되고 written-spec 승인 게이트는 유지된다.
- **AC3:** 다중 plan의 목록·승인 버전·의존성을 기록하며 하나라도 미완료면 인계를 막는다.
- **AC4:** 미커밋 승인 문서는 함께 한 번 커밋하고 커밋 메시지는 첫 커밋 전에 확정한다.
- **AC5:** 기존 유효 커밋을 검증해 재사용하고 amend·중복·빈 커밋을 요구하지 않는다.
- **AC6:** plan 생략은 기존 bounded 기준을 따르고 문서가 실제로 없을 때만 커밋을 생략한다.
- **AC7:** Coder 재개별 실행 대상 선택·상태 확인을 유지하고 유효한 문서 커밋은 재사용한다.
- **AC8:** 계획·구현 중 추가 범위는 필요한 승인 문서와 준비가 끝나기 전 실행하지 않는다.
- **AC9:** 기존 변경 보존, 실패 시 인계 차단, 안전한 Git 권한 복구와 Coder 독립 확인 규칙을 약화하지 않는다.
- **AC10:** SKILL·README·manifest가 일치하며 검증 한계를 정확히 보고한다.
- **AC11:** Spike probe와 후속 구현의 승인 범위를 구분하며, Coder가 수행하는 probe에도 공통 인계 게이트를 적용한다.
- **AC12:** spec·plan의 적법한 생략은 문서 의무만 생략하고 실행 대상 선택, Git 상태·소유권 확인, 인계 증거를 생략하지 않는다.
- **AC13:** 모든 Coder 최초 시작과 재개에 같은 공통 게이트를 적용한다.
- **AC14:** 설계·계획 깊이와 위험별 QA·Reviewer 판단을 독립적으로 기록한다.

## 11. 검증과 한계

검증은 정책·README·기존 계약 검사 소스의 정적 대조, diff 검토, `MANIFEST.sha256` 무결성 확인으로 한정한다. 테스트 추가·수정·실행은 하지 않는다. QA는 기준별 근거와 미검증 범위를 기록하고, Reviewer는 최종 전체 변경을 독립 검토한다.

정적 확인은 실제 에이전트 준수, 설치된 사본 적용, 실행 중인 에이전트 갱신 또는 호스트 Git 권한 복구 성공을 입증하지 않는다.

## 12. 비목표

- 승인 단계를 합치거나 written-spec 승인 전에 plan 작성을 허용하지 않는다.
- 매 Coder 재개의 명시적 실행 대상 선택 의무를 제거하지 않는다.
- 과거 문서 커밋을 재작성하거나 항상 단일 SHA로 합치지 않는다.
- 런타임 강제 장치, Git hook/wrapper, 설치기 기능, worktree 정책을 추가하지 않는다.
- 외부 스킬, 설치된 사본, 별도 프로젝트 파일·권한 또는 샌드박스 정책을 변경하지 않는다.
- push·merge·배포 승인 범위를 확대하지 않는다.

## 자체 검토

- **요청 대응:** spec과 모든 적용 plan을 먼저 완결·승인한 뒤 체크아웃 선택과 docs 준비를 수행한다.
- **승인 순서:** 기존 written-spec 승인과 plan별 승인을 보존한다.
- **외부 스킬 충돌:** brainstorming의 spec 선행 커밋만 이연하고 외부 스킬 파일은 수정하지 않는다.
- **예외:** 다중 plan, plan 생략, 기존 커밋, 문서 변경, 추가 범위, Coder 재개와 실패 경계를 포함한다.
- **범위:** 핵심 편집은 SKILL·README·manifest이며 Coder 확인 계약은 필요한 경우만 보완한다. 테스트는 이 spec 범위에서 수정·실행하지 않는다.
- **검증:** 정적 확인과 실제 준수·실행의 한계를 구분한다.
- **다음 단계:** written-spec 승인 후 `writing-plans`로 구현 계획을 작성해 별도 승인받는다. 체크아웃 선택과 문서 커밋은 모든 승인 후까지 미룬다.
