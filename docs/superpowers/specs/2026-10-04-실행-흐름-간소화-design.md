# 실행 모드 제거와 위험도에 따른 작업 흐름 간소화 설계

## 1. 목적과 승인된 방향

Harness의 두 실행 모드 정의와 모드 선택 의무를 제거한다. 새 실행 모드 이름을 만들지 않는다.

Lead는 종속 구현 작업을 순차 조율한다. Coder는 관련 맥락이 유효하면 재사용한다. 작업에 필요한 설계·계획 깊이와 검증 위험도를 별도로 판단하여 불필요한 specialist 호출과 중복 검토를 줄인다.

승인된 방향은 다음과 같다.

- 검증된 `.gitignore`·IDE/macOS metadata 정리는 Lead의 집중 확인으로 완료할 수 있으며 QA·Reviewer를 자동 호출하지 않는다.
- ordinary behavior에는 독립 QA를 적용한다.
- significant/high-risk 변경에는 QA 이후 전체 변경에 대한 독립 Reviewer 검토를 적용한다.
- 기존 owner routing, TDD, workspace/worktree, 설계·spec·계획 승인 규칙을 유지한다.
- 활성 정책, 관련 프로필, bundled dependency 문서를 동기화한다.
- 과거 승인·실행 기록을 보존한다.
- 각 작업에 적용되는 확인·QA·review를 해결하고 Lead가 acceptance로 결정하면 Lead가 선택적으로 작업 단위의 focused Git commit을 만들 수 있다.

사용자가 최초 written spec을 승인한 뒤 작업 수락 후 커밋 허용을 추가 요청했고, 이를 반영한 updated written spec도 승인했다. Written-spec 승인은 구현 계획 승인이나 구현 승인을 대신하지 않는다.

## 3. 분류와 선택 근거

이번 변경은 여러 역할이 사용하는 실행·승인·검증 계약을 재구성하므로 architectural이다. 정책 자체가 이후 구현의 검증 의무와 agent 호출을 결정하므로 significant 계약 위험으로 취급한다.

검토한 대안은 다음과 같다.

| 대안 | 결과와 trade-off |
|---|---|
| **A. 위험도별 최소 흐름 — 선택** | 순차 Lead 조율과 Coder 재사용을 유지하고 필요한 QA·Reviewer만 호출한다. 위험도 판단 기준과 생략 조건을 명확히 해야 한다. |
| B. 모드 제거 후 항상 최종 Reviewer | 판단은 간단하지만 단순 정리에도 검토 비용이 발생한다. |
| C. 모든 검증을 Lead 재량으로 결정 | 정책은 짧아지지만 ordinary behavior QA와 고위험 독립 검토가 누락될 수 있다. |

A는 사용자가 승인한 방향이다.

## 4. 범위와 보존 대상

변경 범위는 실행 모드 제거, 순차 조율, 위험도별 검증, 관련 문서·프로필의 정합성이다.

다음 계약을 보존한다.

- CEO·Lead·Secretary의 기존 담당 경계
- 공통 Planner·Reviewer·Scout가 호출 owner에게 결과·질문·다음 행동·경로 문제를 반환하는 규칙
- Lead의 개발 승인·통합·수락·검증·완료 책임
- Coder의 지정 파일 소유권과 개발 수정 책임
- QA·Reviewer의 파일 수정 금지와 역할 분리
- specialist의 agent 생성 금지와 기존 동시성 제한
- 한국어 요청에 대한 한국어 spec·plan 작성 규칙
- installed TDD 및 using-git-worktrees 적용
- 단계별 승인과 예외의 범위 제한

모델 설정, installer 동작, 전체 역할 체계, 전역 설정을 변경하지 않는다. 설치된 skill·프로필 덮어쓰기와 재설치는 이 설계의 자동 실행 범위에 포함하지 않는다.

## 5. 실행과 owner routing

Lead는 종속 구현 task를 순차 전달하고, 필요한 선행 결과·확인·발견 사항 처리를 마친 뒤 후속 작업을 시작한다.

Coder는 관련 맥락, 승인된 범위, 실제 workspace, 파일 소유권이 계속 유효하면 재사용한다. 무관한 작업이나 비대해진 맥락에는 새 Coder를 사용할 수 있다. task마다 새 Coder를 강제하지 않는다.

Lead는 개발 수정 사항을 Coder에게 반환한다. QA는 적용 가능한 확인을 독립적으로 수행하며 파일을 수정하지 않는다. Reviewer는 지정 diff/source를 독립적으로 읽고 개발 QA나 완료 결정을 대신하지 않는다.

Planner·Scout의 추가 호출은 해결되지 않은 설계·발견 질문과 기대 결과가 있을 때 사용한다. 모든 역할을 자동 호출하지 않는다.

Secretary의 기존 단독 작업·specialist 선택 권한은 유지한다. 개발용 Coder·QA 조율 및 개발 승인 의무를 Secretary나 공통 specialist에게 일반화하지 않는다.

### 작업 수락 후 Git commit

각 작업에 적용되는 집중 확인·독립 QA·review가 완료되고 발견 사항이 해결되거나 수락 가능한 상태로 명시적으로 disposition된 뒤, Lead가 해당 작업을 acceptance로 결정하면 Lead는 선택적으로 작업 단위의 focused Git commit을 만들 수 있다. 이는 해당 조건을 충족한 작업 커밋의 사용자 허용이며, 작업마다 커밋을 의무화하지 않는다.

Lead는 커밋 전 실제 변경 목록과 staged diff가 수락된 작업 범위에 한정되는지 확인한다. 다른 작업이나 사용자 변경을 섞지 않는다. 미해결 수락 기준·필수 검증·발견 사항이 남은 작업은 이 허용으로 커밋할 수 없다. 커밋이 QA·review·Lead acceptance를 대체하지 않는다.

중간 task를 수락해 커밋했더라도 전체 변경에 필요한 최종 QA·독립 review·integration acceptance는 남는다. 커밋 후 관련 변경이 발생하면 검증 근거 재사용·무효화 규칙을 적용한다.

커밋 메시지는 저장소의 Conventional Commits 규칙을 따른다: `<type>(<scope>): <description>`. 명확한 scope는 소문자로 쓰고 불필요하면 생략한다. description은 간결하고 구체적인 한국어 구절로 작성하고 끝에 마침표를 붙이지 않는다. body와 footer는 필요한 경우에만 사용하며 필요한 Git trailer 키워드와 문법을 보존한다. 한 커밋에는 하나의 논리적 변경을 담는다.

이 허용은 Git commit에 한정한다. Push·PR 생성·merge·배포·설치본 갱신을 자동 허용하지 않으며 각 동작은 해당 지침과 승인 범위를 따른다.

## 6. 설계 깊이와 계획 깊이

설계 깊이는 검증 위험도와 별도로 판단한다. 파일 수와 LOC만으로 경로를 결정하지 않는다.

| 경로 | 판단 기준 | 선행 산출물과 승인 |
|---|---|---|
| Spike | 산출물이 보존할 구현이 아닌 타당성 답변 | 질문·probe 승인 → 조사 → 결과. 구현으로 이어지면 새 분류·설계 승인 |
| Bounded | 읽을 수 있는 기존 흐름에 한정되며 의존 계약을 재구성하지 않는 변경 | 짧은 채팅 설계 승인 → Lead의 별도 계획 깊이 판단 |
| Architectural | 새 체계·하위 시스템 또는 역할·인터페이스·구성 관계 변경 | 설계 승인 → written spec 승인 → installed writing-plans → written plan 승인 |

Bounded 계획은 다음 조건을 모두 만족할 때만 생략할 수 있다.

1. 하나의 국소 변경이다.
2. 종속 단계가 없다.
3. 컴포넌트 간 공유 상태가 없다.
4. lifecycle 변경이 없다.
5. 통합 순서 문제가 없다.
6. 하나의 집중 검증 경로로 수락 기준을 확인할 수 있다.

Lead는 판단 이유와 의존성을 brief에 기록한다. Architectural은 locality·size·risk와 무관하게 writing-plans를 사용한다.

순수 비행동 문서·설정 변경에 대한 기존 직접 진행 허용을 유지한다. agent 행동 계약의 변경은 파일 형식만으로 비행동 변경이라고 판단하지 않는다.

숨은 복잡성이 드러나면 dependent 작업을 멈추고 필요한 상위 경로의 산출물·승인을 확보한다. 환경 오류만으로 자동 architectural로 분류하지 않는다.

## 7. 위험 정의와 최소 검증 흐름

Lead는 영향 행동·계약, 실패 비용, 복구 가능성, 검증 경로를 brief에 기록한다. 적용 조건이 겹치면 가장 높은 검증 요구를 사용한다.

| 위험도 | 정의 | 최소 흐름 |
|---|---|---|
| 작은 저위험 변경 | 영향이 국소적이고 이해되며 복구가 쉽다. significant 조건이 없고 집중 확인으로 수락 기준을 입증할 수 있다. | Coder → Lead 집중 확인 → Lead acceptance |
| Ordinary behavior | 일반 기능·버그·행동 변경으로 작은 저위험 조건을 모두 만족하지 않으며 significant 조건은 없다. | Coder → 독립 QA → Lead acceptance |
| Significant/high risk | 공유 계약·구성 관계의 실질 변경 또는 보안·권한·데이터·공개 인터페이스·설치/복구 위험이 있다. | Coder → QA → 전체 변경의 독립 Reviewer 검토 → Lead acceptance |

다음은 significant/high-risk 판단 조건이다.

- 여러 구성요소가 의존하는 역할·행동·공개 인터페이스 계약의 실질 변경
- 공유 상태, lifecycle 또는 통합 순서의 변경
- 인증·권한·보안 경계의 변경
- 데이터 손실 가능성, migration 또는 복구가 어려운 변경
- 설치·배포·rollback 등 실패 시 비용이 큰 흐름의 변경
- 변경 전체가 동작이나 의존 계약을 실질적으로 바꾸는 substantial scope

“substantial”은 파일 수로 판단하지 않는다. 알려진 metadata의 기계적 삭제는 파일이 많아도 자동 significant가 되지 않는다. 한 파일의 권한·데이터 삭제 규칙은 high risk일 수 있다.

## 8. QA·Reviewer 생략과 상향 조건

작은 저위험 조건을 모두 확인하고 다음 사항을 만족하면 QA·Reviewer를 호출하지 않는다.

- 영향 범위와 수락 기준이 확인되었다.
- 집중 확인에서 실패·증거 공백·범위 불확실성이 없다.
- 적용 지침이나 승인된 구체적 결정이 별도 QA·review를 요구하지 않는다.
- Lead가 Coder의 결과와 실제 근거를 확인했다.

Ordinary behavior의 QA와 significant/high-risk의 QA·독립 Reviewer는 생략하지 않는다.

위험이 불명확하면 생략할 수 없다. Lead는 필요한 범위의 발견 작업으로 불확실성을 해소하거나 높은 검증 요구를 적용한다. 새 공유 계약·lifecycle·통합 문제가 발견되면 설계 경로도 다시 평가한다.

환경 실패는 코드 실패와 구분한다. 환경 제약은 자동 architectural 판정이나 필수 확인의 자동 면제 사유가 아니다. 필요한 확인을 수행할 수 없으면 정확한 제약·대안·한계·필요 결정을 owner에게 반환한다.

## 9. 단순 정리 사례

`.gitignore`에 `.idea/`, `.DS_Store`를 추가하고 열거된 불필요 IDE/macOS metadata만 삭제하는 범위는 다음 근거가 있으면 저위험 흐름을 사용할 수 있다.

- 삭제 대상의 용도와 사용 여부가 확인되었다.
- 필요한 프로젝트 자료·동작·계약에 영향을 주지 않는다.
- ignore pattern이 의도한 경로를 포함하고 필요한 파일을 과도하게 숨기지 않는다.
- 실제 변경 목록이 승인 범위와 일치한다.
- 적용 가능한 집중 확인으로 수락 기준을 확인할 수 있다.

이 경우 QA·Reviewer를 자동 호출하지 않는다. Lead는 삭제 범위·ignore 효과·diff를 집중 확인한다.

“불필요 파일 삭제”라는 표현만으로 임의 자료를 같은 위험도로 분류하지 않는다. installer payload나 manifest 대상이면 정합성·설치 영향까지 확인하고 위험도를 다시 판단한다.

이 예시는 TDD·workspace·승인 예외를 부여하지 않는다.

## 10. QA와 독립 전체 검토의 위치

QA는 필요한 범위의 기존 행동·기능·테스트 확인을 수행한다. 정책·설정 변경에서는 승인된 범위의 적용 가능한 구조·정합성 확인을 수행할 수 있다. QA는 source·문서·test·configuration을 수정하지 않는다.

Significant/high-risk 변경의 독립 Reviewer는 QA 이후, 수락하려는 최종 관련 상태에서 전체 변경을 검토한다. 검토 범위에는 구현 task 사이의 통합과 공유 계약도 포함한다.

Task마다 fresh Reviewer를 강제하지 않는다. Reviewer 독립성은 검토 범위의 작성·구현이나 자기 판단을 검토하는 위치에서 분리되는 것을 뜻한다. 유효한 기존 Reviewer를 재사용할 수 있지만 독립성·맥락·범위·상태를 확인한다. 별도 fresh 요구나 맥락 오염이 있으면 새 Reviewer를 사용한다.

다음 작업이 아직 검증되지 않은 위험한 계약에 의존하면 해당 경계에서 필요한 QA·검토와 발견 사항 처리를 완료한다. 모든 task에 검토 gate를 자동 추가하지 않는다.

## 11. 최소 확인, 예외와 증거 재사용

모든 변경은 다음을 확인한다.

- 실제 workspace·허용 범위·선행 승인
- 수락 기준과 변경 목록
- 적용 가능한 최소 확인의 실제 결과
- 발견 사항의 해결 또는 명시적 disposition
- 남은 제약과 주장할 수 있는 결과의 범위

작은 작업은 짧은 brief와 결과로 기록한다. 구조 확인은 runtime behavior나 실제 agent 준수를 입증하지 않는다.

기존 TDD 규칙을 유지한다. 필수 단계가 막히면 Coder는 편집 전에 범위·정확한 제약·증거·필요 단계·대안·불확실성·필요 결정을 Lead에게 반환한다. 내부 판단은 필요한 인간 승인을 대신하지 않는다.

이전 six-file TDD 예외는 이번 작업에 승계하지 않는다. 이번 변경 자체가 significant 행동 계약 변경이므로 구현 단계에서 TDD 적용과 구체적 제약을 별도로 처리한다.

기존 확인·review는 다음 조건이 현재 요구를 모두 만족할 때 재사용한다.

- 범위
- 실제 증거
- 관련 상태
- 독립성
- 필요한 freshness
- 흐름상 위치

어떤 요구를 충족하는지 기록한다. 관련 수정·실패·증거 충돌·공백은 영향받는 요구만 무효화한다. 행동 수정 뒤 QA는 영향받는 확인을 재실행한다. Reviewer는 무효화된 범위나 새 위험을 다시 검토하며, 최종 전체 검토의 범위·상태·QA 이후 위치가 계속 충족되는지 확인한다.

## 12. Executor adapter와 dependency 호환성

`superpowers:executing-plans`와 `superpowers:subagent-driven-development` 등의 executor 요청은 Lead 순차 조율과 위험도별 최소 흐름으로 대응한다.

이 대응은 executor mechanics와 두 실행 방법 선택 절차를 대체한다. 다른 skill의 TDD·worktree·설계·spec·계획 승인 의무는 보존한다. 실행 방법 선택 의무를 제거해도 계획 검토·승인은 유지한다.

Bundled writing-plans의 task 경계 표현은 의미 있는 deliverable·의존성과 검증 가능성을 기준으로 정리한다. Task별 fresh Reviewer 의무를 만들지 않는다. Execution Handoff는 계획 검토·승인과 정해진 순차 흐름을 설명하며 두 방법 선택을 요청하지 않는다.

Bundled brainstorming은 architectural의 written spec·written plan 승인을 유지하면서 실행 방법 선택 참조만 정리한다.

Installer는 기존 dependency를 보존하며 버전 호환성을 검사하지 않는다. 따라서 bundled 문서 수정이 설치된 skill의 자동 갱신을 뜻하지 않는다. Harness adapter는 보존된 dependency의 기존 executor 선택 요구에도 위 대응을 적용해야 한다.

설치본 직접 수정·전역 덮어쓰기·재설치는 자동 수행하지 않는다. 새 세션이 설치된 프로필을 읽고 실행 중 agent는 자동 reload되지 않는다는 적용 한계를 안내한다.

## 13. 전환과 역사 기록

새 정책 적용 시점부터 두 실행 모드 선택 의무를 제거한다. 이미 승인된 다른 작업의 구체적 QA·review 약속이나 예외 조건은 소급 삭제하지 않는다. 변경이 필요하면 해당 owner가 영향과 필요한 결정을 다룬다.

기존 brief·spec·plan은 과거 승인·실행 증거로 보존한다. 새 문서에서 역사 기록과 현행 규칙의 관계를 설명한다. 옛 문서의 모든 모드 문자열 제거를 수락 기준으로 삼지 않는다.

작업 수락 뒤 커밋 허용을 포함한 updated written spec이 승인되었다. 다음 단계는 기존 계획 초안을 새 명세와 동기화하고 written plan 및 실행 절차 승인을 받는 것이다. 계획과 실행 절차 승인 전 worktree 생성·정책 구현을 진행하지 않는다.

## 15. 수락 기준과 검증 요구

1. 활성 정책·관련 프로필·bundled skill에 두 모드 정의나 선택 의무가 없다.
2. 새 최종 모드 이름이 없다.
3. Lead 순차 조율·Coder 재사용이 명시되고 Lead 직접 구현으로 바뀌지 않는다.
4. 위험이 확인된 단순 정리는 Lead 집중 확인으로 완료할 수 있다.
5. Ordinary behavior는 독립 QA를 요구한다.
6. Significant/high-risk는 QA 이후 최종 관련 상태의 전체 독립 검토를 요구한다.
7. Task마다 fresh Coder·Reviewer나 별도 중복 최종 review를 강제하지 않는다.
8. 위험 불명확 시 생략하지 않고 발견·상향으로 처리한다.
9. 설계 깊이·계획 깊이·위험도가 구분되고 bounded 계획 생략의 여섯 조건이 유지된다.
10. Owner routing, TDD, worktree, 단계별 승인 및 scoped exception이 유지된다.
11. 증거 재사용 조건과 무효화·재확인 범위가 명확하다.
12. 정책·프로필·dependency·README·manifest가 일치한다.
13. 기존 dependency의 보존과 실행 중 세션의 적용 한계를 설명한다.
14. 과거 승인·실행 기록을 보존한다.
15. 실제 검증 출력 없이 pass·TDD·runtime 준수를 주장하지 않는다.
16. 적용 확인·QA·review 및 발견 사항 처리가 완료되고 Lead가 acceptance로 결정한 작업은 Lead가 선택적으로 focused commit을 만들 수 있다.
17. 커밋이 검증·acceptance를 대체하지 않고 미해결 작업·무관한 변경을 포함하지 않으며, 중간 커밋 이후에도 최종 전체 검증 의무를 유지한다.
18. Conventional Commits와 한국어 description 규칙을 보존하고 push·merge 등으로 권한을 확대하지 않는다.

향후 구현 검증에는 TOML·manifest·installer 입력 정합성과 정책 사례 확인이 필요하다. 정책 사례는 저위험 정리, ordinary behavior, significant 계약 변경, 위험 불명확, QA 이후 수정, 기존 dependency의 executor 요구, 역사 승인 유지, owner 보고, 수락 전 커밋 차단·수락 후 focused commit·중간 커밋 뒤 전체 검증 유지를 포함한다.

구체적 명령·검증 허용 범위·TDD 제약 처리·작업 순서는 written-spec 승인 후 계획에서 확정한다. 구조·사례 검토만으로 실제 agent 준수를 입증했다고 주장하지 않는다.

## 16. 가정과 열린 결정

승인된 설계 방향에 대한 열린 제품 결정은 없다.

구현 전 다음 실행 사항은 Lead가 확인해야 한다.

- 실제 실행 workspace와 using-git-worktrees에 따른 필요한 결정
- 이번 계약 변경의 TDD 수행 방법 또는 정확한 제약과 필요한 scoped decision
- 기존 설치본 갱신을 별도 요청 범위로 다룰지 여부

이 사항은 현재 spec의 정책 방향을 바꾸지 않으며, 해결 전 dependent 실행을 시작하지 않는다.

## 17. 자체 검토와 다음 단계

Planner 자체 검토: placeholder와 모드 대체 이름이 없다. 설계 깊이·계획 생략·위험도·검증 의무를 구분했다. 위험 불명확 시 생략 방지, 독립 전체 review의 최종 상태와 QA 이후 위치, 기존 dependency adapter, 역사 기록 보존을 일관되게 반영했다. 과거 TDD 예외와 현재 설계 승인을 후속 gate 승인으로 확대하지 않았다.

Lead 통합·자체 검토: Planner의 한국어 초안을 보존하고 현재 승인 상태 및 조사 workspace 근거를 명시했다. 목표·범위·역할·위험·예외·수락 기준 사이의 모순과 누락 여부를 읽어 확인했다. 두 모드의 제거는 계획 승인·TDD·worktree 면제가 아니며, 이번 significant 변경은 QA와 전체 독립 review 대상이다. 활성 정책·프로필·dependency·manifest 변경은 아직 수행하지 않았다.

커밋 요구 통합·자체 검토: 수락 후 선택적 커밋만 허용하며 QA·review·acceptance 대체와 미해결 작업 커밋을 허용하지 않는다. 메시지 규칙과 범위 확인, 중간 커밋 후 전체 검증 의무를 명시했다. 최초 spec 승인 후 진행하던 계획 초안은 보류했다.

Updated written-spec 승인을 받았으므로 다음 목표는 계획 초안의 동기화·저장·자체 검토와 계획 및 구체 실행 절차 승인이다. 승인 전 worktree 생성·정책 구현을 진행하지 않는다.
