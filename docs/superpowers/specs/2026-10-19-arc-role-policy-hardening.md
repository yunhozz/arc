## 1. 배경과 의도

사용자가 제공한 Codex Coder 서브에이전트 대화에는 .github/workflows/native-prebuilds.yml을 직접 커밋하고 feat/windows-native-install에 push했다는 보고가 있다. 이를 Coder 자신의 실행 보고로 취급한다.

현재 Codex Coder 프로필은 준비 문제를 해결하려는 commit이나 브랜치 변경을 금지하지만, 정상 구현 중에도 stage·commit·push를 수행하면 안 된다는 일반 규칙이 명확하지 않다. Claude Coder 프로필은 commit을 금지하면서 일부 다른 Git 변경을 Orchestrator의 위임으로 허용하는 문구가 있어 플랫폼 간 계약도 일치하지 않는다.

기존 ARC는 Orchestrator가 작업을 수락한 뒤 커밋하도록 규정한다. Reviewer는 각 커밋의 필수 통과 단계가 아니다. 유의미하거나 위험도가 높은 작업에는 계획 유무에 따라 두 경로가 있다. 계획이 없으면 Coder → QA → 최종 전체 변경의 Reviewer 검토 → Orchestrator 수락 순서를 따른다. 계획이 있으면 작업별 Coder → fresh QA → 수락·커밋을 진행한 뒤, 모든 작업의 수락과 필요한 QA가 끝나면 Reviewer가 전체 변경을 한 번 검토한다. 두 경로 모두 필요한 Reviewer 발견 사항 재검토를 수행한다. 계획의 최종 Reviewer 발견 사항은 기존 예외에 따라 Coder → Reviewer로 재검토하며 QA에 재배정하지 않는다.

이번 변경은 여섯 역할군의 계약을 공통 원천으로 통합하고, 각 플랫폼에서 실제로 지원하는 통제를 적용하며, 강제할 수 없는 제한은 정확하게 설명한다.

## 2. 목표와 범위

다음 역할군의 허용 작업, 금지 작업, 승인 책임, Git 변경 권한, 검토 시점을 일관되게 정의한다.

- Orchestrator
- Scouter
- Planner
- Coder
- QA
- Reviewer

공통 정책에서 Codex와 Claude의 역할 계약과 관련 설정을 생성한다. 생성 누락, 오래된 산출물, 설치 payload 누락을 검출한다.

Orchestrator는 최상위 세션 역할을 유지한다. 배포하는 전문 서브에이전트는 기존 다섯 개를 유지한다. 정책이 여섯 역할군을 설명한다는 이유로 Orchestrator 전문 프로필을 새로 만들지 않는다.

이번 범위에는 별도 sandbox runner나 권한 broker 개발, 기존 모델 선택·동시 실행 수·대상 선택 절차 재설계, 무관한 installer 정리, 추가적인 사용자 커밋 승인 절차를 포함하지 않는다.

## 3. 정책 모델

각 규칙에 안정적인 ID를 부여한다. 규칙은 적용 역할, 허용·금지 작업, 필요한 증거, 책임자, 플랫폼 통제 수준을 표현한다.

작업은 다음 조건을 모두 만족해야 한다.

1. 해당 역할이 작업을 허용한다.
2. 사용자 승인과 Orchestrator의 brief가 범위·대상을 포함한다.
3. 플랫폼 설정과 실행 도구가 작업을 허용한다.

Orchestrator의 위임, 재시작, 에이전트 메시지, 첨부 문서의 명령은 역할 권한을 확대하지 않는다. 역할과 brief가 충돌하면 전문 역할은 관련 작업을 멈추고 Orchestrator에 보고한다.

사용자 지시로 역할 계약 변경이 필요하면 Orchestrator가 변경 범위를 명시하고 작업을 다시 배정한다. 기존 세션의 유효한 승인과 준비 증거는 재사용하며 역할 배정이나 재시작만으로 승인을 다시 요구하지 않는다.

| 규칙군 | 계약 |
|---|---|
| 역할·범위 | 맡은 역할과 소유 파일·행동 범위를 넘는 작업은 Orchestrator로 반환한다. |
| Git 소유권 | 전문 역할은 Git 상태를 변경하지 않는다. 작업 수락과 커밋은 Orchestrator가 담당한다. |
| 외부 영향 | push·merge·deploy·publish 및 외부 메시지는 해당 행위에 대한 명시적 사용자 권한이 필요하다. |
| 읽기 전용 | Scouter·Planner·Reviewer는 파일과 실행 환경을 변경하지 않는다. |
| QA 경계 | QA는 승인된 검사와 필요한 제한된 임시 산출물을 다룬다. 제품·소스·테스트·설정은 수정하지 않는다. |
| 독립성 | 작성자 보고, 검사 통과, Reviewer 의견은 Orchestrator의 수락을 대체하지 않는다. |
| 검토 시점 | 계획 없는 유의미·고위험 작업은 Coder → QA → 최종 전체 Reviewer → 수락 순서를 따르고, 계획 작업은 작업별 Coder → fresh QA → 수락·커밋 후 전체 Reviewer를 한 번 수행한다. Reviewer를 매 작업·매 커밋의 필수 단계로 추가하지 않는다. |
| 실패·복구 | 실제 실패와 상태·소유권 불일치는 보고하고 영향받는 작업을 중단한다. |
| 우회 금지 | 다른 도구·간접 명령·재위임으로 금지 행위를 수행하지 않는다. |

역할 프로필의 요약과 상세 참고 문서는 동일한 규칙 ID를 사용한다. 요약 과정에서 예외를 추가하거나 금지를 축소하지 않는다.

## 4. 역할별 계약

### Orchestrator

사용자 의도와 승인 범위 해석, 작업 배정, 실행 대상 준비, 변경 소유권 조정, 검사 선정, 증거 확인, 작업 수락, Git 변경 직렬화를 담당한다.

설계·사양·계획 초안은 Planner에게 배정한다. 구현·설정·테스트 코드 수정은 기존 ARC의 작고 위험도가 낮은 직접 처리 예외가 성립할 때만 직접 수행한다. 이번 변경은 그 예외를 확대하지 않는다.

유의미하거나 위험도가 높은 작업은 다음 경로를 적용한다. 계획이 없는 작업은 필요한 QA와 QA 재검사를 마친 뒤 Reviewer가 최종 전체 변경을 검토하고, Orchestrator가 수락한다. 계획 작업은 각 작업별 필요한 검사와 fresh QA를 마친 뒤 수락·커밋한다. 모든 계획 작업이 수락되고 최종 관련 QA가 끝나면 Reviewer가 최종 전체 변경을 한 번 검토한다. 계획을 생략하는 기존 경로에 새 계획 의무를 만들지 않는다.

승인된 최상위 작업의 기준과 필요한 검사가 충족되면 작업을 수락하고 해당 작업 범위의 커밋을 직접 만든다. 하위 체크박스는 진행 기록이며 별도 커밋 단위가 아니다. 커밋 후 SHA·포함 내용·HEAD·남은 변경 상태를 확인한다.

push·merge·deploy·publish 권한을 로컬 커밋 권한으로부터 추론하지 않는다. 전문 역할에게 이 행위를 넘기지 않는다.

### Scouter

배정된 범위의 정적 탐색과 자료 조사를 수행하고 출처·한계·발견 사항을 보고한다. 파일 수정, 설치, 검사 실행, 작업 대상 준비, Git 변경, 외부 상태 변경을 수행하지 않는다. 실행이 필요한 질문은 Orchestrator에게 반환한다.

### Planner

설계·사양·계획 초안과 의존성·수락 기준·보류 조건·검증 요구를 응답으로 반환한다. 저장·구현·검사·승인 요청·Git 변경을 수행하지 않는다.

실제로 준비된 절대 작업 경로, 브랜치 또는 detached HEAD, HEAD, 변경과 소유권, 대상 선택과 준비 증거, 문서 절대경로가 없으면 그 대상에 의존하는 정식 문서 작성을 멈추고 보고한다. 초기 설계 제안은 기존 절차에 따라 가능하다.

### Coder

승인된 작업과 소유 파일 안에서 구현하고 기존 절차에 따른 집중 검사를 수행한다. 수정 파일과 검사 결과·한계·후속 사항을 보고한다.

stage, commit, push, merge, rebase, reset, 브랜치 생성·전환, worktree 생성·제거를 수행하지 않는다. Orchestrator가 금지 작업을 지시하더라도 직접 실행하지 않고 Orchestrator에게 반환한다. 별칭·스크립트·다른 프로세스나 도구를 통한 실행에도 같은 제한을 적용한다.

작업을 수락하거나 전체 완료를 결정하지 않는다.

### QA

배정된 동작과 승인된 검사 범위를 검증하고 실행 명령, 관찰 결과, 실패 재현, 증거와 한계를 보고한다.

검사에 필수적인 임시 데이터·로그·보고서는 brief가 허용한 위치와 수명 안에서만 생성한다. 테스트 fixture나 제품 설정을 고쳐 검사를 통과시키지 않는다. 지속되는 제품 상태를 변경하는 검사는 범위와 정리 책임이 명시되어야 한다.

소스·테스트·설정 수정, Git 변경, 배포, 작업 수락을 수행하지 않는다. 검사 실패는 Coder 수정과 QA 재검사가 필요한 증거로 반환한다.

### Reviewer

배정된 최종 변경과 관련 증거를 독립적으로 정적 검토한다. 파일 수정, QA 검사 실행, Git 변경, 작업 수락을 수행하지 않는다.

유의미하거나 위험도가 높은 작업의 검토 시점은 계획 유무에 따라 다르다. 계획이 없는 경우 필요한 QA와 QA 재검사 후 최종 전체 변경을 검토하며, Orchestrator는 이 검토 후 수락한다. 계획이 있는 경우 모든 작업이 필요한 검사와 Orchestrator 수락·커밋을 거친 뒤 최종 전체 변경을 한 번 검토한다. 계획이 있는 작업에서 Reviewer를 작업별·커밋별 필수 검토로 추가하지 않는다.

초기 최종 전체 검토 후 발견 사항이 있으면 필요한 수정 재검토를 이어가고 반복 발견 사항도 해결될 때까지 검토한다. 계획의 최종 Reviewer 발견 사항은 동작 발견 사항을 포함해 Coder → Reviewer로 재검토하며 QA에 재배정하지 않는다. 이 예외 밖에서는 필요한 QA와 QA 실패 재검사를 유지한다.

## 5. 공통 정책과 생성 구조

기존 Node.js 런타임을 사용한다. 다음 경로는 이번 사양의 설계 선택이다.

- lib/policy/role-policy.json: 역할·규칙 ID·허용 및 금지 작업·플랫폼 통제 수준의 원천
- lib/policy/render.mjs: 정책 검증과 결정적 렌더링
- scripts/update-role-policy.mjs: 갱신 및 --check 진입점
- 필요한 최소 플랫폼 템플릿: 원천 정책의 의미를 바꾸지 않는 표현 계층

기존 SKILL.md 전체를 재생성하지 않는다. 두 플랫폼의 SKILL.md, 역할 프로필, 관련 참고 문서 및 전역 지시 블록에서 역할 계약을 담는 명확한 관리 영역을 생성한다.

관리 영역에 생성 원천과 수동 편집 금지를 표시한다. 관리 영역 밖의 기존 절차와 모델 설정은 보존한다. 중복되거나 충돌하는 기존 권한 문구는 제거하거나 생성 영역으로 옮긴다. 생성되지 않는 문서가 독자적으로 역할 권한을 정의하지 않게 한다.

정책 생성과 기존 모델 렌더링의 소유 필드를 구분한다. 정책 생성기는 역할 계약·기능 설정·hook 연결을 만들고 모델 렌더러는 모델 관련 필드만 처리한다.

## 6. 플랫폼별 메커니즘과 한계

### Codex

Codex 프로필에 명시적인 역할 계약을 생성한다. 특히 Coder의 Git 변경 금지를 정상 구현과 복구 상황 모두에 적용한다.

공식 custom agent 설정에서 지원하는 기능 축소만 사용한다. Scouter·Planner·Reviewer의 shell 기능 축소는 필요한 정적 읽기 도구를 계속 사용할 수 있는지 확인한 범위에서 적용한다. 지원 여부가 불명확한 설정 키는 생성하지 않는다.

Coder와 QA는 승인된 검사에 shell이 필요하므로 역할 이름만으로 shell을 제거하지 않는다. 앱·플러그인 기능도 필요한 자료 접근을 깨뜨릴 수 있으므로 근거 없이 일괄 비활성화하지 않는다.

확인된 문서에서는 custom agent의 일반 도구 allowlist와 PreToolUse의 역할 식별자가 입증되지 않았다. Codex Coder만 Git 변경을 차단하는 hook을 제공한다고 주장하지 않는다. Orchestrator의 정상 커밋까지 막는 전역 Git 차단도 도입하지 않는다.

Codex에서 남는 prompt 수준 제한을 생성 정책과 사용자 문서에 명시한다.

### Claude

전문 역할의 tools allowlist를 역할별로 정리한다. Scouter·Planner·Reviewer는 정적 읽기와 필요한 조사 기능으로 제한하고 쓰기 도구와 상태 변경 shell을 허용하지 않는다. QA는 검사에 필요한 실행 기능을 갖되 제품 파일 수정 권한은 계약으로 제한한다.

Git 변경을 막는 PreToolUse 보조 guard를 전문 역할에 연결한다. shell이 필요한 Coder·QA에도 적용한다. 프로필 범위 hook을 우선 사용하고 Orchestrator에 설정이 누출되지 않게 한다.

guard는 최소한 다음 직접 호출과 일반적인 명시적 조합을 다룬다.

- Git 변경 subcommand와 옵션
- git -C … 같은 전역 옵션
- 경로를 지정한 Git 실행 파일
- shell 명령 연결과 일반적인 shell wrapper
- 허용할 Git 조회 명령과 금지할 변경 명령

guard를 임의 shell이나 외부 프로그램 전체의 효과를 판정하는 sandbox로 설명하지 않는다. 지원 구문과 간접 실행의 한계를 문서화한다. 전문 역할 계약은 감지 가능한 구문보다 넓게 적용된다.

hook 경로는 설치 위치에서 안정적으로 해석되어야 하며 현재 작업 디렉터리에 의존하지 않는다. 공백이 있는 경로와 macOS/Linux/Windows의 실행·인용 방식을 고려해 installer가 연결한다. 사용자 shell 파일을 임의로 수정하지 않는다.

필수 hook 자산이나 연결이 없으면 설치가 보호 기능을 갖췄다고 보고하지 않는다.

## 7. 패키징과 설치

일반 설치는 검증된 패키지 산출물을 사용한다. 사용자 환경에서 정책을 재생성해 검증되지 않은 산출물을 만들지 않는다.

새 정책과 hook 자산을 다음 기존 체계에 포함한다.

- package.json 배포 파일
- 보호 manifest 생성과 검증
- 필수 런타임 자산 목록
- 설치 대상 매핑
- 업데이트·제거의 managed asset 소유권 처리

기존 사용자 파일의 충돌 감지·보존 절차를 유지한다. 전문 프로필 이름 다섯 개와 모델 설정 형식을 유지한다. 정책 역할군 수 여섯 개와 설치 프로필 수 다섯 개를 별도로 검증한다.

## 8. 실패와 복구

정책 스키마 오류, 중복 규칙 ID, 알 수 없는 역할, 누락된 관리 영역, 생성 결과 불일치는 검사 실패다. 부분 수정이나 설치를 계속하지 않는다.

필수 hook 자산 누락·무결성 불일치는 설치 전 검증에서 실패한다. hook이 작업을 거부하면 전문 역할은 다른 도구로 같은 행위를 재시도하지 않고 Orchestrator에게 보고한다.

hook 실행 오류에 대한 실제 플랫폼 동작을 확인하고 문서화한다. 오류 후 실행을 허용할 수 있다면 fail-closed 보장으로 표현하지 않는다.

예상하지 않은 HEAD·브랜치·index·작업 소유권 변경은 관련 작업과 수락을 보류하는 조건이다. 무단 commit·push가 이미 발생했더라도 자동 reset·force push·이력 수정으로 되돌리지 않는다. Orchestrator가 실제 상태를 확인하고 복구를 조정한다.

## 9. 이전과 호환성

정상 업데이트로 새 정책·프로필·hook을 설치한다. 새 managed asset을 기존 manifest와 소유권 관리에 추가하며 미소유 파일 보존을 유지한다.

기존 검증 중 전문 프로필 다섯 개를 요구하는 기준은 유지한다. 역할군 여섯 개를 설명하는 것 자체를 오류로 보는 기준은 수정한다.

문서 승인, 계획 생략 경로, 작업 수락, 커밋 단위, 계획 없는 작업과 계획 작업의 최종 Reviewer 경로, 최종 Reviewer 발견 사항 재검토 절차는 유지한다. 설치된 플랫폼이 지원하지 않는 설정을 조용히 무시된 보호로 제시하지 않는다.

실행 중인 에이전트가 새 프로필을 즉시 읽었다고 간주하지 않는다. 적용에 새 세션이나 에이전트 생성이 필요하면 설치 안내에 표시한다.

## 10. 수락 기준과 검증 기대

| 영역 | 수락 기준과 필요한 증거 |
|---|---|
| 공통 원천 | 여섯 역할군의 계약이 단일 원천과 안정적인 규칙 ID로 연결된다. |
| 생성 일관성 | 재생성 결과가 동일하며 --check가 오래된 산출물을 감지한다. |
| Codex | 정상 구현 중에도 Coder의 stage·commit·push가 금지되며 실제 기능 축소와 prompt 수준 제한을 구분한다. |
| Claude | 필요한 전문 프로필에 hook이 연결되고 대표적인 Git 변경 명령을 차단한다. 조회 명령과 필요한 검사 실행은 허용한다. |
| 전체 역할 | Scouter의 검사 실행, Planner의 저장·구현, QA의 제품 수정, Reviewer의 검사·수락, Orchestrator의 초안 작성·무조건 직접 구현을 각각 제한한다. |
| 수락·커밋 | Orchestrator가 작업 수락 후 커밋하며 전문 역할에 대한 위임이 권한을 확대하지 않는다. |
| 계획 없는 Reviewer 경로 | 유의미하거나 위험도가 높은 작업이 Coder → QA → 최종 전체 Reviewer → Orchestrator 수락 순서를 유지한다. |
| 계획 있는 Reviewer 경로 | 작업별 Coder → fresh QA → 수락·커밋을 유지하고 모든 작업 수락·필수 QA 완료 후 최종 전체 Reviewer 검토를 수행한다. |
| Reviewer 재검토·빈도 | 필요한 발견 사항 재검토를 보존한다. 최종 계획 발견 사항은 Coder → Reviewer로 진행하며, Reviewer를 작업별·커밋별 필수 검사로 추가하지 않는다. |
| 설치 | 누락 자산과 manifest 불일치를 탐지하며 업데이트·제거에서 사용자 파일을 보존한다. |
| 호환성 | 전문 프로필 다섯 개와 기존 모델 설정·렌더링을 유지한다. |
| 설명 정확성 | Codex 계약이나 Claude guard를 완전한 sandbox로 설명하지 않는다. |

검증은 문구 존재 검사만으로 끝내지 않는다. 생성 일관성, hook 입력·출력, installer의 격리된 대상 적용, 허용·거부 사례를 확인한다.

조회 명령, 금지 명령, 공백 경로, 전역 옵션, 연결 명령, 누락 자산을 fixture로 다룬다. 명령 문자열 검사 테스트에서 해당 명령 자체를 실행하지 않는다.

실제 Codex/Claude에서 실행하지 못한 동작은 모의 입력 결과와 구분한다. mock 통과를 네이티브 플랫폼 검증 완료로 표현하지 않는다.

계획 없는 유의미하거나 위험도가 높은 작업에서는 필요한 QA 후 최종 전체 Reviewer 검토를 마쳐야 Orchestrator가 수락한다. 계획 작업에서는 작업별 검사를 각 작업 수락 전에 완료하고 모든 작업 수락과 필요한 QA 완료 후 Reviewer가 최종 전체 변경을 한 번 검토한다. 두 경로를 별도 사례로 확인하며, 계획 없는 작업에서 Reviewer가 빠지거나 계획 작업에서 Reviewer가 각 커밋의 필수 단계가 되면 실패로 처리한다. 필요한 발견 사항 재검토는 계속한다.

## 11. 위험과 결정

문장 계약과 런타임 통제를 같은 강도로 이해하는 위험이 있다. 플랫폼별 통제 수준과 한계를 함께 설명한다.

생성기가 모델 렌더링·설치 무결성 검사와 충돌할 수 있다. 생성 순서, 필드 소유권, 기존 설정 보존을 검증한다.

Reviewer 시점을 단순화하면서 계획 없는 유의미하거나 위험도가 높은 작업의 검토가 누락될 수 있다. 두 경로를 정책 원천·생성 문구·검증 사례에 각각 명시한다. 최종 계획 발견 사항의 QA 재배정 예외를 계획 없는 경로로 확장하지 않는다.

Claude guard는 정상 명령을 잘못 차단하거나 간접 명령을 놓칠 수 있다. 지원 구문을 명시하고 허용·거부 사례를 함께 확인한다.

관리 영역 생성, 기존 Node.js 사용, 다섯 전문 프로필 유지, 별도 sandbox runner 제외는 이번 설계의 선택이다. 구현 중 새 런타임이나 권한 broker가 필요하면 범위 변경으로 보고하고 의존 작업을 보류한다.

이 사양 승인 후 비로소 구현 계획을 작성한다.

## 12. 근거

현재 worktree는 조사한 기준 HEAD와 동일하다. 다음 상대경로의 근거를 적용한다.

- codex/agents/arc-coder.toml: 보존·준비 오류·보고 계약과 일반적인 Git 변경 금지의 누락.
- claude/agents/arc-coder.md: Orchestrator의 커밋 소유권과 일부 Git 작업의 위임 허용 문구.
- codex/agents/arc-reviewer.toml: 읽기 전용·최종 전체 검토·발견 사항 재검토.
- codex/skill/references/commit.md: 작업 수락 후 Orchestrator의 커밋 및 최종 Reviewer 발견 사항 재검토.
- lib/installer/manifest.mjs: 필수 자산과 전문 프로필 다섯 개 검증.
- scripts/update-manifest.mjs: 보호 payload manifest 생성·검사.

플랫폼 근거는 Orchestrator가 현재 문서에서 확인해 제공한 다음 자료를 사용한다.

- [Codex custom subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- [Claude subagents](https://code.claude.com/docs/en/sub-agents)
- [Claude hooks](https://code.claude.com/docs/en/hooks)

## 자체 검토

- 수정된 managed worktree 경로·detached HEAD·문서 절대경로만 실행 대상 증거로 사용했다.
- Coder 자신의 commit·push 증거를 반영했다.
- 모든 역할군을 다루며 전문 프로필 수와 역할군 수를 구분했다.
- 계획 없는 유의미·고위험 작업의 Coder → QA → 최종 전체 Reviewer → 수락 경로를 보존했다.
- 계획 작업의 작업별 Coder → fresh QA → 수락·커밋과 이후 최종 전체 Reviewer 경로를 보존했다.
- Reviewer를 작업별·커밋별 필수 단계로 추가하지 않았고 필요한 후속 재검토를 보존했다.
- Codex 기능 한계와 Claude guard의 제한을 명시했다.
- 제품 수정 권한과 QA 임시 산출물 권한을 구분했다.
- 파일 저장·구현·검사·구현 계획 작성은 수행하지 않았다.
