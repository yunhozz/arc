# Coder 인계 게이트와 Git 메타데이터 권한 복구 설계 명세

## 1. 목적

승인된 계획 문서를 커밋하기 전에 Coder가 시작되는 실수를 방지한다. Coder를 시작하거나 재개하기 전에 실행 체크아웃을 명시적으로 선택하고, 계획 문서 커밋 또는 생략 근거, 최종 Git 상태를 확인한다. 문서 커밋 메시지는 첫 커밋 전에 확정한다. Git 메타데이터 쓰기가 거부되면 권한을 우회하지 않고 승인된 복구 경로를 사용하거나 인계를 중단한다.

이 변경은 CEO와 Coder 사이의 공통 인계 계약 및 실행 순서를 바꾸므로 아키텍처 변경으로 취급한다. 이 명세의 승인을 받은 뒤 별도 구현 계획을 작성하고 승인을 받는다.

## 2. 근거와 확인 경계

참조된 `Fix object placement flow` 대화에서 계획 승인 후 확인한 상태는 `master`, HEAD `2a89b233ee5f5101b40f18b900b63ea98648b8a2`, 승인된 spec과 plan은 미추적 상태였다. 그런데 Coder가 먼저 시작됐다. 이후 Coder가 상태 변경을 보고 멈춘 다음, CEO가 계획 문서 선행 커밋 규칙을 확인하고 문서만 커밋한 후 재개했다. 첫 메시지가 일반적인 내용이어서 이를 고치려 `git commit --amend`를 시도할 때 `.git/index.lock` 쓰기 권한 오류가 보고됐다.

현재 읽기 전용 확인에서 `token-planet` 경로는 `/Users/ma-24-007/Desktop/workspace/token-planet`, 브랜치는 `master`, HEAD는 계획 문서 커밋 `a1dee6ac4d08075a86fbe6797b7a2f00ecc50deb`이며 구현 변경이 미커밋 상태로 남아 있다. 현재 `.git/index.lock`은 없고 `.git` 디렉터리와 index 파일은 OS 권한상 소유자 쓰기가 가능하다. 이 실행 환경은 해당 저장소의 Git 메타데이터 쓰기를 샌드박스로 제한한다. 이는 과거 실패가 stale lock이나 OS 소유권 문제였다고 입증하지 않는다. 정확한 당시 오류 원인은 확정하지 않는다.

## 3. 변경 범위와 책임

| 파일 | 변경 책임 |
|---|---|
| `skill/SKILL.md` | 명시적 체크아웃 선택, 단일 인계 게이트, 계획 문서 커밋, 권한 실패 복구 절차 |
| `agents/arc-coder.toml` | 편집 전 인계 증거 독립 확인 및 누락 시 중단 |
| `README.md` | 인계·Git 권한 실패 흐름의 간단한 사용자 안내 |
| `MANIFEST.sha256` | 변경 대상 파일 해시 갱신 |
| 이 설계/구현 계획 문서 | CEO가 통합·저장·자체 검토하고 승인 기록 |

Coder가 구현 파일을 편집하고 변경된 관리 파일의 manifest 해시를 갱신한다. CEO는 승인·체크아웃 선택·계획 문서 커밋·인계 브리프·통합과 수락을 소유한다. QA와 Reviewer는 승인된 범위에 따라 독립적으로 정책 일관성과 전체 변경을 검토한다. 설치기의 실행 기능, 다른 역할 프로필, 모델 설정은 범위 밖이다.

## 4. 명시적 실행 대상 선택

모든 Coder 최초 시작과 재개 전에 CEO는 이번 인계의 실행 대상을 사용자에게 제시하고 선택을 기록한다.

1. 공급된 절대 경로의 현재 체크아웃에서 진행
2. 같은 체크아웃 안에서 확인된 기준 HEAD로 새 작업 브랜치를 만들어 진행

선택 요청에는 절대 작업공간, 현재 브랜치 또는 detached HEAD, 기준 HEAD를 포함한다. 새 브랜치를 선택지로 제시할 때에는 검증한 브랜치 후보도 포함한다. 계획 승인을 체크아웃 선택으로 간주하지 않는다. 무응답, 불명확한 답변, 단순한 계획 승인은 선택 완료가 아니다. 선택이 없으면 기다리고 Coder를 시작하거나 재개하지 않는다.

새 브랜치명 검증, 충돌 검사, 후보 변경 시 재승인, 작업공간 고정, 기존 변경 보존 및 실패 시 중단 규칙은 유지한다. 새 작업공간이나 worktree 생성은 허용되지 않는다.

## 5. 단일 Coder 인계 게이트

CEO는 다음 조건을 모두 확인한 뒤에만 Coder를 생성하거나 기존 Coder에 구현을 재개시킨다.

1. 작업에 적용되는 설계·명세·계획 승인이 완료됐다.
2. 이번 인계의 명시적 체크아웃 선택을 기록했다.
3. 절대 경로가 접근 가능하고 의도한 Git 저장소인지 확인했다.
4. 실제 브랜치 또는 detached HEAD, HEAD, staged·unstaged·untracked 상태와 기존 변경의 소유권을 확인했다.
5. 승인된 계획 문서 전용 커밋을 검증했거나, 문서가 요구되지 않고 생성되지 않은 근거를 기록했다.
6. 커밋·브랜치 전환 이후 최종 상태를 재확인하고 미해결 실패나 부분 완료가 없음을 확인했다.
7. Coder brief에 승인 산출물 경로와 위 준비 증거를 넣었다.

하나라도 누락되거나 실패하면 인계는 차단 상태다. CEO의 읽기 전용 탐색과 준비·복구 작업은 계속할 수 있지만, 이를 이유로 Coder를 먼저 시작하지 않는다. 이미 커밋된 유효한 계획 문서는 검증해 재사용하며 중복 커밋하지 않는다. 문서 내용·선택 대상·브랜치·HEAD가 바뀌면 관련 증거를 다시 확인한다.

## 6. 계획 문서 커밋

작성·승인된 spec 또는 plan은 Coder 인계 전에 승인된 문서만 포함하는 하나의 집중 커밋으로 준비한다. CEO는 승인 버전과 대상 경로를 기록하고, staged 경로와 staged diff가 승인 문서와 정확히 일치하는지 확인한다. 무관한 staged 변경이 있으면 그대로 보존하고 중단한다. 자동 unstage, reset, stash, clean 또는 다른 변경 삭제를 하지 않는다.

문서가 이미 유효하게 커밋됐다면 SHA, 커밋 메시지, 포함 경로와 내용이 승인본과 일치하는지 확인해 재사용한다. 문서가 요구되지 않았고 생성되지 않은 경우에만 커밋을 생략하며, 적용된 계획 깊이 판단과 생략 이유를 기록한다. 미커밋 문서가 있는데 생략된 것으로 취급하지 않는다.

CEO는 첫 커밋 전에 최종 메시지를 정한다. 예를 들어 `docs(arc): Coder 인계와 Git 권한 복구 절차 정리`와 같이 범위를 드러내는 구체적인 한국어 메시지를 사용한다. 일반 임시 메시지로 먼저 커밋한 뒤 메시지만 고치는 `git commit --amend` 흐름을 준비 절차로 사용하지 않는다. 실제 amend가 별도로 필요하면 기존 승인 범위와 현재 HEAD·공개 여부를 다시 확인한다.

커밋 성공 후 SHA, 실제 메시지, 포함 경로, post-commit HEAD, 최종 브랜치, staged·unstaged·untracked 상태를 확인해 브리프에 기록한다. 명령의 종료 코드만으로 완료를 선언하지 않는다. 이 커밋은 구현 수락이나 push 승인이 아니다.

## 7. Git 메타데이터 쓰기 거부

승인된 `git add`, `git commit`, 브랜치 생성 또는 전환에서 `.git/index.lock`이나 다른 Git 메타데이터 쓰기가 거부되면 CEO는 Coder 인계를 중단한다. 다음 내용을 읽기 전용으로 확인한다.

- 실패한 정확한 명령, 작업공간, 오류 및 실패 경로
- 실제 Git 디렉터리 위치, 현재 브랜치·HEAD·index 상태와 부분 완료 여부
- `.git/index.lock` 존재 여부와 확인 가능한 관련 프로세스 상태
- 샌드박스 제한, OS 권한·ACL, 동시 Git 작업 중 어느 원인인지 확인 가능한 근거와 남은 불확실성

lock 생성 거부만으로 stale lock이라고 판단하지 않는다. lock 파일을 삭제하거나 `chmod`·`chown`으로 권한을 바꾸지 않는다. 샌드박스 제한이 원인으로 확인되고 작업이 이미 승인된 범위라면, 도구가 지원하는 정확한 단일 Git 명령과 작업공간만 대상으로 최소 권한 escalation을 요청한다. 재시도 전 브랜치·HEAD·index 및 부분 완료 상태를 다시 확인하고, 이미 완료된 작업을 반복하지 않는다. 재시도 성공 뒤 커밋 또는 전환 결과를 다시 검증하고 인계 게이트를 재평가한다.

escalation이 거부되거나 OS 권한·ACL 문제가 해결되지 않으면 CEO는 실패 이유와 현재 상태를 보고하고 인계를 계속 차단한다. 다른 작업공간으로 우회하거나 broad Git 권한을 요청하지 않는다. 권한 변경, stale 여부를 확인하지 않은 lock 삭제, 자동 reset/stash/clean도 복구 기본값이 아니다.

최종 메시지를 처음부터 올바르게 정하면 불필요한 amend를 예방할 수 있지만, 필수 Git 메타데이터 쓰기 권한 자체를 해결하지는 않는다. 실제 권한 복구는 승인된 쓰기 작업이 성공하고 결과를 검증해야 완료된 것으로 본다.

## 8. Coder의 독립 확인

Coder는 편집 전에 brief의 승인 산출물, 이번 인계의 명시적 체크아웃 선택, 절대 작업공간, 브랜치·HEAD, 관련 변경 상태, 계획 문서 커밋 또는 생략 근거를 확인한다. 공급된 작업공간을 읽기 전용으로 대조한다.

증거가 누락되거나 실제 경로·브랜치·HEAD·소유권이 다르면 편집을 시작하지 않고 누락 항목과 관찰 상태, CEO가 해야 할 다음 조치를 보고한다. Coder는 이 문제를 해결하기 위해 커밋하거나 브랜치를 만들고 전환하거나 Git 권한을 바꾸지 않는다. CEO가 준비를 해결하고 게이트를 다시 통과시킨 뒤 재개한다.

## 9. 수락 기준

- **AC1:** 모든 Coder 최초 시작과 재개 전에 명시적 실행 대상 선택을 받으며 무응답을 선택으로 취급하지 않는다.
- **AC2:** 적용 승인, 체크아웃 확인, 계획 문서 커밋 또는 유효한 생략 근거, 최종 상태 검증 중 하나라도 미충족이면 Coder를 시작하지 않는다.
- **AC3:** 승인 문서 외 staged 변경은 보존하고 인계를 중단한다.
- **AC4:** 이미 유효한 계획 문서 커밋은 SHA·메시지·경로·내용을 검증해 재사용한다.
- **AC5:** 첫 커밋 메시지를 사전에 확정해 routine amend를 제거한다.
- **AC6:** Coder가 brief 증거와 실제 작업공간 상태를 독립 확인하고 불일치 시 편집 전에 중단한다.
- **AC7:** Git 쓰기 거부 시 안전한 조사, 최소 escalation, 거부 시 차단, 성공 후 재검증을 요구한다.
- **AC8:** 권한 우회, lock 삭제, 임의 작업공간 전환, 자동 reset/stash/clean을 복구 수단으로 쓰지 않는다.
- **AC9:** SKILL, Coder 프로필, README와 manifest가 같은 계약을 반영한다.

## 10. 검증과 한계

Coder는 승인된 범위의 기존 정책·설치 구조 검사를 수행하고 변경 파일만 manifest에 반영한다. QA는 AC별 근거와 미검증 사항을 확인하고, Reviewer는 수정 후 전체 변경을 독립 검토한다. 정적 정책·manifest 검사는 지침의 일관성만 확인하며 실제 에이전트 준수나 호스트의 파일시스템 권한 해결을 입증하지 않는다.

실제 Git 권한 문제는 대상 저장소에서 승인된 쓰기가 성공하고 브랜치·HEAD·index 결과를 확인해야 해결됐다고 판단한다. 현재 확인된 `token-planet`의 상태는 이 명세를 저장하는 ARC 체크아웃의 변경 대상이 아니며, 해당 저장소 파일이나 권한을 수정하지 않는다.

## 11. 비목표

- Git hook, wrapper, 런타임 제어기 등 지침 외의 실행 강제 장치를 추가하지 않는다.
- 모델, 역할 계층, worktree 정책, push·merge·배포 승인을 변경하지 않는다.
- OS 소유권·ACL 또는 샌드박스 정책 자체를 변경하지 않는다.
- 설치된 ARC 사본이나 실행 중인 에이전트를 이번 저장소 변경만으로 갱신했다고 주장하지 않는다.

## 자체 검토

- 계획 승인과 체크아웃 선택을 서로 다른 근거로 분리했다.
- 최초 인계와 기존 Coder 재개 모두 같은 필수 게이트를 거친다.
- 계획 문서 커밋 증거를 Coder handoff 전 단계에 연결했다.
- 불필요한 amend 예방과 실제 `.git/index.lock` 쓰기 권한 복구를 구분했다.
- lock 삭제·권한 변경·다른 작업공간 우회를 복구 수단에서 제외했다.
- 현재 `token-planet`의 읽기 전용 확인을 과거 오류의 원인 확정으로 과장하지 않았다.
- 다음 단계는 이 written spec 승인 후 Planner가 구현 계획을 작성하는 것이다.
