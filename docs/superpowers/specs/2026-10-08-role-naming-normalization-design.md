# 역할 이름 정규화와 README 한국어화 설계 명세

**상태:** 승인된 설계를 반영한 written-spec 초안
**작성 책임:** Planner
**통합·저장·검토·승인 책임:** CEO
**작업공간:** `/Users/yunho/.codex/worktrees/cd32/arc`

## 1. 목적과 승인 범위

저장소의 역할 이름을 일관된 `arc` 명명 체계로 변경하고, 기존 설치에서 이전 역할 프로필이 중복 노출되지 않도록 안전하게 이전한다. README의 영어 설명 문장은 한국어로 번역한다.

변경 대상은 현재 저장소의 소스·설정·테스트·manifest·README·과거 계획 및 명세 문서와 파일명이다. Git 과거 객체를 재작성하거나 실제 사용자 홈을 변경하지 않는다. 설치 검증은 임시 환경에서 수행한다.

이 작업은 Architectural 경로다. 이 written spec 승인 후 `writing-plans`에 따라 전체 구현 계획을 작성한다. 설치 마이그레이션과 공유 역할 인터페이스 변경은 중요 위험 작업으로 보고 QA와 최종 전체 변경의 독립 Reviewer 검토를 거친다.

## 2. 명명 규칙

여섯 역할에 다음 이름을 사용한다.

| 역할 | 역할 ID 및 모델 설정 키 | 저장소 프로필 경로 |
|---|---|---|
| Secretary | `arc_secretary` | `agents/arc-secretary.toml` |
| Planner | `arc_planner` | `agents/arc-planner.toml` |
| Scout | `arc_scout` | `agents/arc-scout.toml` |
| Coder | `arc_coder` | `agents/arc-coder.toml` |
| QA | `arc_qa` | `agents/arc-qa.toml` |
| Reviewer | `arc_reviewer` | `agents/arc-reviewer.toml` |

각 프로필의 `name`, `ROLE_FILES` 키, `models.toml`의 역할 키, 설치기의 `PROFILE_FILES`, 테스트 기대값, 문서 참조를 이 표에 맞춘다. 모델 ID, 추론 강도, 역할 책임, 권한, 보고 관계는 기존 값을 유지한다.

과거 문서에 기록된 폐기 역할은 `arc_lead`와 `arc-lead.toml` 표기로 정규화한다. 이 역할을 현재 역할이나 설치 대상으로 다시 추가하지 않는다.

요청된 옛 접두사는 구성 요소 `("yunho", "team")`를 `_` 또는 `-`로 연결해 계산한다. 이 호환 처리와 검사 코드를 포함해 현재 저장소의 파일 내용과 경로에 해당 접두사가 연속된 문자열로 남지 않게 한다.

## 3. 모델 설정 형식

`skill/models.toml` 형식 버전을 `4`로 변경한다. 최상위 키는 `version`과 `roles`이며, `roles`에는 위 여섯 ID만 정확히 포함한다.

각 역할은 `model`과 `model_reasoning_effort` 두 문자열 필드만 가진다. 기존 문자열 검증과 프로필 렌더링 제약을 유지한다. 직렬화 결과도 버전 `4`와 새 여섯 역할 키를 사용한다.

버전 `1`, `2`, `3`은 자동 변환하지 않는다. 이전 형식 또는 새 버전에 이전 역할 키를 넣은 설정은 명확한 검증 오류를 반환하고 파일을 변경하지 않는다. 오류 안내는 새 설정 형식과 업데이트 필요성을 설명한다.

새 설치는 저장소 설정을 사용한다. 기존 사용자 모델 설정을 자동 병합하지 않으며, 기존 ARC 백업에서 원래 설정을 복원하거나 참고할 수 있다. 원격 모델 지원이나 계정 접근 여부를 검증한다고 주장하지 않는다.

## 4. 이전 설치 후보와 보존 범위

이전 프로필 후보는 구성 요소 `("yunho", "team")`를 `-`로 연결한 접두사에 아래 역할 suffix와 `.toml`을 붙여 산출한다.

```text
secretary
planner
scout
coder
qa
reviewer
```

후보는 선택한 Codex home의 `agents/` 바로 아래 여섯 경로로 한정한다. glob이나 파일 내용의 유사성으로 다른 파일을 삭제하지 않는다. 폐기 역할과 다른 사용자 프로필은 대상에 포함하지 않는다.

후보가 없으면 신규 설치로 처리한다. 후보 일부만 있는 설치도 지원한다. 이전 후보와 새 대상이 함께 존재하면 각각의 원래 파일을 백업하고 새 대상 여섯 개를 설치한다.

존재하는 이전 후보는 일반 파일이어야 한다. 심볼릭 링크, 디렉터리, 특수 파일 또는 안전하지 않은 상위 경로는 설치 변경 전에 오류로 처리한다. 새 대상에 적용되는 기존 경로 검사도 유지한다.

이전 프로필의 사용자 수정은 파일 전체를 백업해 보존한다. 일부 필드를 새 프로필로 자동 병합하지 않는다.

## 5. 설치 거래와 실패 처리

설치는 다음 순서를 따른다.

1. 내부 payload, manifest, 모델 설정, 새 프로필, 설치 대상과 이전 후보를 검사한다.
2. 외부 스킬을 기존 취득·검증 계약대로 준비한다.
3. 기존 ARC, 외부 스킬 대상, 새 프로필 대상, 존재하는 이전 후보를 기존 timestamp 백업 아래 보존한다.
4. 교체할 payload와 새 프로필을 staging에 준비한다.
5. 존재하는 이전 후보를 거래용 보존 위치로 이동한다.
6. 외부 스킬, ARC, 새 프로필을 기존 거래 체계 안에서 설치한다.
7. 성공하면 거래용 임시 데이터를 정리하고 영구 백업 위치를 보고한다.

이전 후보 제거는 새 프로필 설치보다 먼저 수행한다. 복구 가능한 이동으로 구현하고 기존 거래 action 기록에 포함한다.

대상 변경 전 백업·staging 준비가 실패하면 활성 설치 파일은 바뀌지 않아야 한다. 이전 후보 이동이나 이후 교체가 실패하면 완료한 동작을 역순으로 복구해 거래 전 상태를 회복한다.

- 원래 있던 이전 후보의 내용과 경로
- 원래 있던 새 이름 대상의 내용과 경로
- 원래 없던 새 대상의 부재
- 거래 중 변경된 ARC와 외부 스킬의 이전 상태

복구 자체가 실패하면 기존 오류 보고 계약대로 백업과 필요한 recovery 데이터를 보존하고 경로를 보고한다. 전체 파일시스템에 걸친 원자성을 보장한다고 설명하지 않는다.

성공 후 활성 `agents/`에는 새 역할 여섯 개가 설치되고, 존재했던 이전 후보는 남지 않는다. 범위 밖 프로필은 내용·경로·파일 유형이 유지되어야 한다.

## 6. 검사 모드와 모델 적용

`install.py --check`와 `install.py --dry-run`은 이전 후보와 새 대상의 안전성을 읽기 전용으로 검사한다. `--dry-run`은 존재하는 이전 후보의 제거와 새 대상 설치 계획을 표시한다.

두 모드는 파일·백업·캐시를 만들지 않고 subprocess, 외부 취득, 네트워크를 실행하지 않는 기존 계약을 유지한다. 설치기 오류 종료 코드는 `2`다.

설치된 `apply-models.py`는 새 역할·파일명과 형식 버전 `4`를 사용하며 기존 동작을 유지한다.

- `--check`: 일치 시 `0`, 모델 설정 차이 시 `1`
- `--dry-run`: 변경 예정 내용만 표시
- 일반 실행: 새 여섯 프로필에 설정 적용
- 설정·프로필·경로 오류: `2`
- 원본 모델 설정 파일은 자동으로 다시 쓰지 않음
- 준비 또는 적용 실패 시 기존 프로필 보존·복구 계약 유지

실행 중인 에이전트의 설정·부모 관계·역할 선택은 설치로 자동 변경되지 않는다. 사용자 작성 외부 참조를 자동으로 찾아 바꾸지 않는다.

## 7. 문서 정규화와 README 번역

현재 저장소의 과거 plans, specs, brief에도 새 명명 체계를 적용한다. 날짜, 기존 승인 사실, 당시 범위와 폐기 역할의 역사적 의미는 유지한다. README에 과거 문서의 명칭 표기를 현재 체계로 정규화했음을 짧게 설명한다. 과거 기록을 현재 실행 지시나 새 승인으로 표현하지 않는다.

README의 소개와 본문 설명, 표와 목록의 설명, 주의 문구를 한국어로 번역한다. 역할 책임, 검증 위험, 필수 참조, 설계·계획 승인, Coder 인계, 설치, 모델 변경, 백업과 무결성 설명을 모두 포함한다.

문장으로 쓰인 영어 역할 설명은 한국어로 바꾸되, 제품명과 기술 표기는 유지한다. 역할 ID, 모델 ID, 스킬/API 이름, 명령, 옵션, 환경 변수, 설정 키와 literal 값, 경로, URL, 링크 대상, 파일명, 식별 가능한 CLI 출력 예시는 정확히 보존한다.

명령과 TOML 예시는 새 이름 체계 및 형식 버전으로 갱신한다. 번역 과정에서 설치 제한이나 검증의 한계를 생략하지 않는다. README에는 이전 프로필 백업·제거, 설정 버전 변경, 사용자 모델 설정을 자동 병합하지 않는 점, 새 세션 필요성, 외부 역할 참조의 수동 수정 필요성을 설명한다.

## 8. Manifest와 변경 책임

변경된 immutable payload와 새 프로필 경로의 SHA-256을 갱신하고 이전 프로필 경로 항목을 제거한다. `skill/models.toml`은 기존 mutable 제외 계약을 유지한다.

구현·설정·테스트 및 구현 의존 문서는 CEO의 개발 범위 아래 지정된 역할이 편집한다. CEO는 승인 문서 통합·저장·검토·준비와 개발 수락을 담당한다. 실제 사용자 home의 설치 파일과 외부 설치 스킬은 수정하지 않는다.

## 10. 검증 요구사항

기존 `tests/test_install.py`의 설치·모델 검증을 확장해 다음 동작을 확인한다.

- 신규 설치, 이전 후보 일부·전부가 존재하는 업그레이드, 이전·새 대상 공존, 반복 설치
- 이전 후보 백업의 원본 내용과 활성 위치 제거
- 범위 밖 프로필 보존
- 이전 후보 이동 실패, 새 대상 교체 실패, 복구 실패와 recovery 보존
- 이전 후보 및 새 대상의 심볼릭 링크·디렉터리·특수 파일 거부
- 검사 모드의 파일시스템 불변성과 외부 취득 부재
- 형식 버전 `4` 정상 설정, 이전 버전 거부, 역할·프로필 이름 불일치 거부
- 새 모델 적용의 check·dry-run·쓰기 및 실패 복구

옛 접두사를 필요로 하는 테스트 입력과 검색 검사는 구성 요소를 결합해 생성한다. 테스트 소스에 두 금지 접두사의 연속 문자열을 남기지 않는다.

별도로 저장소 전체 내용·경로 검사, TOML 매핑 검사, manifest 검사와 README 번역 검토를 수행한다. QA는 기준별 실제 근거를 보고하고, 최종 독립 Reviewer는 QA 이후 전체 변경의 마이그레이션 범위·복구·문서 의미·번역 누락을 검토한다.

임시 설치 실험은 설치기 동작을 입증한다. 실제 Codex 새 세션에서 새 역할을 선택할 수 있는지는 별도 runtime 확인이 필요하며 구조 검사나 설치 성공만으로 입증했다고 보고하지 않는다.

## 11. 가정과 범위 제한

- “모든 곳”은 현재 저장소 내용과 경로를 뜻한다. Git 과거 객체와 사용자 백업은 정규화 대상이 아니다.
- 이전 설치 후보는 위 여섯 경로뿐이다. 폐기 역할과 다른 파일의 정리는 범위 밖이다.
- 기존 사용자 모델 설정은 자동 병합하지 않는 현재 설치 계약을 유지한다.
- README 번역은 설명 문장에 적용하며 기술 표기는 보존한다.
- 실제 설치 실행이나 외부 소비자 설정 수정은 구현·검증 범위에 포함하지 않는다.
- 승인된 설계에 추가로 결정해야 할 사항은 발견하지 않았다. 범위가 달라지면 CEO가 변경 승인과 영향받는 문서를 처리한다.

## 자체 검토 결과

- **범위:** 이름 변경, 설치 이전, 모델 형식, 전체 문서 정규화와 README 번역을 포함한다.
- **일관성:** 새 여섯 역할 표를 프로필·모델·설치기·문서의 공통 기준으로 사용한다.
- **실패 처리:** 후보 이동, 새 대상 교체와 복구 실패를 구분하고 백업·recovery 보존을 명시했다.
- **보존:** 범위 밖 프로필, 사용자 모델 백업, 역사적 승인 의미, Git history 및 실제 사용자 home의 경계를 명시했다.
- **검증 한계:** 임시 설치 행동과 실제 Codex runtime 역할 선택의 증거를 구분했다.
- **문구 검사:** spec 자체에 금지 접두사를 연속된 문자열로 쓰지 않았다. 미완성 항목이나 승인에 필요한 추가 결정은 없다.
- **다음 단계:** CEO가 초안을 저장·통합·자체 검토한 뒤 written-spec 승인을 받아야 한다. 그 이후 전체 구현 계획을 작성한다.
