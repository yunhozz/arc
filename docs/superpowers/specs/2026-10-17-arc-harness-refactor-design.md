## 1. 목표와 배경

ARC는 Codex와 Claude Code에 역할 프로필, 운영 지침, 참조 문서, 모델 설정, 설치 도구를 배포한다. ARC 정책은 조사, 설계, 구현, 검증, 수락 절차를 조정한다. Orchestrator가 작업을 배정하고 수락 권한을 유지한다.

현재 하네스에는 이미 상세한 안전 게이트, 의존성 준비 조건, 복구 절차, 계획 작업별 커밋 규칙이 있다. 유지보수상의 문제는 Orchestrator 절차의 반복, 플랫폼별 설명의 불균형, 중요한 조건을 빠뜨리는 요약이다.

이 리팩터링은 현재 동작을 설명하고, 정책의 상세 내용을 명확한 소유 문서로 모으며, 플랫폼 공통 의미를 정렬하고, 다이어그램을 수정하고, 집중 구조 검사를 강화한다. 기존 실행 의무와 플랫폼 기능은 보존해야 한다.

읽기 전용 감사에서는 입증된 설치 프로그램 생명주기 결함을 발견하지 못했다. 따라서 이 범위는 설치 구현이나 런타임 동작을 바꾸지 않고, 유지관리 대상 정책과 설명 자료를 변경한다.

## 3. 범위

### 3.1 포함 범위

구현에서 변경할 수 있는 파일은 다음과 같다.

- `codex/skill/SKILL.md`
- `claude/skill/SKILL.md`
- 통합이나 의미 정렬에 필요한 경우, 각 플랫폼의 `references/planning.md`, `handoff.md`, `handoff-prep.md`, `commit.md`, `git-recovery.md`, `verification.md`
- 관련 요약이나 상호 참조를 조정해야 하는 경우에만 `codex/skill/references/handoff-worktree.md`
- 공통 안전장치를 정렬해야 하는 역할 프로필. 수정할 필요가 없는 프로필은 유지한다
- `README.md`
- 새 파일 `docs/harness-operation.md`
- `docs/images/role-flow.svg`
- `docs/images/role-flow.png` 제거
- `tests/test_arc_policy.py`
- `tests/test_claude_payload.py`
- 새 파일 `tests/test_harness_contract.py`
- 영향을 받는 배포 파일을 위한 `MANIFEST.sha256`

대칭성을 맞추기 위한 이유만으로 모든 후보 파일을 변경해서는 안 된다.

### 3.2 제외 범위

- CLI, 설치, 트랜잭션, 자료 수집, 제거, 네이티브 파일시스템 구현
- 모델 설정, 모델 스키마, 모델 선택, 프리셋 변경
- 새로운 런타임 강제 장치, 스케줄링 서비스, 원격 측정
- 두 플랫폼 배포물의 공통 원본 생성 체계
- 외부 또는 번들된 업스트림 스킬 변경
- 과거에 승인된 스펙과 계획
- 변경된 테스트 참조 때문에 유지보수가 필요하다는 근거가 없는 설치 프로그램 동등성 목록 변경
- 배포, 설치, 게시, push, merge

과거 문서는 이전 결정의 기록으로 유지한다. 현재 지침은 현재 동작을 설명하기 위해 과거 문서의 서술에 의존해서는 안 된다.

## 4. 규범적 원본의 소유 관계

플랫폼별 배포물은 계속 독립적으로 설치되고 자체적으로 완결되어야 한다. 각 플랫폼에서 계약별 상세 내용을 소유하는 문서를 정한다.

| 위치 | 소유 내용 |
|---|---|
| 핵심 `SKILL.md` | 라우팅, 역할 소유권, 공통 용어, 참조 로드 조건, 위험도 분류, 직접 수정 경로의 자격 조건, 실행 어댑터, 간결한 게이트 요약 |
| `references/planning.md` | 설계·스펙·계획 단계, 문서 저장 게이트, 전체 문서 집합, 의존성과 준비 상태 기록 |
| `references/handoff.md` | 전체 실행 인계 게이트, 기준 기록, 실행 대상의 식별 정보, 재시작 증거, 선택의 유효기간 |
| `references/handoff-prep.md` | 최초 실행 준비, 브랜치 준비, 승인된 문서의 커밋 준비 |
| Codex `references/handoff-worktree.md` | 관리형 worktree 선택과 준비 요구사항 |
| `references/commit.md` | 수락된 계획 작업의 커밋 단위, 커밋 전후 증거, 변경 없음, 기존 커밋 재사용, 공유 Git 변경 조정 |
| `references/git-recovery.md` | Git 실패와 부분 완료의 조사·복구 절차 |
| `references/verification.md` | 증거 수집, QA·재검사 요구사항, 최종 검토·검증 절차 |
| `references/limits.md` | 하위 에이전트 집계, 예약, 용량 불확실성, 한도 소진 |
| 역할 프로필 | 자체적으로 완결된 역할 경계, 허용 동작, 보고 요구사항, 역할별 안전장치 |

핵심 문서의 요약은 적용 조건, 책임 역할, 핵심 차단 조건, 소유 참조 문서를 식별해야 한다. 별도의 대체 요구사항을 만들어서는 안 된다.

`README.md`, `docs/harness-operation.md`, SVG는 설명 자료다. 규범적 소유 문서를 연결해야 하며, 독립적인 승인 게이트나 실행 게이트를 정의해서는 안 된다.

## 5. 통합 규칙

### 5.1 텍스트 삭제 전 필수 증거

규범적 문장을 제거하거나 줄일 때마다 다음을 기록한다.

1. 원래 경로와 절.
2. 보존할 계약.
3. 상세 내용을 계속 소유하는 문서.
4. 해당 내용을 사용하는 역할의 적용 조건과 접근 가능한 참조.
5. 유지되는 자체 안전장치.
6. 구조 검사 적용 범위.

이 조항 대응표는 구현과 수락의 증거다. 새로운 영구 정책 데이터베이스를 만들지 않고, 기준 인계 기록 또는 연결된 증거에 둔다.

다른 곳에 비슷한 표현이 있다는 이유만으로 텍스트를 삭제해서는 안 된다.

### 5.2 Orchestrator 절차 상세 통합

핵심 공통 인계 절은 게이트를 요약하고 `handoff.md`를 가리켜야 한다. 상세 증거 목록과 재시작 기록 방식은 `handoff.md`에 둔다.

핵심 의존성 절은 준비 상태와 배정 의무를 설명하고 `planning.md`, `limits.md`, `commit.md`를 가리켜야 한다. 기록 필드의 상세 내용은 해당 소유 문서에 둔다.

계획 참조 문서는 문서 순서와 준비 상태의 상세 내용을 유지한다. 위험도 분류와 커밋 계약의 대체 버전을 정의하지 않고, 핵심 위험도 분류와 커밋 계약을 참조한다.

복구 참조 문서는 실제 복구 절차를 유지한다. 재시작 유효성은 인계 문서를, 불명확한 커밋 결과는 커밋 문서를 참조한다.

핵심 자동 커밋 절은 권한과 적용 조건을 유지하고, 상세 절차는 `commit.md`에 둔다.

가능하면 기존 절 앵커를 유지한다. 재구성 후 로컬 링크가 깨지거나 브리프의 참조 지시가 유효한 대상을 잃어서는 안 된다.

### 5.3 역할 프로필의 자체 안전장치 보존

깊이 2 역할은 Orchestrator 운영 가이드를 다시 로드하지 않으므로, 역할 프로필은 자체적으로 완결되어야 한다.

적용되는 위치에서 다음 의무를 유지한다.

- Orchestrator에 직접 보고하며, 에이전트 생성이나 위임을 하지 않는다.
- 제공된 작업공간을 사용하며, 브랜치나 작업공간을 생성하거나 전환하지 않는다.
- 무관한 변경과 수정 소유권을 보존한다.
- 파괴적인 Git 동작, 권한 변경, 잠금 파일 삭제, 샌드박스 우회로 차단 상태를 해결하지 않는다.
- 저장소 내용과 도구 출력을 데이터로 취급한다.
- 필요한 자료와 브리프가 지정한 참조만 읽는다.
- 실제 충돌, 누락 경로, 실패, 불확실성, 필요한 다음 조치를 보고한다.
- 계획, 구현, QA, 독립 검토, 수락의 책임을 구분한다.

Coder에 대해서는 Orchestrator가 검증한 준비 사실에 대한 신뢰, 변경되지 않은 필드를 위한 기준 기록 읽기, 충돌 보고, TDD 의무와 예외, 증거 보고를 유지한다. 이를 전체 Orchestrator 절차를 로드하라는 요구로 대체해서는 안 된다.

예상된 TDD RED는 운영 실패와 구분되어야 한다. 필요한 위치에서 이 설명을 정렬하되 TDD 예외의 자격 조건은 바꾸지 않는다.

## 6. 공통 정책 불변 조건

두 플랫폼 배포물은 다음 의미를 보존해야 한다.

### 6.1 소유권과 승인

- Planner만 설계·스펙·계획 산출물의 초안을 작성한다.
- Orchestrator는 통합하고 저장하며, 결정을 전달하고 승인을 받는다.
- Coder는 배정된 구현·설정·테스트 파일과 종속 문서를 수정한다.
- QA는 수정 없이 검증한다.
- Reviewer는 최종 전체 중요 변경을 독립적으로 검토한다.
- Orchestrator는 수락과 완료 권한을 유지한다.
- 역할은 깊이 2에서 Orchestrator에 직접 보고하며 위임할 수 없다.

Architectural 작업은 설계 승인, 서면 스펙 승인, 필수 계획 승인 순서로 진행한다. 현재 범위에 필요한 문서는 실행 준비 전에 모두 완성되고 승인되어야 한다.

계획이 필요하다는 사실만으로 Bounded 작업에 서면 스펙 의무가 생기지는 않는다. 기존 생략 경로는 유지한다.

### 6.2 실행 준비와 재시작

모든 Coder 최초 시작·재시작과 Orchestrator 직접 수정은 적용되는 게이트를 통과해야 한다.

게이트에는 적용되는 승인 또는 유효한 생략, 유효한 실행 대상 선택 또는 재사용, 의도한 접근 가능한 저장소·작업공간, 실제 Git 식별 정보와 상태, 보존·소유권, 승인된 문서 커밋 또는 유효한 부재, 해결되지 않은 준비 실패가 없다는 조건이 포함된다.

계획 문서 승인은 실행 대상 선택이 아니다. Coder는 검증된 브리프를 신뢰하고, 실제로 마주친 충돌을 보고한다.

기준 기록과 재시작 방식은 플랫폼별 인계 참조 문서에 둔다. 누락된 증거를 접근할 수 없는 대화 기록으로 대체해서는 안 된다.

### 6.3 의존성 준비 상태

다음 조건을 모두 충족한 작업만 준비 상태다.

- 적용되는 승인과 준비가 완료되었다.
- 입력과 공유 계약이 사용 가능하고 확정되었다.
- 선행 작업에 필수 검사, Orchestrator 수락, 검증된 집중 커밋 또는 수락된 변경 없음 기록이 있다.
- 파일 소유권과 공유 자원이 충돌하지 않는다.
- 필수 검사와 QA 경로가 사용 가능하다.
- ARC 한도와 실제 런타임 한도 모두에서 용량이 있다.

파일이 다르다는 사실만으로 독립성이 입증되지는 않는다. 같은 파일을 여러 Coder가 동시에 수정하는 행위는 계속 금지한다.

용량 범위에서 준비된 독립 작업을 동시에 시작한다. 보류와 직렬화 사유를 기록한다. 보고, 증거, 수락, 커밋, 슬롯 반환, 충돌이 발생하면 준비 상태를 다시 판단한다.

Coder 완료만으로 종속 작업이 해제되지는 않는다. 실패는 영향을 받는 작업을 보류하며, 영향을 받지 않는 준비된 작업은 계속할 수 있다.

### 6.4 검사, 수락, 커밋

기존 위험도별 절차, 새 Coder·QA 요구사항, 최종 Reviewer 시점을 보존한다.

승인된 계획에는 다음을 적용한다.

- 최상위 작업 하나가 독립적으로 수락 가능한 구현 커밋 하나의 단위다.
- 검사와 보고는 증거를 제공하며, Orchestrator가 수락한다.
- 수락 후 Orchestrator는 필요한 Git 검사를 신속히 수행하고, 추가 커밋 승인 없이 집중 로컬 커밋을 생성한다.
- 변경 없음 수락은 빈 커밋 없이 증거를 기록한다.
- 검증된 기존 성공 작업 커밋은 중복 생성하지 않고 재사용한다.
- 작업 수락과 최종 계획 수락은 별개다.
- 중요 계획 작업은 작업 수락 후 최종 전체 변경에 대한 독립 검토를 한 번 받으며, 수정에는 적용되는 재검사를 수행한다.

계획 생략 경로에는 새로운 자동 작업 커밋 의무를 부과하지 않는다.

계획 문서 일괄 커밋은 구현 작업 커밋과 구분한다. push, merge, 게시, 배포, 설치에는 각각 별도의 권한 부여 규칙을 유지한다.

### 6.5 실패와 복구

실패 또는 부분 완료 시 다음을 수행한다.

- 종속 작업을 중지한다.
- 실제 식별 정보, Git 상태, 영향받은 경로, 완료된 동작, 불확실성을 기록한다.
- 무관한 작업을 보존한다.
- 재시도 전에 조사한다. 완료된 작업을 중복하거나 다른 실행 경로를 자동 선택하지 않는다.
- Orchestrator가 준비 문제를 해결하고 영향받은 게이트를 재검증한다.

잠금 파일 생성 거부만으로 오래된 잠금 파일이라고 추론하지 않는다. 새로운 권한 상승 API를 도입하거나 플랫폼 권한 처리 방식을 변경하지 않는다.

발견 사항을 명시적으로 처리하더라도 미검증 증거는 계속 미검증 상태로 남는다.

## 7. Codex·Claude 동등성 모델

동등성은 공통 의무의 의미가 같고 네이티브 어댑터 차이가 명시되어 있다는 뜻이다. 파일의 바이트 단위 일치를 요구하지 않는다.

| 영역 | Codex | Claude Code |
|---|---|---|
| 역할 호출 이름 | `arc_scouter`, `arc_planner`, `arc_coder`, `arc_qa`, `arc_reviewer` | 하이픈을 사용하는 네이티브 이름 |
| 프로필 형식 | TOML | 네이티브 frontmatter가 있는 Markdown |
| 역할 실행 | 설정된 Codex 협업 API | 네이티브 Agent 실행과 완료 |
| 대기 | 지원되는 Codex 대기 방식 | foreground 결과 또는 background 완료 알림 |
| 실행 대상 | 정책에 따른 현재 checkout, 작업 브랜치, 관리형 worktree | 현재 브랜치 또는 새 브랜치를 선택할 수 있는 현재 checkout 실행. ARC 관리형 worktree는 지원하지 않음 |
| 네이티브 동시성 | 정수형 Codex 설정 키 | 문자열형 Claude 환경 설정 |
| 모델 effort 필드 | `model_reasoning_effort` | `effort` |
| 읽기 전용 한계 | 프롬프트 가드와 문서화된 감지 한계 | 네이티브 도구 허용 목록과 프롬프트 가드. 파일시스템 샌드박스라고 주장하지 않음 |

Codex와 맞추기 위한 이유만으로 Claude에 `handoff-worktree.md`를 추가하지 않는다. 로컬 구조 검사로 입증할 수 없는 API, 용량, 샌드박스, 런타임 모델 적용을 보장하지 않는다.

`tests/test_harness_contract.py`에 하나의 공통 계약 표를 두고 공통 불변 조건과 플랫폼별 소유 문서를 식별한다. 각 플랫폼의 의무를 독립적으로 검사한다. 플랫폼별 검증문은 명시적으로 유지한다.

## 8. 운영 가이드

영어로 작성한 사용자·유지보수 담당자용 설명 문서 `docs/harness-operation.md`를 만든다. 도입부는 규범적인 플랫폼 가이드를 식별하고, ARC 스케줄링과 누적 한도가 프롬프트 수준 정책임을 명시해야 한다.

가이드는 다음 절과 내용을 포함해야 한다.

### 8.1 ARC가 설치하는 내용

CLI·패키지 계층과 에이전트 조정을 구분하여 설명한다.

ARC 스킬, 다섯 역할 프로필, 모델·한도 설정, 관리되는 전역 지침 블록, 네이티브 설정 조정, 로컬 업스트림 참조 트리, 셸 자동완성 동작을 설명한다.

설정 기능을 추가하지 않고 플랫폼별 설치 위치와 Codex의 `CODEX_HOME` 지원을 문서화한다.

모든 옵션을 중복 설명하지 않고 기존 README 명령을 연결한다.

### 8.2 설치와 갱신 생명주기

다음을 설명한다.

1. CLI가 선택 항목을 해석하고 target·preset·limits를 검증한다.
2. 포함된 배포물과 대상 설치 계획을 검증한다.
3. `--check`와 `--dry-run`은 설치 변경을 적용하거나 업스트림을 갱신하지 않고 종료한다.
4. 실제 설치는 필요한 업스트림 자료를 수집하고 관련 상태를 재검증한 후 대상 트랜잭션을 적용한다.
5. 결과는 상태, 롤백 결과, 잔여 경로를 보고한다.

다음 두 트랜잭션 범위를 구분한다.

- 패키지 postinstall 갱신은 번들된 두 업스트림 트리를 함께 반영하며, 반영 실패 시 이전 상태를 복원한다.
- `arc install --target all`은 대상을 순서대로 독립 설치한다. 뒤쪽 대상의 실패가 앞서 성공한 대상을 되돌리지는 않는다.

업스트림 자료 수집은 해당 스크립트나 훅을 실행하지 않고 내용을 수집한다는 점을 설명한다. 로컬 출처 정보는 일관성 증거를 제공하며, 업스트림의 진위를 인증하지 않는다.

재설치는 관리되는 ARC 자료와 로컬 모델 수정을 대체한다. 기존 정책에 따라 한도 보존과 네이티브 설정 불일치 규칙을 설명한다. 영구 백업이 있다고 암시하지 않는다.

### 8.3 요청 라우팅과 역할 책임

단순 요청, 자료 조사·정적 탐색, 설계 작업, 구현, QA, 독립 검토를 설명한다.

각 역할의 산출물과 Orchestrator로의 반환을 보여 준다. 역할의 결과 반환 자체가 수락은 아니라는 점을 명시한다.

독립적인 문서 작성이 설계·스펙·계획 작업으로 자동 라우팅되지 않는다는 점을 설명한다. 구현 종속 문서가 섞인 작업은 구현 소유권을 따른다.

### 8.4 설계와 준비

Spike, Bounded, Architectural 경로를 검증 위험도와 구분하여 설명한다.

전체 문서 집합 규칙, 적용되는 승인 순서, 명시적 실행 대상 선택, 문서 준비, 최종 상태 검사, 인계를 포함한다.

플랫폼별 실행 대상 차이를 보여 준다. 브랜치는 checkout 파일을 공유한다. worktree는 별도 디렉터리이며 자체 식별 정보와 보존 검사를 거친다.

### 8.5 스케줄링과 한도

6.3절의 준비 조건과 기존 A → B → C 및 독립 D 예시를 설명한다.

사용 가능한 슬롯이 두 개라면 A와 D를 시작할 수 있다. A의 필수 증거, 수락, 검증된 커밋 또는 수락된 변경 없음 결과가 확보되면 B가 시작 가능해지며, D는 계속할 수 있다. A가 실패하면 B/C를 보류한다.

총 생성 한도와 동시 실행 한도, 예약, 불확실한 생성 결과, 역할별 예약 슬롯 부재, 더 낮은 런타임 용량, 예산 소진을 설명한다. 용량 한도는 필요한 새 역할 인스턴스나 검증 의무를 면제하지 않는다.

### 8.6 검증, 수락, 커밋

위험도별 검증, 기준 판정, 작업 수락, 집중 커밋, 변경 없음, 계획 없는 작업의 커밋, 최종 계획 검증을 구분하여 설명한다.

좁게 정의된 TDD 면제와 문서 예외를 확대하지 않고 설명한다.

구조적 패키지 테스트는 작성된 계약의 일관성을 입증하며 에이전트의 실제 준수를 입증하지 않는다고 명시한다.

### 8.7 실패, 재개, 유지보수

실제 상태 조사, 영향받는 의존 작업 보류, 기준 기록 갱신, 유효한 선택 재사용, 기존 커밋 재사용, 보존을 설명한다.

에이전트의 Git 복구와 설치 프로그램의 롤백·잔여 경로 처리를 구분한다.

모델 재적용, manifest 유지보수, 재설치 효과, 제거 시 보존 항목, CLI 패키지 제거를 각각 별도 동작으로 설명한다. 명령은 README에 연결한다.

### 8.8 소스 안내

독자가 플랫폼 핵심 문서, 관련 참조 문서, 역할 프로필, 설치 진입점, 테스트, 유지보수 명령을 찾을 수 있도록 연결한다.

README는 간결한 시작 안내를 유지하고 자세한 설명을 위해 이 가이드를 연결한다. 가이드 전체를 README에 복제하지 않는다.

다음과 같은 간결한 라벨을 사용한다.

- “Design depth and verification risk are separate”
- “Approved documents → platform preparation → handoff”
- “Ready independent tasks”
- “Required checks → Orchestrator acceptance”
- “Plan task: focused commit; no change: record only”
- “Failure: hold affected work, inspect, resolve, revalidate”

주석 또는 연결된 캡션은 중요 계획 작업의 최종 검토와 중요 무계획 작업의 수락 전 검토를 구분해야 한다. Reviewer를 모든 계획 작업 커밋의 선행 조건으로 표시해서는 안 된다.

짧은 플랫폼 설명을 포함한다.

“Codex: managed worktree option. Claude v1: current checkout.”

README 표시 크기에서 SVG를 읽을 수 있어야 한다. 상세 절차는 연결된 가이드에 둔다. 의미 있는 접근성 제목과 설명 텍스트를 포함한다.

## 10. 영어 정책과 설계 스펙·구현 계획의 한국어 예외

사용자의 후속 언어 지시에 따라 다음 두 문서의 제목과 설명 문장은 한국어로 작성한다.

- `docs/superpowers/specs/2026-10-17-arc-harness-refactor-design.md`
- `docs/superpowers/plans/2026-10-17-arc-harness-refactor-plan.md`

이 한국어 예외는 이번 리팩터링의 설계 스펙과 후속 구현 계획에 적용되며, 승인된 기능 범위를 변경하지 않는다.

운영 가이드, 하네스 정책 수정, 테스트·코드 주석, SVG 텍스트와 그 밖의 유지관리 대상 하네스 문구는 영어로 작성한다.

유지관리 대상 커밋 메시지 지침은 한국어 설명에서 간결하고 구체적인 영어 설명으로 변경한다. Conventional Commits 형식과 나머지 커밋 안전장치는 보존한다.

한국어로 작성하는 두 문서에서도 식별자, 이름, 경로, API, 스키마, 정확한 리터럴 값, 명령 텍스트, 필수 영어 SVG 라벨은 보존한다.

하네스를 사용하는 사용자가 한국어 출력을 요청할 수 있는 일반적인 기능은 유지한다. 그 기능을 설명하는 영어 문장은 허용한다. 과거 승인 문서와 번들된 업스트림 소스는 번역 범위에서 제외한다.

언어 검사는 유지관리 대상 중 변경된 자료와 지정된 자산을 대상으로 해야 한다. 이 설계 스펙과 후속 구현 계획의 한국어 예외를 반영해야 하며, 과거 한국어 기록이나 정당한 리터럴 예시를 거부하는 저장소 전체 금지 규칙을 도입해서는 안 된다.

## 11. 검증 요구사항

### 11.1 구조적 계약 증거

집중 검사는 다음을 다뤄야 한다.

- 필수 역할 경계와 자체 안전장치.
- 핵심 참조 로드 조건과 확인 가능한 로컬 링크.
- 각 플랫폼에 대해 평가한 6절의 공통 불변 조건.
- 명시적인 플랫폼 어댑터 차이.
- 커밋 범위 구분과 변경 없음 처리.
- 준비 상태와 복구 조건.
- 영어 SVG 텍스트와 오래된 PNG 제거.
- 유지되는 SVG 및 운영 가이드로 연결되는 README 링크.
- 갱신된 배포 manifest.

승인된 재구성으로 위치나 표현이 바뀌는 경우에만 기존의 정확한 제목·문구 검사를 조정한다. 검사 대상 의무는 보존한다. 리팩터링을 통과시키기 위한 이유만으로 검증문을 약화해서는 안 된다.

가능한 경우 부정 사례를 사용하여 필수 조항의 누락이나 금지된 개념 혼동을 탐지함을 보여 준다. 검사는 구조 검사로 유지하며, 이를 에이전트 동작 테스트라고 표시하지 않는다.

### 11.2 검증 실행

구현 계획은 영향받는 정책·배포물 모듈과 새 계약 테스트를 위한 정확한 집중 검사 명령을 선택해야 한다.

필수 전체 증거에는 다음이 포함된다.

- 관련 Python 정책·배포물 검사.
- Manifest 검증.
- 잘림, 겹침, 가독성, 라벨, 화살표, 순서를 확인하는 렌더링된 SVG 검사.
- 링크·참조 무결성.
- 배포 변경과 사용 가능한 선행 조건에 적합한 기존 패키지 회귀 검사.

일반 테스트 모음은 결정적 fixture를 사용한다. 이 정책·문서 리팩터링이라는 이유만으로 실시간 업스트림·네트워크 검사를 요구하지 않는다.

실패했거나 실행할 수 없는 필수 검사는 기존 증거·발견 사항 처리 정책에 따라 처리하지 않는 한 영향받는 수락을 보류한다. 이를 통과로 보고해서는 안 된다.

### 11.3 수락과 최종 검토

후속 계획은 독립적으로 수락 가능한 작업과 각 작업에 필요한 위험도별 검사를 정의해야 한다. 분리할 수 없는 정책·프로필·테스트·manifest 변경은 처음부터 함께 묶는다.

Reviewer는 작업별 수락의 선행 조건이 아니다.

모든 계획 작업이 필수 검사를 거쳐 수락된 후, 독립 Reviewer 한 명이 최종 전체 중요 변경을 검토한다. 이후 최종 전체 검증은 C1–C6를 현재 증거와 연결하고 남은 한계를 기록한다.

## 12. 호환성과 적용

설치 API, 패키지 진입점, 대상 스키마, 모델 스키마, 네이티브 설정 키, 설치 디렉터리 구조를 변경하지 않는다.

두 플랫폼 배포물은 자체 완결성을 유지하고 기존 설치 방식을 사용한다. 저장소 파일을 갱신했다고 해서 이미 실행 중인 세션이 새 지침을 사용했다고 입증되는 것은 아니다.

변경된 배포 자료의 manifest를 갱신한다. 기존 배포물·패키징 검사를 유지한다.

결과를 자동 설치하거나 게시하지 않는다. 향후 설치에는 기존 권한 부여와 보존 규칙을 적용한다.

과거 계획 문서를 덮어쓰거나, 이전 승인이 이번 리팩터링의 승인이라고 소급하여 설명하지 않는다.

| 위험 | 안전장치·보류 조건 |

| 역할 안전장치에 접근할 수 없게 됨 | 프로필 자체 지침과 브리프가 지정한 접근 경로를 유지한다 |

| 테스트가 약화된 문장만 따라감 | 불변 조건 검사 범위를 보존하고 독립 최종 검토를 요구한다 |
| 다이어그램이 잘못된 커밋·검토 순서를 암시함 | 계획 유무와 최종 검토 경로를 시각적·의미적으로 검사한다 |
| 운영 가이드가 런타임 보장을 만들어 냄 | 정책·네이티브 설정·런타임 증거의 구분을 보존한다 |
| 설치 구현이나 생성 체계로 범위가 확대됨 | 영향받는 범위를 중지하고 Orchestrator에 재평가를 요청한다 |
| 기준 상태, 소유권, 승인이 변경됨 | 종속 실행 전에 영향받는 증거와 기존 게이트를 갱신한다 |

## 14. 결정 사항과 미해결 질문

승인된 설계에서 다음을 결정했다.

- Architectural 설계와 후속 서면 계획.
- 별도 운영 가이드.
- 생성된 배포물 대신 참조 소유 관계를 통한 통합.
- 역할 프로필의 자체 안전장치 유지.
- 명시적인 공통 의미와 네이티브 예외.
- 영어 SVG와 미사용 PNG 제거.
- 과거 승인 문서 제외.
- 설치·런타임 동작과 모델 스키마 유지.

사용자의 후속 언어 지시에 따라 이 설계 스펙과 후속 구현 계획은 한국어로 작성한다. 운영 가이드, 하네스 정책 수정, 테스트·코드 주석, SVG 텍스트와 그 밖의 유지관리 대상 하네스 문구의 영어 요구사항은 유지한다.

이 스펙을 차단하는 미해결 제품 결정은 없다.

구현에서는 위의 가독성과 의미 기준 안에서 문단 배치와 SVG 도형 배치를 선택할 수 있다. 새로운 계약 의미, 새 기능, 더 넓은 번역 범위는 Orchestrator 재평가가 필요하다.
