# QA 근거 보고와 발견사항 인계 계약 설계

## 목적

QA 보고에서 검사 명령의 성공과 수락 기준의 입증을 분리하고, 모든 수락 기준에 확인 범위와 근거를 연결한다. Reviewer가 재현 가능한 행동 결함을 발견하면 CEO가 Coder에게 수정시키고, 수정 후 QA가 해당 동작을 재확인하도록 인계 흐름을 명확히 한다.

## 배경과 현행 계약

위험도별 최소 흐름은 작은 저위험 변경의 CEO 집중 확인, 일반 행동 변경의 독립 QA, 중요·고위험 변경의 QA 후 최종 전체 변경 독립 Reviewer 검토다. QA 실패는 해결 또는 명시적 처분 전까지 acceptance에 도달할 수 없으며, 수정으로 무효화된 행동 검사는 QA가 다시 수행한다.

현재 공통 지침은 QA가 행동·테스트 또는 승인된 구조 검사를 실행하고, 명령·결과·증거·미해결 사항·한계를 보고하도록 한다. 그러나 각 수락 기준과 검사·증거의 연결 및 검사 통과와 기준 입증의 구분을 QA 보고 항목으로 강제하지 않는다. Reviewer의 범위는 코드 정확성·사실성·보안 검토이고 QA 실행은 하지 않는다. Reviewer가 찾은 기준 연계 행동 결함을 Coder 수정과 QA 재확인으로 전달하는 세부 인계도 명시되어 있지 않다.

## 승인된 사용자 의도

- QA 보고는 수락 기준별 확인 방법과 근거를 보인다.
- 근거가 없는 기준은 미검증으로 남긴다.
- “검사 실행 통과”와 “요구 동작 입증”을 구분한다.
- Reviewer가 발견한 재현 가능한 승인 기준상 행동 결함은 수정 후 QA가 재확인한다.
- 실행 검사만으로 판단하기 어려운 코드 구조·설계·사실·보안 문제는 Reviewer 검토 범위에 둔다.
- QA가 실패한 상태에서는 Reviewer 단계로 넘어가지 않고, CEO가 Coder에게 수정 작업을 배정한 다음 QA 재검증을 거친다. 중요·고위험 변경은 QA가 통과한 최종 관련 상태에서 Reviewer에게 전달한다.

## 설계

### 1. 기준별 상태와 근거

QA는 brief에 있는 모든 수락 기준을 결과에 포함한다. 각 기준에는 확인 방법과 범위, 실행 결과, 접근 가능한 근거, 기준 판단, 미확인 범위를 연결한다. 배정 범위 밖이거나 검사 부재·환경 차단·증거 부족으로 확인하지 못한 기준도 누락하지 않고 `미검증`으로 기록한다. 식별자가 없는 기준은 brief의 원문으로 가리킨다.

보고에서는 다음 두 축을 구분한다.

| 축 | 값 | 뜻 |
|---|---|---|
| 검사 실행 결과 | 통과, 실패, 미실행, 환경 차단 | 명령·테스트·관찰 절차의 실행 결과 |
| 수락 기준 판단 | 입증, 불충족, 미검증 | 해당 기준의 기대 동작이 증거로 확인되었는지 |

검사 실행 성공만으로 기준을 입증 처리하지 않는다. 입증하려면 해당 기준의 조건과 기대 결과, 실제 관찰 결과를 연결하는 근거가 있어야 한다. 부분 확인은 입증된 범위와 남은 미검증 범위를 함께 기록한다. 보고에 공통 `PASS`가 필요하면 그 의미를 실행 결과에만 한정하고, 수락 기준별 판단을 대체하지 않는다.

정책·설정의 구조 검사는 그 구조에 대한 기준을 입증할 수 있다. 정적 구조 결과를 실제 행동, 설치 결과 또는 실행 중인 역할의 지침 준수 증거로 확대하지 않는다.

### 2. QA 실패와 Reviewer 발견사항의 인계

QA가 기준을 불충족으로 판단하거나 실행 가능한 검사에서 실패를 발견하면 CEO는 해당 결과를 Coder의 수정 brief에 포함한다. 수정이 끝나면 QA가 결함 재현 경로와 변경으로 무효화된 관련 검사를 다시 확인한다. QA 재확인이 해결·미해결·미검증 중 무엇인지 근거와 함께 보고하기 전에는 Reviewer 단계로 진행하지 않는다.

Reviewer는 QA와 같이 행동 검사를 실행하지 않는다. 수락 기준과 연결되는 재현 가능한 행동 결함을 찾으면 CEO에게 기준, 기대 동작과 관찰된 문제, 관련 소스, 재현 조건·절차 및 근거를 전달한다. 재현 절차를 소스에서 추론했지만 실행으로 관찰하지 못했다면 그 구분을 표시한다. CEO는 이를 Coder 수정 brief와 QA의 수정 후 확인 항목에 반영한다. 중요·고위험 변경에서는 QA 확인 뒤 Reviewer가 수정된 최종 전체 변경을 다시 검토한다.

코드 구조·설계·사실·보안 등 실행 검사만으로 판단할 수 없는 발견사항은 Reviewer가 근거와 함께 계속 다룬다. 동작 확인도 가능한 보안·인터페이스 문제는 QA 행동 검증과 Reviewer 소스 검토를 각각 수행할 수 있다.

### 3. CEO acceptance

CEO는 QA의 전체 실행 결과 하나만으로 수락을 결정하지 않는다. 기준별 입증·불충족·미검증 상태, Reviewer 발견사항, 재검증 근거와 증거 공백을 확인한다. 기존 정책대로 미해결 finding이나 증거 공백은 해결하거나 명시적으로 disposition한다. disposition은 미검증 상태를 입증으로 바꾸지 않으며, 완료 보고도 잔여 미검증 범위를 보존한다.

저위험 변경처럼 QA 에이전트를 호출하지 않는 경우에도 CEO의 집중 확인은 확인된 기준과 근거 및 미검증 범위를 같은 방식으로 구분한다. 위험도별 역할 호출 조건과 QA의 호출 범위는 바꾸지 않는다.

## 영향을 받는 파일

- `skill/SKILL.md`: 기준별 증거 계약, QA 실패 및 Reviewer 발견 인계, CEO acceptance 원칙.
- `agents/harness-qa.toml`: 필수 기준별 결과와 실행/입증 상태 보고 형식.
- `agents/harness-reviewer.toml`: 기준 연계 행동 발견의 근거·재현 상태·CEO 인계.
- `README.md`: 위험도 흐름과 “검사 통과” 대 “기준 입증” 구분의 짧은 설명.
- `MANIFEST.sha256`: 변경된 배포 파일의 digest 동기화.

설치기, 위험도 분류, 모델 설정, 직접 보고 구조, QA 읽기 전용 범위, Reviewer의 QA 실행 금지, CEO의 수락 권한은 변경하지 않는다. 새 보고 도구나 별도 자동화도 추가하지 않는다. 이번 설계는 저장소의 Harness 원본을 다루며, 설치된 사용자 프로필을 수정하거나 설치기를 실행하는 범위는 포함하지 않는다.

## 수락 기준

1. 모든 QA 보고에서 각 수락 기준은 확인 방법·범위·실행 결과·접근 가능한 근거·기준 판단에 연결되며, 확인하지 못한 기준은 사유와 함께 미검증으로 남는다.
2. 검사 실행 결과와 기준 판단이 별도 필드이며, 실행 통과만으로 행동 기준이 입증되지 않는다.
3. 부분 확인, 범위 밖, 검사 부재, 환경 차단은 전체 통과로 합쳐지지 않고 남은 증거 공백이 보인다.
4. QA 실패 시 CEO가 Coder 수정과 QA 재확인을 먼저 완료하기 전 Reviewer 단계로 진행하지 않는다.
5. Reviewer의 승인 기준 연계 행동 결함은 근거와 재현 상태를 구분해 CEO에게 전달되고, Coder 수정 후 QA 확인으로 이어진다.
6. 실행 검사가 다룰 수 없는 Reviewer 발견사항, 중요·고위험 변경의 QA 후 전체 review, 기존 위험도별 흐름과 역할 권한이 유지된다.
7. README와 공통 지침, 두 프로필의 정책이 일치하며 `MANIFEST.sha256`이 변경된 배포 항목과 일치한다.
8. 정적 구조 검사나 코드 문구 확인을 실제 모델 런타임 준수의 증거라고 주장하지 않는다.

## 검증과 한계

구현 계획은 QA 보고 기준표, 검사 통과·기준 미검증 조합, 환경 차단, Reviewer 행동 발견의 수정·QA 재확인 순서, 실행 검사로 확인할 수 없는 Reviewer 발견, README·프로필·공통 지침 정합성을 확인해야 한다. Manifest도 변경된 항목과 일치해야 한다. Harness 문구·구조 검사는 live agent runtime에서의 모델 준수까지 증명하지 않는다.

## 자체 검토

- 세 사용자 요구를 공통 정책, QA 실행 보고, Reviewer 발견 인계 및 CEO acceptance로 각각 연결했다.
- QA 실패 후 Reviewer로 넘어가지 않는 순서를 명시하고, 수정 후 QA의 영향 검사를 배치했다.
- 구조 검증이 행동·실행·런타임 증거로 오해되지 않도록 범위를 분리했다.
- 기존 위험도 흐름과 역할 권한을 보존하고 설치 작업·자동화·불필요한 도구를 범위 밖에 두었다.
