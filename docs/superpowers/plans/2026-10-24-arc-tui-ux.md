## 공통 제약

- 제품 TUI는 영어다. 홈은 정확히 `Configure`, `Update`, `Uninstall`, `Exit`다.
- Configure 아래에 `Install / Reconfigure`, `Change Preset`을 둔다.
- 수동 Workflow 메뉴·새 명령·숨겨진 단축키를 제공하지 않는다. 자동 runtime·연동은 그대로 유지한다.

- `Validate (read only)`를 제거하고 별도 validation API를 만들지 않는다.
- README와 보호된 소스 변경에 맞춰 기존 생성기로 `MANIFEST.sha256`를 갱신한다. 자동 runtime 파일의 내용·해시는 변경하지 않는다.

## 검토에서 집중할 입력과 조건

아래 다섯 조건을 T1의 테스트에 포함한다.

1. 매우 긴 경로·여러 줄 설명·제어문자가 포함된 상세: 끝까지 읽을 수 있고 terminal 명령으로 실행되지 않는다.
2. `managedPaths`, `removals`, 전역 변경에 같은 경로가 반복되는 계획: 건수가 부풀지 않고 삭제와 수정 의미가 구분된다.
3. 계획이 없거나 일부 정보만 있는 Update: 알려지지 않은 건수를 0건으로 표시하지 않고 보존·세션 종료 정보를 유지한다.
4. 상세 확인 중 축소·확대: 잘린 내용을 확인 완료로 처리하거나 Apply를 허용하지 않는다.
5. Edit·Escape·Details 왕복과 연속 Enter: 초안·snapshot·종료 코드를 유지하고 의도하지 않은 실행을 하지 않는다.

## T1. TUI 탐색·검토·표시와 설명을 함께 개선

**목표·범위:** C1–C7 전체를 구현한다. 위 소유 파일을 하나의 연결된 작업으로 다룬다. 홈·검토·페이지·렌더링은 같은 상태와 테스트를 공유하므로 별도 수용 작업으로 분리하지 않는다.

**선행 조건·의존성:** 승인 설계, 이 계획의 사용자 승인, Orchestrator의 문서 준비·fresh Implementer handoff 완료. 다른 구현 선행 작업은 없다. 동일 파일을 수정하는 병렬 Implementer를 배정하지 않는다.

### 유지·추가할 인터페이스와 Escape 계약

- `runTui(options) -> Promise<number>`와 관리 서비스의 `prepareOperation(context, options)`, `executeOperation(context, prepared)` 계약을 유지한다.
- `runSetup({ui,statuses,draft,kind,prepare}) -> Promise<prepared|null>`를 유지한다. `ui.review()`의 `'edit'`는 설정 복귀, `'cancel'`은 작업 종료, `'apply'`는 준비된 객체 반환이다.
- 공통 `menu(title, rows, options) -> Promise<number|null>`는 **모든 화면에서 Escape를 동일하게 `null`로 반환**한다. 직접 세션을 종료하거나 작업을 실행하지 않는다.
- `menu()`의 `backLabel:'exit'` 선택은 footer 문구에만 영향을 준다. 기본값은 `'back'`이며 키 이벤트와 반환 의미를 바꾸지 않는다.
- **홈 호출자 `runTui()`는 `choice === null`이면 현재 `code`를 반환한다.** 초기값은 `0`이며, 앞선 실행 결과가 실패 코드라면 그 값을 유지한다. 이 반환은 기존 `finally`를 거쳐 `session.dispose()`를 실행한다. 홈의 `Exit` 선택도 같은 종료 경로를 사용한다.
- Configure·대상·설정 등 하위 호출자는 같은 `null`을 해당 이전 단계로의 복귀로 해석한다. `review()`는 `null`을 설치·Preset·Uninstall에서 `'edit'`, Update에서 `'cancel'`로 변환한다.
- `review(title, prepared)`의 기존 문자열 반환값을 유지한다. 명시적 `Cancel`은 작업 종류와 무관하게 `'cancel'`이다.
- 공통 footer 생성 함수는 `render.mjs`의 `navigationHint(mode, {backLabel, hasNext}) -> string`으로 둔다. `mode`는 `menu`, `text`, `page`, `reviewPage`, `busy`다.
- terminal session에 `viewport() -> {columns,rows}`를 추가한다. 실제 session과 app 테스트의 session 대역이 같은 인터페이스를 사용한다.
- 상세 줄바꿈은 `render.mjs`의 `wrapDetailRows(rows, columns) -> string[]`로 둔다. 외부 문자열을 escape한 뒤 폭에 맞춰 연속 행을 만들며 정보를 생략하지 않는다.
- `renderScreen()`의 기존 `{text,applyEnabled}` 반환을 유지하면서 고정 워드마크용 신뢰된 스타일 범위를 추가할 수 있다. `text`에는 ANSI를 삽입하지 않는다. `terminal.mjs`만 고정 흰색·초록색 스타일을 출력하며 외부 문자열은 스타일 명령의 원천이 될 수 없다.

### 1. 탐색·검토 변경의 실패 테스트

- [ ] `tests/node/tui-app.test.mjs`에서 기존 메뉴 인덱스 기반 시퀀스를 새 구조에 맞게 갱신하고 다음 행동을 검증하는 테스트를 먼저 추가한다.

### 4. 요약·전체 상세·공통 표시 구현

- [ ] `app.mjs`에서 준비된 계획을 작업·대상별 표시 자료로 변환한다. 파일 탐색·서비스 호출·네트워크를 추가하지 않는다.
- [ ] 변경 건수는 대상·분류·정규화된 경로 기준으로 중복 제거한다. 동일 경로의 다른 설명은 버리지 않는다. 분류가 다른 행동은 의미에 맞게 구분한다.
- [ ] 설치·Preset의 관리 경로와 전역 변경은 변경 목록으로, Uninstall의 실제 removals는 삭제 목록으로 표시한다. 보존 정책 설명은 Notes/주요 영향으로 유지하고 실제 열거된 보존 항목 수처럼 계산하지 않는다.
- [ ] Update의 대상은 준비된 plans/state의 실제 제공 정보를 사용한다. global/npx 실행 경로가 아직 확정되지 않은 경우 CLI 교체를 조건부 영향으로 표시하고 임의 조회를 추가하지 않는다.
- [ ] Details를 요약 우선·대상별 전체 목록으로 표시한다. 긴 경로와 설명은 escape 후 줄바꿈하고 viewport에 맞춰 페이지를 구성한다.
- [ ] 필수 상세 확인은 화면에 실제 표시 가능한 순서로 진행한다. 미확인 구간이 남으면 마지막 Apply 확인으로 넘어가지 않는다. resize로 줄바꿈이 바뀌면 확인 위치를 안전하게 다시 계산하거나 해당 상세 확인을 처음부터 다시 요구한다.
- [ ] `render.mjs`의 공통 footer와 작은 ARC 워드마크를 연결한다. `terminal.mjs`에는 viewport·신뢰된 색상 출력만 추가한다.
- [ ] 선택지·필수 정보·footer가 안 보이면 Apply를 차단한다. 큰 장식이나 요약 생략으로 안전 게이트를 우회하지 않는다.
- [ ] 3단계 명령을 다시 실행해 통과를 확인한다.

### 독립 QA와 증거

fresh QA는 위 결과를 확인하고 실제 키 입력으로 다음을 검증한다.

| 범위 | 필수 증거 |
|---|---|
| C1–C4 | 흰색 중심·초록색 강조 및 단색 홈, 정확한 메뉴·footer, Configure 두 경로, 하위 Escape 복귀와 홈 Escape 종료·현재 코드 보존·terminal 복원 |
| C5 | 작업별 Cancel/Edit/Apply/Details, 설치·Preset·Uninstall 선택 유지, Update Edit 없음, Validate 없음, 확인 전 실행 `0` |
| C6 | 중복·정보 누락·다중 대상·긴 경로 상세, 전체 확인 우회 불가, resize 차단·복구, snapshot 객체 유지와 서비스의 stale 거부 |
| 보존 | Update 세션 종료·복구 보고, 제거 보존 설명, 연속 Enter·Ctrl+C·EOF·signal 복원, terminal 직접 PTY 검사 |
| C3·C7 | README 대조, 공개 Workflow 명령 거부 유지, 자동 runtime·연동 파일 불변, setup·집중 테스트 및 PTY 결과 |

명령·종료 코드·skip 여부와 핵심 화면 또는 transcript, 실행 대역의 호출 기록을 반환한다. 실제 Update·Uninstall을 사용자 홈에 실행하지 않는다. QA 실패는 Implementer 수정 → 필요한 QA 재검증을 거친다.

**T1 수용 기준:** C1–C7과 위 필수 검사가 충족되고 QA finding이 해결되어야 한다. Orchestrator가 증거·범위·manifest 변경을 확인하고 수용한 뒤 `feat(tui): ARC 탐색·검토 UX 개선` 한 건의 집중 구현 커밋을 수행한다. Implementer·QA는 stage·commit하지 않는다.

**T1 보류 조건:** 승인되지 않은 파일 변경, backend·runtime·CLI·payload 의미 변경 필요, 불명확한 계획 분류, 상세 누락·확인 우회, stale 검증 약화, terminal 복원 실패, native/PTY 환경 미준비, 예상 밖 Git 상태. 영향받는 작업을 멈추고 관찰 결과와 필요한 해결을 Orchestrator에 반환한다.

## 최종 전체 검증

T1 수용·집중 커밋과 필수 QA 완료 후 독립 Reviewer가 기준 HEAD 이후 최종 전체 변경을 한 번 검토한다. 승인 설계 C1–C7, README, manifest, 자동 runtime 불변, 검토·terminal 안전 경계를 함께 본다. 이는 작업별 Reviewer 게이트가 아니다.

최종 Reviewer finding은 Implementer → Reviewer 재검토로 해결하며 새 QA를 재배정하지 않는다. 초기 최종 리뷰 전에 요구된 QA와 QA 실패 재검증은 생략하지 않는다. 새 변경·실패·미해결 우려가 없으면 통과한 검사를 반복하지 않는다.

Orchestrator가 최종 finding 해결, 승인 범위, 테스트·QA·리뷰 증거와 최종 Git 상태를 확인해 전체 완료를 판단한다. push·배포·publish는 이 계획에 포함하지 않는다.
