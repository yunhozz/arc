> **에이전트 작업자 안내:** 필수 하위 skill은 `superpowers:subagent-driven-development` 또는 `superpowers:executing-plans`다. 작업은 task별로 진행하고 체크박스로 진행 상태를 기록한다.

**Tech Stack:** Node.js `>=22`, ESM, `node:readline`, 기존 safe-fs native 모듈, `node:test`, 기존 PTY·release 검증 도구. 새로운 runtime 의존성은 추가하지 않는다.

## 공통 인터페이스

### Runtime

```text
runWorkflowCommand(args, {
  input: string | undefined,
  output: Writable,
  readInput?: () => string
}) -> Promise<number>
```

`command.mjs`가 제공한다. 기존 인자 해석·JSON 오류·종료 코드를 보존한다. `readInput`은 변경 명령에서만 호출한다. `cli.mjs`는 이 함수를 호출하고 `process.exitCode`를 설정한다. 직접 실행과 import를 구분하여 import만으로 stdin을 읽거나 프로세스를 종료하지 않는다.

### 관리 서비스

```text
ManagementContext = {
  packageRoot, userHome, cwd, env, safeFs,
  deps?: injected operational dependencies
}

inspectTargets(context)
  -> Promise<TargetStatus[]>

TargetStatus = {
  platform, home,
  state: "missing" | "installed" | "incomplete" | "unavailable",
  settings: object | null,
  diagnostics: string[]
}

prepareOperation(request, context)
  -> Promise<PreparedOperation>

PreparedOperation = {
  kind: "install" | "preset" | "uninstall" | "update",
  targets: string[],
  summary: string[],
  details: string[],
  opaque: internal plan/snapshot/context
}

executeOperation(prepared, {context, signal})
  -> Promise<OperationResult>

OperationResult = {
  code: number,
  exitSession: boolean,
  results: Array<{
    platform, status, rollback, residualPaths, error
  }>,
  notices: string[]
}
```

`opaque`는 TUI가 재구성하거나 수정하지 않는다. 준비 단계는 네트워크·변경 작업을 실행하지 않는다. 실행 단계는 준비한 snapshot을 재검증한다.

설치 요청은 target별 설정을 보존할 수 있게 다음 형태를 사용한다.

```text
{
  kind: "install",
  selections: [{
    platform, preset, language,
    maxTotalSubagents, maxConcurrentSubagents,
    concurrentExplicit, skipGlobal
  }]
}
```

Preset 요청은 `{kind:"preset", platforms, preset}`, 제거 요청은 `{kind:"uninstall", platforms, skipGlobal}`, 업데이트 요청은 `{kind:"update"}`다.

### TUI

```text
createTerminalSession({input, output, error, signal?})
  -> {readEvent(), render(view), dispose()}

runTui({input, output, error, context, services?})
  -> Promise<number>
```

`services`의 기본값은 관리 서비스 함수다. 테스트는 이 경계에 호출 기록 함수와 시험 데이터를 주입한다. 입력 이벤트는 `up`, `down`, `enter`, `back`, `interrupt`, `eof`, `resize`, `text`, `backspace`로 정규화한다.

### Workflow 관리

```text
inspectWorkflowWorkspace(cwd)
  -> Promise<{target, workflows}>

loadWorkflowInput(absoluteFile)
  -> Promise<object>

invokeWorkflow({command, cwd, workflowId, input?}, {output})
  -> Promise<number>
```

`invokeWorkflow`는 공통 runtime 명령 전달 함수를 사용한다. 파일 입력·화면 확인으로 actor·approval·revision을 추가하거나 바꾸지 않는다.

## 의존성과 실행 순서

```text
T1 → T2 → T3 → T4 → T5 → T6 → T7
```

이 순서는 runtime·installer·manifest의 공유 소유권을 직렬화한다. TUI를 공개하기 전에 자동화 endpoint와 관리 기능을 준비한다.

Orchestrator는 각 task 시작 전 branch·HEAD·변경 상태·이전 task의 수용·commit·필수 QA 증거를 확인한다. 수정·재검증은 같은 task로 처리한다. 독립적으로 수용할 수 없는 변경이 발견되면 task를 실행 중 임의로 합치지 않고 계획 수정으로 반환한다.

## 최종 전체 검증과 Reviewer

각 task의 수용은 해당 task의 기준·필수 QA로 완료할 수 있다. 최종 Reviewer를 기다리느라 이미 독립적으로 수용 가능한 task의 commit을 미루지 않는다.

모든 task 수용·필수 QA 완료 후 다음을 수행한다.

1. Orchestrator가 C1–C15 증거와 생성물·manifest·배포 결과를 취합한다.
2. 기존 version 불일치와 플랫폼별 미실행·생략의 처리 상태를 명시한다.
3. Reviewer가 전체 최종 diff와 증거를 한 번 독립 검토한다. 공개 문법, 승인 경계, 설치 의존 파일, runtime hash, shell 보존, lifecycle·updater 실패를 집중 검토한다.
4. 최종 Reviewer finding은 Implementer → Reviewer 재검토로 해결한다. 이 단계의 finding에 새 QA를 재배정하지 않는다. 초기 최종 review 전에 요구된 QA와 QA 실패 재검증은 생략하지 않는다.
5. Orchestrator가 finding·필수 검증·범위를 확인하고 전체 완료를 수용한다.

인터페이스 이름과 결과 형태는 task 간 동일하게 정의했다. Review Focus 다섯 항목 모두 소유 task의 테스트에 연결했다. 원본·배포 lifecycle 차이와 안내 전용 postinstall을 T6·T7에서 명시적으로 검증한다.

문서 제목·설명은 한국어이며 제품 TUI의 정확한 영어 문구, API 식별자, 경로, 명령, 코드 값은 유지했다.

실행 중 사용할 테스트는 승인된 스펙의 검증 요구를 구현한다. 이번 계획 작성에서는 테스트를 실행하지 않았다.

남은 사항은 계획의 개별 승인과 실행 전 canonical handoff record 준비다. 기존 package version assertion 불일치는 범위 밖 문제로 기록하며, 전체 검증에서 발생할 기존 실패의 수용 방식은 Orchestrator가 결정해야 한다. 이 문제를 숨기거나 신규 실패를 같은 이유로 면제해서는 안 된다.
